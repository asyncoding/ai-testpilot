## 1. 落地涉及的角色全景

### 1.1 真实企业里的角色清单

| 角色 | 典型职位 | 在本项目里干什么 | 投入形态 |
|---|---|---|---|
| **赞助人 Sponsor** | 研发总监 / 测试总监 / 质量 VP | 给目标、给资源、压跨部门配合、拍板准入准出、对外背书 | 关键节点 1–2 小时/周 |
| **AI 解决方案负责人** | AI 解决方案工程师 | 痛点调研、方案设计、POC/试点交付、评测治理、培训推广——项目第一责任人 | 全职 |
| **领域专家（测试侧）** | 资深测试 / 测试架构师 | 讲清现有用例体系、判定用例质量、标注 oracle、评审 AI 用例、提供历史事故解读 | 试点期 2–4 小时/周 |
| **领域专家（研发侧）** | 资深研发 / 模块 owner | 讲代码架构与术语、确认代码类问答对错、评审 MR 摘要/影响面准确性 | 按需 1–2 小时/周 |
| **一线测试工程师** | 业务测试 | 真实使用：提问、审 AI 用例草稿、反馈采纳/拒绝；**知识库第一批语料的主要生产者** | 融入日常工作 |
| **一线研发工程师** | 业务开发 | 真实使用：看 MR 影响面评论、确认/纠偏归因结论；不额外加任务 | 融入日常工作 |
| **测试开发 / 自动化工程师** | SDET | 对接执行器：梳理测试命令、环境准备、xcodebuild/Gradle 接入、报告解析、CI webhook | 试点期重度参与 |
| **DevOps / 平台工程师** | CI/CD、基础设施 | 给 CI/日志/制品系统的 API 和 webhook 权限、K8s 资源、模型部署环境（GPU 机） | 集中投入 1–2 周 |
| **各系统 Owner** | Git 平台、Jira、Confluence、用例平台、设备云管理员 | 开账号/token、讲 API 限制与限流、确认数据边界、审批写入权限 | 按需，常是推进瓶颈 |
| **安全 / 合规 / IT** | 安全团队、法务合规 | 数据分级、出域评估（代码能不能进模型/云端 API）、私有化要求、审计要求 | 立项期 + 上线评审 |
| **数据 / 算法工程师** | 数据平台、算法团队（大厂有） | 大语料 ETL 支持、embedding/rerank 模型选型微调、评测统计 | POC 期可由 AI 负责人兼任 |
| **项目经理 / PMO** | 研发效能 PM | 排期、跨团队会议、试点团队组织、度量数据收集 | 试点期参与 |

### 1.2 POC 阶段的"一人分饰"映射

个人 Demo 里由建设者承担全部角色，但文档和演示要能说出真实分工：

| POC 里自己做的事 | 真实落地时对应角色 |
|---|---|
| 读 AlarmKitSpike 的 CLAUDE.md、事故文档、用例 | 领域专家访谈 + 语料盘点（需测试/研发专家配合确认） |
| 解析 Markdown 用例、挖 oracle | 资深测试评审确认，AI 负责人实现挖掘流程 |
| 跑 xcodebuild、解析 xcresult | SDET 出命令与环境，AI 负责人做归一化 |
| 设计 JSON 工单结构 | 系统 owner 提供真实 schema，安全确认数据边界 |
| 写 golden set 与评分 | **必须**领域专家共同标注，AI 自说自话的评测没有公信力 |
| 决定接哪些系统、私有化边界 | Sponsor + 安全合规共同拍板 |

## 2. RACI 总表（按工作包）

> R=负责执行，A=最终问责（每行一个），C=被咨询，I=被告知

| 工作包 | AI 负责人 | Sponsor | 测试专家 | 研发专家 | 一线测试 | SDET/平台 | 系统 Owner | 安全/IT |
|---|---|---|---|---|---|---|---|---|
| 痛点调研与场景排序 | **R/A** | C | C | C | C | I | – | – |
| 方案设计与评审 | **R/A** | A | C | C | – | C | C | C |
| 数据分级与出域评估 | R | A | – | – | – | – | C | **R/A** |
| 账号/API/环境开通 | R | A | – | – | – | C | **R** | C |
| 语料盘点与接入 | **R** | I | C | C | C | – | C | I |
| golden set 标注 | R | I | **R**（质量裁定） | C | R（参与） | – | – | – |
| 知识库加工/检索调优 | **R/A** | – | C | C | – | – | – | – |
| Agent 工作流开发 | **R/A** | – | C | – | – | C | – | – |
| 测试执行器对接 | R | – | C | – | – | **R** | C | – |
| HITL 审批流试点 | R | I | C | – | **R**（审批人） | – | C | – |
| 评测与质量报告 | **R/A** | A | C | – | – | – | – | – |
| 培训与推广 | R | **A**（站台） | C | – | R | I | – | – |
| 持续运营（bad case 周会） | **R/A** | I | R | C | R | C | – | – |

**关键认识**：AI 负责人对"系统建得对不对"负责，但有三件事他不能单方面拍板——
①用例/答案对错由**领域专家**裁定；②数据能不能用、出不出域由**安全合规**裁定；
③跨团队推不推得动由 **Sponsor** 负责。提前把这三个 A 交出去，项目才不会卡在"你算老几"。

## 3. 分阶段推进：每步谁做什么

### 阶段 0：立项与调研（2–3 周）

**目标**：拿到 Sponsor 背书、锁定一个种子项目、确认数据边界，输出《场景调研与价值评估》。

| 步骤 | 谁做 | 具体动作 | 产出 |
|---|---|---|---|
| 0.1 找痛 | AI 负责人 | 跟岗观察测试/研发各 3–5 人的一天；收集"找知识、写用例、查失败原因"各花多少时间 | 痛点清单 + 耗时基线 |
| 0.2 排场景 | AI 负责人 + 测试经理 | 按"痛感 × 数据可得性 × AI 适配度"排序；**先选证据链完整、数据已在线的场景**（通常是知识问答或 CI 失败归因，而非开放式用例生成） | 场景优先级矩阵 |
| 0.3 定价值口径 | Sponsor + AI 负责人 | 定 2–3 个北极星指标（如：用例编写耗时、失败定界耗时、知识检索命中率），并测**基线值** | 度量口径表 |
| 0.4 选种子项目 | Sponsor 牵头，测试/研发经理定 | 标准见 §4.2；务必选"有 pain、有数据、有愿意配合的人"的项目，而不是最大最重要的项目 | 种子项目确认书 |
| 0.5 数据与合规评估 | 安全/IT + AI 负责人 | 盘点代码、文档、工单、日志的密级；确认走本地模型/内网模型网关还是可申请云端 API | 数据分级结论、私有化红线 |
| 0.6 资源与权限清单 | AI 负责人 + 系统 Owner | 一次性提交所有只读账号/token 申请（清单见 §7），借 Sponsor 邮件催办——**这是头号隐形工期** | 权限申请表 |
| 0.7 立项评审 | AI 负责人讲，Sponsor 拍板 | 演示痛点数据、POC 范围（明确不做什么）、4–6 周计划、成功标准 | 立项纪要 |

**阶段准出**：种子项目锁定 + 只读权限到手 + 基线数据测完 + Sponsor 发过一次全员/部门邮件背书。

典型卡点：
- "先做个 demo 看看效果再说"——没有正式立项，后面系统 Owner 不给权限。对策：把 POC 范围压到 4 周、明确准出标准，让立项很轻；
- 种子项目负责人怕"暴露烂数据/烂代码"。对策：由 Sponsor 定调"POC 不考核数据质量、不排名"，且价值主张本身就是"迁就脏乱数据"。

### 阶段 1：POC（4–6 周）

**目标**：在种子项目的真实数据上跑通 1 个场景的端到端闭环，用评测数据证明"有用且可控"。

| 步骤 | 谁做 | 具体动作 | 产出 |
|---|---|---|---|
| 1.1 语料只读接入 | AI 负责人 | 按 §4 的知识库开建流程执行 | 语料清单 + 初版索引 |
| 1.2 黄金集共建 | 测试专家主标，AI 负责人组织 | 30–50 条问答/用例 ground truth（POC 期规模），冻结封存 | golden set v0 |
| 1.3 核心链路开发 | AI 负责人 | RAG/Agent + 适配器（端口层先立住，见 docs/04 §6） | 可运行系统 |
| 1.4 执行器对接（M6 场景） | SDET 深度配合 | 提供测试命令、环境、报告位置；AI 负责人做 TestRun 归一化 | runner adapter |
| 1.5 内部 dogfood | AI 负责人 + 2–3 个志愿者 | 每天真实问题走系统，记 bad case，不许只测准备好的题 | bad case 台账 |
| 1.6 评测出报告 | AI 负责人 | 忠实度/命中率/采纳率/成本，**标注数据版本与模型版本**；所有错误分类 | AI 质量报告 v1 |
| 1.7 专家评审会 | 测试/研发专家 + Sponsor | 现场挑真实问题提问；专家逐条判对错；决定进/退/改 | 评审结论 |

**阶段准出（三条同时满足）**：
1. golden set 达标（如答案引用准确率 ≥ 85%，具体阈值与专家在 1.2 共定）；
2. 专家评审现场不出现编造文件/符号类幻觉，或幻觉有显式"未知"降级；
3. 至少 3 名一线用户在无辅导情况下连续一周真实使用。

注意：**评测题不能由建系统的人单独出**。专家评审会要允许专家当场"出题超纲"，这是取信于团队的唯一方式。

### 阶段 2：试点（6–10 周，一个真实团队日常使用）

**目标**：嵌入真实工作流（MR 评论、用例审批、CI 归因回写），跑出效率对比数据和运营机制。

| 步骤 | 谁做 | 具体动作 |
|---|---|---|
| 2.1 工作流嵌入 | AI 负责人 + SDET/平台 | 接 webhook（MR/CI/工单事件）；**写操作默认只出草稿，人审后回写** |
| 2.2 HITL 机制 | 一线测试/研发担任审批人 | 审用例草稿、归因结论、工单草稿；一键采纳/修改/拒绝；操作即反馈样本 |
| 2.3 权限升级评审 | 安全 + 系统 Owner | 从只读升级到受限写（评论/建工单）；限定项目范围、配审计日志与幂等记录 |
| 2.4 双周演示会 | AI 负责人讲，用户讲 | 让一线用户自己讲"它帮我干了什么/坑了什么"——比建设者自夸可信十倍 |
| 2.5 bad case 周会 | AI 负责人 + 测试专家 | 每周分类 Top 问题（召回/生成/数据过期/权限），定修复优先级 |
| 2.6 效率对比测量 | PMO/AI 负责人 | 试点组 vs 对照组（或前后对比）：用例编写耗时、CI 失败定界耗时、回归选择耗时 |
| 2.7 保鲜机制上线 | AI 负责人 + 各系统 Owner | 事件驱动增量摄入接通；stale/reindex 监控；确认"谁负责修接入"的值班人 |

**阶段准出**：连续 2–4 周核心指标稳定达标 + 试点团队主动愿意继续用（续费意愿是硬指标）+ 有完整安全审计无越权读写。

试点期红线：
- **永远保留人审开关和一键停用开关**，Sponsor 手里要有"明天就能关掉"的按钮；
- 出了错误结论由 AI 负责人在群里**公开认错并归因修复**，不护短——团队对 AI 的信任是按"出错后怎么处理"建立的。

### 阶段 3：推广与运营（持续）

| 步骤 | 谁做 | 做什么 |
|---|---|---|
| 3.1 接入模板化 | AI 负责人 + 平台 | 新项目接入做成 checklist + `.testpilot.yaml` 自描述 + 适配器配置，目标：新项目 1–2 天接入而非 2 周 |
| 3.2 接系统 Owner 共建 | 平台团队 | 知识库/用例/工单平台把 TestPilot 端口当正式集成方；Java 技术栈补 JUnit/Gradle/K8s 适配器（见 docs/04 §5） |
| 3.3 多语言/多项目扩展 | AI 负责人 | 第二个项目优先选 Java 服务，验证端口语言中立性——这也是方案可复制性的关键证据 |
| 3.4 运营岗移交 | AI 负责人 → 培养 1–2 名运营人 | bad case 例会、prompt/检索调优、用户答疑 SOP 文档化，避免"作者一走系统就死" |
| 3.5 季度治理报告 | AI 负责人 + Sponsor | 采纳率、定界耗时、漏放/误报、单请求成本趋势；每个数字带版本标注 |

## 4. 专项：知识库从零开建，团队怎么配合、怎么开始

这是最容易被做成"AI 工程师自己闷头爬文件"的环节，也是失败率最高的环节。正确开法是**业务驱动、只读起步、专家共建**。

### 4.1 开建前提（缺哪条先补哪条）

| 前提 | 谁给 | 没有会怎样 |
|---|---|---|
| Sponsor 明确"先做哪个项目、解决什么问题" | Sponsor | 变成全公司文档大杂烩，检索什么都不精 |
| 语料系统的只读权限 | 各系统 Owner + IT | 只能拿零散导出文件，无法保鲜，演示即巅峰 |
| 2 名以上愿意陪聊的领域专家 | 测试/研发经理指派 | 切块和问答对错没人裁定，质量无法证明 |
| 数据密级结论 | 安全 | 建完才发现代码不能进模型，推倒重来 |
| 一批真实用户问题（≥30 条） | 一线测试/研发提供 | 检索优化没有靶子，只能自我感觉良好 |

### 4.2 第一步：选种子知识域（不是选最多的文档）

由 AI 负责人提候选、测试经理和研发 owner 共同拍板，选择标准：

1. **问答高频且当前痛苦**：新人常问、老人反复答、翻文档平均 >10 分钟；
2. **语料已在线且相对集中**：文档 + 代码 + 历史事故/工单能拿到；
3. **有明确专家能判对错**：存在公认的"活字典"式资深同事，且愿意参与；
4. **业务相对稳定**：避开正在大重构的模块（重构演示可以人为造，别拿真在失控的模块起步）；
5. **敏感等级允许试点**。

AlarmKitSpike 天然满足全部五条，所以它是好种子。真实企业里典型好种子：一个迭代多年的中型业务线的测试域（用例 + 缺陷 + 事故 + 接口文档齐全）。

### 4.3 开建步骤与角色配合

| 步 | 动作 | AI 负责人 | 领域专家 | 一线用户 | 系统 Owner |
|---|---|---|---|---|---|
| K1 | **语料盘点**（不导入，先登记） | 设计盘点表，跑只读清单 | 指出哪些文档权威、哪些已废弃、术语黑话有哪些 | 提供"平时都去哪找答案"清单 | 给目录/空间/项目 key 清单 |
| K2 | **权威性分级** | 按信号给初版分级建议 | **拍板**：规范/事故/个人分享各是什么权威等级；指定每个域的"事实裁定人" | – | – |
| K3 | **真实问题收集** | 发问卷 + 蹲群聊记录，收集 ≥50 条真实提问 | 补 10 条"只有内行才会问"的深问题 | 每人提 5 个真实问题 | – |
| K4 | **只读接入 + 初加工** | 文件/API 适配器接入，跑切块/实体链接，**不写回源系统** | – | – | 确认只读 token 范围 |
| K5 | **30 题冒烟评测** | 用 K3 的题跑检索+生成，录证据 | 逐条判对错，标出"看着对其实错"的危险答案 | – | – |
| K6 | **加工质量评审会**（1 小时） | 展示切块样本、实体关系、引用 | 现场挑错：术语认错、符号认错、文档版本认错 | – | – |
| K7 | **小范围试用 2 周** | 每天看日志、修 bad case | 答疑、裁定争议 | 真实提问、点采纳/踩 | – |
| K8 | **保鲜责任人机制** | 接通事件、上线 stale 监控 | 每域指定一名"知识 owner"（通常资深测试），收到 stale 提醒后处理 | – | webhook 维护人 |
| K9 | **扩域** | 复制 K1–K8 到下一知识域 | 新域专家进场 | – | – |

语料盘点表（K1 产出物）模板：

| 语料 | 位置/系统 | 密级 | 更新频率 | 权威等级 | 事实裁定人 | 能否只读 API | 备注 |
|---|---|---|---|---|---|---|---|
| 接口规范 | Confluence/xxx | 内部 | 双周 | L1 权威 | 张三 | 是 | 有过期页需标 |
| 历史缺陷 | Jira project TEST | 内部 | 持续 | L2 经验 | 李四 | 是（需工单组审批） | 2023 前字段缺失 |
| 事故复盘 | 飞书空间 | 内部 | 月度 | L2 历史证词 | 王五 | 仅导出 | webhook 无，先定时导 |
| 代码 | GitLab/group-x | 机密 | 持续 | L0 实时 | 模块 owner | 是 | 须走内网模型 |

### 4.4 团队最常见的四个顾虑与应对

1. **"我们文档很乱，等整理好了再给你"**
   → 明确告知：系统设计前提就是迁就脏乱数据，机器信号（代码/CI/工单）为主，人写文本降权不删；
   **越等越不会开始，乱数据本身就是加工素材**。只要求专家花 1 小时做权威性分级，不要求改文档。

2. **"AI 学错了/拿旧文档误导人谁负责？"**
   → 每条答案强制带来源引用 + 版本 + 新鲜度标注；历史文档标"验证于版本 X"；
   live-verify 机制兜底；试点期定位是"实习生草稿"，决策权在人。

3. **"这是不是要替代测试/抢饭碗？"**
   → Sponsor 在启动会明确定位：工具承担"找格式、找资料、跑重复执行"，
   人转向"判对错、设计策略"；考核上**不因为效率提升立刻裁员/减编**（需要 Sponsor 当面承诺，否则没人会真实反馈）。

4. **"接入又要我们开发配合，没排期"**
   → 第一阶段全部只读，系统 Owner 只需开 token（半小时工作量）；
   写入类集成放到试点期且由 AI 负责人开发适配器，对方只 review。

## 5. 三个场景的试点协作流程（谁在什么时刻做什么）

### 5.1 场景 A：知识问答上线（最轻，建议第一个做）

```text
测试/研发在 IM/Web 提问
  → AI 负责人：已建好检索 + 引用 + live-verify
  → 领域专家：前 2 周轮值抽查答案（每天 5 条），错的进 bad case 会
  → 一线用户：点采纳/踩；踩的必须能选原因（没召回/引用过期/答非所问/事实错）
  → AI 负责人：每周修 Top 问题，修完 golden set 回归，发周报
  → 系统 Owner：只管 token 不过期
```
人力需求：AI 负责人全职 + 专家 2h/周。准出：抽查引用准确率达标、周活跃用户 ≥ 试点组 60%。

### 5.2 场景 B：测试设计 Agent（需求→测试点→用例）

```text
需求评审前：测试经理选 2–3 个真实需求做试点（不挑简单的，挑有代表性的）
  → AI 负责人：跑"需求→测试点→用例草稿（含 oracle）"
  → 需求 owner（产品/研发）：评审会上把 AI 输出当"另一个参会者的清单"讨论
  → 资深测试：会后裁定：哪些测试点有效、哪些 oracle 挖对了、哪些是幻觉
  → 一线测试：在草稿上改而不是从零写；修改 diff 自动成偏好样本
  → AI 负责人：统计草稿采纳率、被补测试点数量（漏点率）、误导性点数量
```
关键配合：**需求文档必须提前给**（哪怕粗糙）；试点团队要允许"AI 漏点"暴露——漏点统计比采纳率更能说明系统边界。

### 5.3 场景 C：测试执行与失败归因（协作最重，价值也最高）

```text
立项期：SDET + 平台工程师 + AI 负责人三方会，定：
  ① 执行器边界（谁触发、在哪跑、并发/成本谁批）
  ② 环境归属（模拟器/设备/K8s 资源谁分配，签名/测试账号谁管）
  ③ 日志可取范围（日志平台 Owner 确认查询 API 与密级）
POC 期：
  SDET：提供一条可稳定运行的测试命令 + 一份已知失败的报告样本（iOS xcresult / Java Surefire XML）
  AI 负责人：runner 独立 worker 化，TestRun 归一化，归因输出带证据
试点期：
  CI 平台 Owner：配 PipelineFinished webhook（只读起步）
  一线研发：CI 失败时收到 AI 归因评论，按"有用/无用/错误"反馈
  测试专家：标定真实历史：flaky 率、环境失败率、真缺陷率——作为归因准确率的对照基线
  Sponsor：批执行预算（Agent 触发重跑会消耗 CI 资源），先限制每日条数
写回阶段：
  安全 + 工单 Owner：开"建工单/评论"权限，限定项目、必须经 HITL、全审计
```

环境类风险（签名、真机后台行为、多进程）必须由 SDET/测试专家明确告诉 AI 负责人
"哪些结论模拟器环境永远给不出"，归因输出要显式标注"此结论未覆盖真机/生产层"——
这与 CLAUDE.md 的工程纪律一致。

**S4 事件化落地补充（2026-11-11）**：webhook 不需要一步到位——CI 平台先把
PipelineFinished 事件落成 JSON 信封文件（schema 与回放目录一致），Agent 侧
`testpilot-ingest --replay-events` 即可全量消费，后续再替换为消息总线；失败闭环
产出的建工单草稿默认 dry-run（outbox pending，不外部写），走 R3 人审后才派发。
保鲜侧不在进程内装定时器：由运维挂外部 cron 定时跑 `testpilot-ingest --scheduled`
做全量兜底（批次留痕 trigger='scheduled'，与事件触发的 event-reindex 可区分），
并每日跑 `--latency-report` 看摄入 P95（门限 5min，空样本显式不放行而非假绿）。
详细命令与 crontab 示例见 [03 语料工程备忘](03-语料工程与实测环境（AlarmKitSpike）.md) §6。

## 6. 最小人力配置（现实版）

| 配置 | 编制 | 能做到什么 |
|---|---|---|
| **1 人极限 POC** | AI 负责人全职；Sponsor 给授权；2 名专家各 2h/周 | 一个种子项目、一个场景、只读接入、离线演示——**就是当前 Demo 的形态**，文档里如实说明 |
| **3 人试点小队** | AI 负责人 1 + SDET/数据 1 + 兼职领域专家 1（50%）；平台支持计 1–2 人周 | 一个真实团队日常使用、写回 HITL、双周迭代 |
| **5–6 人推广小队** | AI 负责人 1 + AI/数据工程师 2 + SDET 1 + 运营/PM 1 + 各域专家虚拟组 | 3–5 个项目、双技术栈（iOS+Java）、季度治理报告 |

落地叙事：POC 用 1 人力证明技术闭环；方案中给出 3 人/5 人编制和每角色的不可替代性，证明理解落地成本。

## 7. 权限 / 资源申请清单（立项后一次性提，Sponsor 催办）

| 资源 | 用途 | 审批方 | POC 阶段建议范围 |
|---|---|---|---|
| 代码仓只读 token | 代码检索、diff、符号 | 代码平台 Owner + 安全 | 单项目 group，只读 |
| 文档空间只读 | 需求/规范/复盘语料 | 文档空间 Owner | 单空间 |
| 工单系统只读 | 缺陷语料、相似工单 | 工单管理员 | 单 project |
| CI 只读 API + webhook | 流水线状态、失败触发 | DevOps | 单项目，webhook 只发到指定服务 |
| 日志查询 API/token | 失败归因取证 | 日志平台 Owner + 安全 | 限定项目/时间窗，只读 |
| 制品/报告下载 | xcresult/JUnit/截图 | DevOps | 只读、保留期内 |
| 测试环境/设备额度 | 执行器跑用例 | 环境管理员 | 每日限额，先 10–20 次 |
| GPU 机 / K8s namespace | Ollama/vLLM、向量库 | 平台团队 | 单租户 namespace |
| 工单/评论**写入** | 回写归因、建工单 | 安全 + 系统 Owner | **试点期才申请**，限项目 + HITL + 审计 |
| IM Bot 应用 | 触点入口 | IT/协同平台管理员 | 单群试水 |

原则：**只读权限立项即申（不给就是 Sponsor 的事）；写入权限试点再申，且带着审计与幂等方案去申**，
安全团队看到"先存账本再发起、可一键停用"的设计，过审率会高很多。

## 9. 落地风险与对策（按真实出现频率排序）

| 风险 | 表现 | 对策 |
|---|---|---|
| 没有真正的 Sponsor | 权限批不动、试点组不配合 | 立项前先验证 Sponsor 能发出邮件、能催来账号；否则不启动 |
| 评测自说自话 | 系统建的人出题、自己评高分 | golden set 专家主标、评审现场超纲出题、冻结题集防泄漏 |
| 语料无人保鲜 | 上线三个月后答案开始过期 | K8 知识 owner 机制 + stale 自动提醒纳入绩效小事；事故文档不改写只加版本标注 |
| 权限过度收紧 | 每个系统都要单独评审，拖数周 | 只读打包一次申；写操作带审计/HITL/停用开关主动降低安全顾虑 |
| 试点变成"表演赛" | 用户只问准备好的题 | dogfood 期强制真实问题；指标看周活与采纳率，不看演示效果 |
| 错一次信任崩盘 | 一次编造结论被群里截图 | 答案强制引用+降级；出错公开归因修复；试点期定位明示为"草稿" |
| 执行器成本失控 | Agent 疯狂重跑 CI | 每日条数限额、执行预算审批、取消/超时控制、环境复用 |
| 作者依赖 | 人走系统停 | 阶段 3 强制运营移交：SOP、值班表、配置而非脑内知识 |
