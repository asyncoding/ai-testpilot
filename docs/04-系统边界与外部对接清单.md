# 系统边界与外部对接清单（端口/适配器）

| 项      | 内容                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------ |
| 版本     | v0.1（当前）；版本演进见 git 历史                                                                                        |
| 讨论结论   | TestPilot 只做智能编排、领域判断、证据组织与人审；代码、知识、用例、工单、CI、执行器、环境、日志、模型等都视为可替换外部系统                                         |
| 架构模式   | 六边形架构 / Ports & Adapters：核心定义端口，iOS 本地与企业 Java 技术栈分别提供适配器                                                    |
| 当前 POC | iOS 工程 AlarmKitSpike + 本地文件/Git/xcodebuild/JSON fixture/Ollama                                               |
| 目标形态   | GitLab/GitHub、Confluence/飞书、TestRail/禅道、Jira、Jenkins/GitLab CI、JUnit/Gradle/Maven、K8s/设备云、ELK/SLS、内部知识库与模型网关 |

## 1. 一句话结论

**不要把 Agent、知识库、CI、测试执行器、设备环境、工单系统揉成一个进程。**

TestPilot Core 只依赖一组稳定的业务端口，例如 `CodeRepositoryPort`、`KnowledgeSourcePort`、`TestCaseRepositoryPort`、`TicketPort`、`TestRunnerPort`、`LogQueryPort`。当前用本地文件、JSON fixture、xcodebuild 实现这些端口；未来切换到公司内部系统时，新增/替换适配器，不改编排图和归因逻辑。

特别要分清三件事：

1. **CI/CD 系统**：管流水线、阶段、触发、构建历史和凭证；
2. **测试执行器**：真正运行选定用例并返回结构化结果（iOS 是 xcodebuild/XCTest，Java 是 Gradle/Maven/JUnit）；
3. **环境/设备管理系统**：分配和重置模拟器、真机、K8s namespace、测试租户或容器。

Agent 可以调用它们，但不把自己变成它们。

```text
└────────┬────────────────┴────────────────────────┬─────────────────┘
         │                                         │

│ 适配器层（Adapters，按 profile 装配）                                 │
│ ┌─────────────────────────────┐ ┌─────────────────────────────────┐ │
│ │ iOS 本地 POC                 │ │ 企业 Java/内网目标形态            │ │

│ │ xcresult + os_log            │ │ Gradle/Maven/JUnit/Surefire     │ │

└─────────────────────────────────────────────────────────────────────┘
```

关键边界：

- **原始数据的权威来源在外部系统**：需求、代码、用例、工单、CI run、日志、制品不归 TestPilot 所有；
- **TestPilot 持有 AI 派生资产**：测试点草稿、用例草稿、实体关系、置信度、质量分、归因结论、评测集、prompt、反馈与审计记录；
- **本地索引只是派生视图/缓存**：即使当前知识库来自文件系统，文件系统也是 `KnowledgeSourcePort` 的一个适配器，不能让 RAG 流程直接假设“语料一定在本地目录”。

## 3. 核心系统自己保留什么、不做什么

### 3.1 TestPilot Core 必须拥有

| 能力 | 说明 |
|---|---|
| 统一领域模型 | Requirement、TestCase、TestPoint、Commit、ChangeSet、TestRun、Failure、Issue、Evidence、Approval |
| 三条工作流状态机 | 知识问答、需求→测试点→用例、选用例→执行→取证→归因→人审→回写 |
| HITL 与策略 | 哪些动作只读、哪些写外部系统必须审批；审批人、审批版本和 diff 留痕 |
| 证据账本 | 每条结论绑定来源系统、URI、版本/hash、时间、查询条件、抓取人/身份 |
| 权限与降级 | 结合用户身份过滤检索结果；外部系统不可用时显式降级，不编造 |
| 幂等与外部副作用控制 | 写评论、建工单、改工单状态、回写用例前先持久化 outbox/幂等键，再发起调用 |
| AI 质量治理 | golden set、引用校验、live-verify、trace、反馈回流、成本与质量看板 |

### 3.2 TestPilot Core 不直接做

| 不直接做 | 交给谁 |
|---|---|
| 读取磁盘 Markdown 的具体路径格式 | `FileSystemDocumentAdapter` |
| 解析 Jira/GitLab 字段 | 各自 adapter；核心只看 canonical model |
| 执行 `xcodebuild` / `gradle test` | 独立 `TestRunner` worker |
| 启动/重置模拟器、创建 K8s namespace | `EnvironmentManager` |
| 保存 xcresult、截图、录屏、Surefire XML | `ArtifactStore` |
| 直接查 ELK/Splunk/os_log 的查询语法 | `LogQueryPort`，适配层翻译谓词 |
| 决定向量库/企业搜索 API 的具体查询 | `KnowledgeSearchPort` |
| 直接调用某个模型 SDK | `ModelGatewayPort`（Ollama/vLLM/内部网关） |
| 渲染 IM 卡片或 Web 页面 | 通道适配器/前端 |

## 4. 需要对接的系统总清单

### 4.1 研发资产与流程系统

| # | 外部系统 | 核心能力 | 当前 Demo 实现 | 生产/Java 常见替代 | 读写边界与新鲜度 |
|---|---|---|---|---|---|

| 2 | **需求 / 文档系统** | 需求正文、验收标准、版本、评论、附件、权限 | 本地 `docs/**/*.md` 文件适配器 | Confluence、语雀、飞书文档、Notion/SharePoint、内部需求平台 | 以外部文档版本为准；读取实时元数据，加工摘要入派生索引；测试点可作为评论/附件回写 |

| 4 | **用例管理系统** | 用例 CRUD、目录、标签、版本、执行记录、与需求/缺陷关联 | Markdown 测试用例文档解析；AI 草稿先放本地 draft store | TestRail、Xray、Zephyr、TestLink、禅道、自研用例平台 | 生成用例不直接入库；人审后 create/update；保留 external_id、版本和回写 diff |

| 6 | **事故 / 复盘系统** | 事故时间线、根因、修复记录、改进项 | Markdown 事故复盘文档 | PagerDuty/Opslane、内部故障平台、事故文档空间 | 历史事故不改写；只补充 AI 抽取的实体链接和“验证于版本”标注 |

### 4.2 构建、执行与环境系统

|---|---|---|---|---|---|

## 5. iOS POC 到企业 Java 技术栈的映射

| 能力 | iOS 本地 POC | 企业 Java 目标适配 |

| 需求/知识 | Markdown 文件系统 | Confluence/飞书/内部知识库/企业搜索 API |

| 运行环境 | iOS Simulator/真机、`simctl`/`devicectl` | K8s Job/Pod、Docker Compose、测试租户、共享测试环境 |

| 模型/向量 | Ollama + Chroma/BM25/SQLite | 内网模型网关 + 托管向量/检索服务，或联邦企业搜索 |

### Java 适配器的最小结果归一化

无论 XCTest 还是 JUnit，执行器都向核心返回统一结构：

```text
TestRun
├── run_id / idempotency_key
├── project_ref
├── commit_sha / build_id
├── status: queued | running | passed | failed | error | canceled | timeout
├── environment: { provider, env_id, capabilities, version }
├── started_at / finished_at / duration_ms
├── case_results[]
│   ├── external_case_id / node_id
│   ├── status: passed | failed | skipped | error
│   ├── duration_ms
│   ├── failure_type / message / stacktop
│   └── evidence_refs[]
├── artifacts[]: { type, uri, content_hash, retention }
└── raw_report_ref / runner_capability_version
```

核心不允许出现“只有 iOS 才懂”的字段作为主流程判断；iOS 的 `scheme/udid/destination`
和 Java 的 `module/tags/profile` 都是各 runner adapter 的配置。

## 6. 建议的端口与统一模型

### 6.1 关键端口（示例）

```python
class CodeRepositoryPort:
    async def get_change_set(self, repo_ref: RepoRef, base: str, head: str) -> ChangeSet: ...
    async def get_symbol_at_commit(self, repo_ref: RepoRef, symbol: SymbolRef, commit: str) -> SymbolSnapshot: ...
    async def list_commit_events(self, checkpoint: EventCheckpoint) -> list[RepoEvent]: ...

class KnowledgeSourcePort:
    async def fetch(self, source_ref: SourceRef, version: str | None) -> KnowledgeDocument: ...
    async def list_changes(self, checkpoint: EventCheckpoint) -> list[DocumentChanged]: ...

class KnowledgeSearchPort:
    async def search(self, query: Query, scope: AccessScope) -> list[KnowledgeHit]: ...
    async def live_verify(self, evidence: EvidenceRef, version: str) -> VerifyResult: ...

class TestCaseRepositoryPort:
    async def list_cases(self, selector: CaseSelector) -> list[TestCase]: ...
    async def create_case_draft(self, draft: TestCaseDraft) -> DraftRef: ...
    async def write_approved_case(self, approval: ApprovedChange) -> ExternalRef: ...

class TicketPort:
    async def search(self, query: TicketQuery) -> list[Issue]: ...
    async def create(self, draft: IssueDraft, idempotency_key: str) -> ExternalRef: ...
    async def add_comment(self, issue_ref: ExternalRef, comment: CommentDraft, idempotency_key: str) -> ExternalRef: ...
    async def transition(self, issue_ref: ExternalRef, transition: str, idempotency_key: str) -> None: ...

class TestRunnerPort:
    async def submit(self, request: TestExecutionRequest) -> RunHandle: ...
    async def cancel(self, run_id: str) -> None: ...
    async def get_run(self, run_id: str) -> TestRun: ...

class EnvironmentPort:
    async def acquire(self, requirements: EnvironmentRequirements) -> EnvironmentLease: ...
    async def health_check(self, env_id: str) -> EnvironmentHealth: ...
    async def reset(self, env_id: str) -> None: ...
    async def release(self, lease_id: str) -> None: ...

class ArtifactStorePort:
    async def put(self, local_path: str, metadata: ArtifactMetadata) -> ArtifactRef: ...
    async def get_presigned_uri(self, ref: ArtifactRef) -> str: ...

class LogQueryPort:
    async def query(self, filter: LogFilter, scope: AccessScope) -> LogBundle: ...
```

### 6.2 统一模型的最低要求

| 模型 | 必带字段 |
|---|---|
| `Requirement` | external_id、source_system、version/etag、标题、验收标准、owner、URI、权限范围 |
| `TestCase` | external_id、版本、前置条件、步骤、oracle、标签、关联需求、来源系统 |
| `ChangeSet` | repo、base/head commit、变更文件、变更符号、diff URI、merge request |
| `CodeSymbol` | 稳定 symbol id、语言、文件/行范围（版本化）、签名、调用/被调用关系 |
| `Issue` | external_id、状态、现象、复现步骤、严重级别、关联用例/commit/run、URI |
| `Evidence` | source_system、URI、查询条件、版本/hash、抓取时间、访问身份、可信度 |
| `Approval` | 审批人、审批前/后 diff、基于的输入版本、审批结论、时间、幂等键 |

外部系统 ID 不直接当作核心主键，建议使用：

```text
urn:testpilot:<source_system>:<resource_type>:<external_id>@<version>
```

例如：


## 7. 数据新鲜度、读写与外部副作用规则

### 7.1 哪些实时查，哪些加工后入库

| 类型 | 处理方式 | 原因 |
|---|---|---|
| 当前 HEAD 代码、符号是否存在、MR/CI 状态、工单当前状态、环境是否空闲 | **L0 实时联邦查询，不长期缓存结论** | 变化最快，缓存容易误导执行和归因 |
| 需求文档、项目文档、历史用例、事故复盘、代码符号摘要 | 事件驱动 ETL，入 L1/L2，带版本和 TTL | 适合语义检索，但必须可追溯版本 |
| 实体关系、confidence、质量分、AI 摘要、oracle 草稿 | TestPilot 派生资产入库 | 这是核心增量价值，不是外部原始数据 |
| 日志流、Trace、指标、xcresult/视频等大文件 | 按需查询 + artifact URI，不整量入向量库 | 体量大、噪声高，归因时围绕 runId/time window 取证据 |
| 历史事故/日志原文 | 保留原值，不改写；只增加版本注记和关系链接 | 历史证词必须保真 |

### 7.2 外部动作分级

| 级别 | 动作 | 策略 |
|---|---|---|
| R0 | 查代码、查文档、查用例、查工单、查日志、提交一次测试执行 | 可按工作流自动执行，但需要权限、预算和审计 |
| R1 | 创建 AI 草稿、内部审批评论、给用户生成建议 | 自动执行，仅写 TestPilot 内部 draft/audit |
| R2 | MR 评论、外部评论附件、回写用例 | 默认人审；可按白名单/低风险模板自动 |
| R3 | 创建工单、工单状态流转、取消流水线/执行、发布/部署动作 | 必须人审，幂等键、回滚/撤销路径和审计齐全 |
| R4 | 删除数据、改权限、操作生产环境、直写业务数据库 | POC 禁止；生产也不交给 Agent 直接做 |

执行任何 R2/R3 前遵守：

1. 先持久化 `Approval`、外部请求体、`idempotency_key`、目标系统和回滚策略；
2. 再调用外部系统；
3. 调用成功后回写 external_ref；
4. 调用失败进入可重试/人工接管状态，不能重复建工单/重复评论；
5. 定时对账“幻影记录”：本地显示已发起但外部无记录的请求补建或标记失败。

## 8. 标准化事件清单

Demo 即便用 JSON 文件，也要按真实 webhook/event 的方式设计 schema，便于未来替换 Kafka：

| 事件 | 触发源 | 消费动作 |
|---|---|---|
| `CommitPushed` | Git 平台/本地 Git | 增量解析 diff、AST 变更符号、stale 检测 |
| `MergeRequestOpened/Updated` | MR 系统 | 生成 MR 摘要、影响面、推荐用例 |
| `MergeRequestMerged` | MR 系统 | 知识条目转正、blue-green 索引切换 |
| `PipelineFinished` | CI | 拉取结果/制品；失败时触发归因 |
| `TestCaseCreated/Updated` | 用例平台 | 重新切块、链接需求/代码符号 |
| `RequirementPublished` | 需求/文档系统 | 生成测试点草稿、标注验收标准缺口 |
| `TicketCreated/Closed` | 工单系统 | 建立缺陷-用例-commit-符号关系 |
| `IncidentClosed` | 事故平台 | 抽取时间线/根因/改进项，事故作为历史证词入库 |
| `DeploymentFinished` | 发布系统 | 记录服务版本、环境和 feature flag |
| `TestRunFinished` | Runner | 保存结构化结果，触发失败归因/通知 |
| `ModelFeedbackSubmitted` | Web/IM | 采纳/修改/拒绝样本进入评测与 prompt 回归 |

事件信封至少包含：`event_id`、`event_type`、`source_system`、`occurred_at`、`project_ref`、
`subject_ref`、`version`、`actor`、`payload_uri`、`idempotency_key`。

## 9. 失败归因闭环中的系统协作（示例）

```text
CI/PipelineFinished
  └─ TestPilot 拉取 CI run 元数据（只读）
      └─ 判断是否需要选择重跑/补跑
          └─ EnvironmentPort.acquire(capabilities=[ios.simulator/ios.device/java.container])
              └─ TestRunnerPort.submit(TestExecutionRequest)
                  └─ Runner 在独立 worker 中执行 xcodebuild / gradle test
                      └─ ArtifactStorePort 保存 xcresult/JUnit XML/截图/录屏/log
                          └─ LogQueryPort 按 runId/时间窗查询应用与系统日志
                              └─ CodeRepositoryPort/KnowledgeSearchPort 实时校验代码与历史经验
                                  └─ Agent 产出带证据的归因：真缺陷 / 用例过期 / 环境失败 / flaky
                                      └─ HITL 审批
                                          ├─ TicketPort.create / add_comment / transition
                                          ├─ MergeRequestPort.comment
                                          └─ TestCaseRepositoryPort.write_approved_case
```

这个流程里：

- Runner 只负责“执行与采集”，不负责下最终归因结论；
- CI 可以是触发器，但不是唯一执行入口；
- 环境不满足能力要求时直接报 `unsupported_capability`，例如模拟器不能声称完成真机后台/签名验证；
- 归因结论必须同时有结构化失败、日志/制品证据和当前代码版本。

## 10. 建议的工程拆分

当前不必一次做成微服务，但从第一版代码就按边界分包，避免后期拆不出来。

```text
    └── notify-web/
```

### 装配 profile

```text
subsystems/config/profiles/      # 实际落地四个 profile（选择方法见 docs/13 §3）
├── offline-demo.yaml            # 无外部依赖演示：全 fixture/录制件，仍走真实 adapter 接口
├── ios-local-poc.yaml           # 本地 iOS：Git + Markdown + JSON + 真 Ollama + 模拟器录制链
├── ios-local-poc-xcode.yaml     # Xcode 真机链：真 xcodebuild/simctl/xcresulttool，单设备 udid 租约
```

JSON 工单不是“在 Agent 里 return 假对象”，而是实现一个 `JsonTicketAdapter`：

- 从 `fixtures/tickets/*.json` 读取；
- 创建/评论经过同一端口、同一权限检查、同一幂等键；
- 写操作落到 `store/<profile>/ticket-store/`（即 `data_dir/ticket-store`，生成物，不入库）；
- 未来替换为 Jira adapter 时，工作流层不改代码，只改 profile 与凭证。

## 11. POC 落地顺序（已执行）

初期七步顺序建议（canonical model/端口先行 → 只读 adapter → runner 独立 worker →
outbox+HITL → offline-demo → JUnit 归一化验证 → 企业系统原型）已按垂直切片方式执行：
S0–S4 切片全部完成；JUnit adapter 验证与企业系统原型属 S5/P2，未开始。七步原文与
S0–S4 落地台账见 [ADR-20261111-01](archive/03-方案演进与废弃决策.md#adr-20261111-01)。

### 设计验收标准

- Core 包中 grep 不到 `xcodebuild`、`simctl`、`gradle`、Jira SDK、GitLab SDK、具体 fixture 路径；
- LangGraph 节点只依赖端口接口和统一模型，不知道当前是 iOS 还是 Java；
- 从 `tickets-json` 换成内存/Jira adapter，不需要改归因节点；
- 从 `runner-xcode` 换成录制结果 runner/JUnit runner，只改配置；
- 每个外部写操作都能找到审批记录、请求体、幂等键、外部返回 ID 和失败重试状态；
- 每条结论都能点开来源证据，且证据标明系统、版本、时间、查询条件和数据权限。
