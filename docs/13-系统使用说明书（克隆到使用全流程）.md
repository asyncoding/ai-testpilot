## 0. 这套系统是什么、两个场景

TestPilot 是智能研发测试助手，本说明书聚焦 2026-11 定案的 Xcode 执行闭环：

- **场景 A（需求 → 全量用例 → 真实 Xcode 执行）**：系统把需求加工成测试点/用例/oracle
  规格，导出结构化 JSON 用例集；**人工**把 JSON 携出系统边界，交给 Claude 等外部 Agent
  在被测仓的长期演示分支上生成 Xcode 测试代码（人审 + 编译门禁）；回流后系统扫描建立
  「用例 ↔ Xcode 测试方法」映射，并真实驱动 `xcodebuild` 执行、回收 xcresult。
- **场景 B（commit diff → 影响面 → 存量用例选择重跑）**：被测仓有新 commit 后，系统做
  符号级 diff 与影响面三分类（可自动跑/无自动化/冲突待人工），经映射翻译成
  `-only-testing` 选择集，只跑受影响的存量用例；空选择硬失败，**绝不静默退化为全量**。

**系统边界**：系统内不生成 Swift 代码、不直接写被测仓；测试代码生成、
演示分支创建与合入都是人工步骤（§5、§6 给出可照跑的 runbook）。模拟器覆盖不到的三层
（后台音频/签名/真机）永远如实标注为未覆盖层，不夸大为真机验证。

### 验证层级声明（先建立预期）

| 层级 | 跑什么 | 何时跑 |
|---|---|---|
| L1 hermetic 自动化 | `pytest` 全量（当前基线 1704 passed / 3 skipped，随版本增长）、`verify_s0.sh` 24 门禁、import-lint；不起模拟器/端口/外部服务 | 每次改动后，全本地可复现 |
| L2 模拟器真机链 | xcode profile 下真实 `xcodebuild` + simctl + xcresulttool（本说明书 §7/§8） | 演示前手动跑，依赖 macOS + Xcode |
| L3 仅生产/真机可验 | 后台音频、代码签名、真机进程生命周期 | 本地**永不**声称已验，见 docs/03 §3.6 手动 runbook |

## 1. 仓库布局与角色

需要两个仓库（系统不拷贝被测代码，只通过文件系统/git 只读对接）：

```
~/Documents/Code/
├── ai-testpilot/              # 本仓（智能体系统）
```

### 2.2 安装 Python 依赖

```bash
cd ai-testpilot/subsystems
uv sync            # 创建 .venv，editable 安装四个包
```

- 默认 PyPI TLS 失败时（受限网络 fallback）：
  `UV_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple uv sync`（只作临时环境变量，不写进仓库）。
- 若曾在包目录未建全时 sync 过，import 报 ModuleNotFoundError 空壳：
  `uv sync --reinstall-package testpilot-core --reinstall-package testpilot-adapters \
    --reinstall-package testpilot-orchestrator --reinstall-package testpilot-workers`
- **tree-sitter 可选 extra（verify_s0 A2 必装，每次 `uv sync` 后都要重装）**：
  tree-sitter 是 adapters 包的 optional dependency group，**不在默认依赖里，`uv sync`
  不会装、而且每次重跑 `uv sync` 都会把它从 .venv 移除**（环境被对齐回 lockfile）。
  缺它时 A2 恰好 8 个 `tests/test_tree_sitter_chunker.py` 用例报
  `AdapterUnavailableError: tree-sitter/tree-sitter-swift 未安装`。安装命令（README E6 同源）：

  ```bash
  VIRTUAL_ENV=$PWD/.venv uv pip install -e 'packages/adapters[tree-sitter]'
  # 验证：uv run python -c "from testpilot_adapters.tree_sitter_chunker import tree_sitter_available; print(tree_sitter_available())"
  # 应输出 True
  ```

  注意上面的 `--reinstall-package` 命令**不会**装回 optional extra，两件事不要混为一谈；
  日常顺序固定为「先 `uv sync`，再装 tree-sitter extra」。

## 3. 四个 profile 怎么选

所有 worker 都用环境变量 `TESTPILOT_PROFILE` 选 profile，**值必须是 yaml 的完整路径**
（传 profile 名字会报「profile 配置不存在」）：

| profile | 用途 | runner / environment / logs | 数据目录 | 外部依赖 |
|---|---|---|---|---|
| `offline-demo`（默认） | 纯离线 hermetic 演示、CI | recorded / stub / stub | `store/offline-demo` | 无 |
| `ios-local-poc` | 真实语料库的录制型离线链路（不跑 xcodebuild） | recorded / stub / stub | `store/ios-local-poc` | ollama + chroma |
| `ios-local-poc-xcode` | **L2 真机链：真实 xcodebuild 执行（模拟器目的地）** | xcode / ios-simulator / os-log | `store/ios-local-poc-xcode` | ollama + chroma + Xcode + 模拟器 |
| `ios-local-poc-device` | **物理真机链（切片一）：xcodebuild 真机目的地 + devicectl 盘点 + 两步法设备日志** | xcode(target=device) / ios-device / os-log-device | `store/ios-local-poc-device` | ollama + chroma + Xcode + 已配对真机 |

便捷写法（后续命令统一用这个变量）：

```bash
export XCODE_PROFILE=$PWD/config/profiles/ios-local-poc-xcode.yaml
export DEVICE_PROFILE=$PWD/config/profiles/ios-local-poc-device.yaml
export IOS_PROFILE=$PWD/config/profiles/ios-local-poc.yaml
```

xcode profile 关键装配（改机型时编辑 yaml，不要把个人 UDID 写进文档/命令）：

- `runner.settings`：workspace=`AlarmKitSpike/AlarmKitSpike.xcworkspace`、scheme=`AlarmKitSpike`、
  xcresult 工作目录与产物根都在 gitignored 的 `store/ios-local-poc-xcode/` 下；
- `environment.settings.devices`：模拟器清单，**空清单在容器构造期就报错**（fail-closed）；
- `logs.settings.udid` 必须与设备清单 udid 显式一致，拒绝 booted 隐式目标。
- 查自己机器上的模拟器 UDID：`xcrun simctl list devices available | grep iPhone`，
  替换 yaml 中两处 udid（devices 与 logs）。
- **换工程只改这一组键（`project.ios`，2026-11-22 起通用化）**：`engineering_root`
  （workspace 工程根目录段，扫描 containment 用）、`unit_test_target`、`ui_test_target`
  （自动化映射 OID 与导出约定里的两个 target 名）。scan-automation / export-cases
  读取本组键；**解析优先级统一为 CLI 显式参数 > profile 本键 > 内置 legacy 常量**，
  不配置则回退常量（演示工程值即 `AlarmKitSpike` / `AlarmKitSpikeTests` /
  `AlarmKitSpikeUITests`），老 profile 零改动。

device profile 真机专用约定（详见 docs/03 §3.7；刺激动作方案对比与真机实测见 [CAL-20261113-02](archive/02-探针校准与环境实测.md#cal-20261113-02) 与 [EVD-20261113-02](archive/04-真机验收台账.md#evd-20261113-02)）：

- UDID 必须是**硬件 UDID**（`devicectl list devices --json-output -` 的
  `properties.hardware.udid`），不是顶层 CoreDevice UUID；真机清单空/未连接时
  health_check 回 False、reset 永远被策略拒绝（平台不自动化任何抹机）；
- 日志默认 `collect_mode: manual`：worker 无 TTY 不代跑提权 collect。查询时若归档
  缺失，平台报错里携带可照跑的 `/usr/bin/log collect --device-udid …` 命令，人工
  采集到指定 `.logarchive` 后重跑即可（需要提权时人工自行加 sudo）；确认本机免提权
  才可改 `auto`（`use_sudo: true` 走 `sudo -n`，凭据未缓存立即失败不挂密码提示）；
- 上线前先跑手动探针（**不是自动门禁**）：
  `.venv/bin/python scripts/device_chain_probe.py`——首跑 exit 2 打印人工采集命令
  属设计内待办，同 `--run-id` 重跑接上 `log show`，报告在 `out/eval/device-chain-probe.*`。

#### 3.5.2 人工闸门（/gates，设计全文见 [01 总体设计](01-总体设计.md) §10.6）

混合执行中凡是需要人工动作/感官判定的检查点都建模为 gate，与审批流同纪律：
裁决必填评审人与理由，全程留痕。

- 生命周期：`PENDING` → 裁决后 `RESPONDED`；超时转 `EXPIRED`（可 `renew` 续期复活）；
  `abandon` 显式废弃。已 RESPONDED 的 gate 拒绝二次裁决。
- API（6 个，前缀 `/api/gates`）：`POST ""` 开闸、`GET ""` 列表、`GET /{id}` 详情、
  `POST /{id}/respond` 裁决、`POST /{id}/renew` 续期、`POST /{id}/abandon` 废弃。
- Web 入口：http://127.0.0.1:8765/gates 。混合会话进入 `AWAITING_HUMAN` 后在该页
  挂起可见，裁决后用 `testpilot-hybrid resume` 续跑。

#### 3.5.3 混合执行 testpilot-hybrid（hybrid-plan-v1，设计见 [01 总体设计](01-总体设计.md) §10）

把一个用例拆成**有序步骤列表**，每步声明执行方与结构化前置条件；五个执行方：

| actor | 允许动作（摘要） |
|---|---|
| `AUTO_XCODEBUILD` | `run_selector`（跑 -only-testing 选择集） |
| `AUTO_DH_AX` | DeviceHub 辅助功能：`home` / `rotate_left` / `readiness` / `state` |
| `AUTO_DEVICECTL` | devicectl 设备盘点与生命周期操作 |
| `HUMAN_ACTION` | 人工真机动作：`lock_screen` / `press_side_button` / `other` |
| `HUMAN_VERDICT` | 人工感官判定：`sensory_check` / `other` |

会话开跑前先执行**六个前置探针**（全过才放行，fail-closed）：设备已解锁、窗口已具象、
竖屏方向、App 未在运行、无活跃闹钟、通知权限就位。

六个子命令：

| 子命令 | 用途 |
|---|---|
| `start` | 从计划 JSON 建/重建混合会话 |
| `drive` | 推进自动步，到下一个等待点或终态停 |
| `resume` | 人工闸门裁决后续跑 |
| `unblock` | 环境阻塞解除后续跑 |
| `get` | 只读打印会话快照 |
| `ws-run` | USB 反向监听单用例会话（driver-first 全链路） |

`ws-run` 拓扑（定案见 [ADR-20261118-01](archive/03-方案演进与废弃决策.md#adr-20261118-01)，
P0 五跑与 T1–T7 三跑证据见 [EVD-20261118-01](archive/04-真机验收台账.md#evd-20261118-01)/[EVD-20261118-02](archive/04-真机验收台账.md#evd-20261118-02)）：
Runner 设备本机 loopback 起 WebSocket 服务，主机经 `iproxy` 反向转发接入；
`TESTPILOT_RELAY_TOKEN` 做鉴权，driver 端重连/重试有界（`--retry-seconds` 默认 300），
全过程 transcript 落 `--evidence-dir`（默认 `./ws-gate-evidence`）。配套独立入口
`testpilot-ws-gate-driver`（参数：`--url` 默认 `ws://127.0.0.1:9876/ws/hybrid/hsess-p0`、

`--transcript-out`）。**H4 边界**：锁屏/侧边键等人工真机刺激不做平台自动化，
由 HUMAN_ACTION 步骤承载（真机刺激动作方案对比与实测见 [CAL-20261113-02](archive/02-探针校准与环境实测.md#cal-20261113-02) 与 [EVD-20261113-02](archive/04-真机验收台账.md#evd-20261113-02)）。

#### 3.5.4 生成 Swift 静态红线（testpilot-scan-generated-swift）

外部 Agent 生成的测试代码合入前必须过这三条红线（实现于
`testpilot_core.generated_swift_lint`，规则全文与外部 Agent prompt 见[附录 A](#appendix-a)）：

| 规则 | 禁止内容 | 理由 |
|---|---|---|
| GS-001 | `sleep(` / `usleep(` 等固定死等 | UI 自动化必须轮询条件，不能赌时间 |
| GS-002 | 同一测试方法 `app.activate()` 与 `app.launch()` 并存 | 接力类用例附着既有进程，冷启动毁现场 |
| GS-003 | 同一测试方法出现两次以上 `.launch(` | 同上，重复冷启动毁现场 |

扫描为纯静态、不构建工程；发现违规则 exit 2 并逐条给文件与行号。

#### 3.5.5 用例文档 lint（testpilot-lint-cases）

对用例 Markdown 做静态体检（实现于 `testpilot_core.case_lint`），**report-only：
只产 finding 不改正文库**。规则集：

- error 级（阻断）：LINT-C-001 标记缺冒号、LINT-C-002 有步骤却零断言（真缺预期的
  最终信号）、LINT-C-003 步骤编号断裂/解析死信；
- warning 级：LINT-C-004 背景材料混进预期段、005/006 原文子弹格式问题、
  007 表格体迁移进度指标、008 叙事体活跃用例缺前置段；
- info 级：LINT-C-009 锚点覆盖提示、LINT-C-010 规范化提示。
  （LINT-C-011 需求侧 EARS 句式属二期，未实现。）

退出码：**0 无 finding；1 有 finding（本入口专属退出码）；2 硬失败**（文件读不动等）。

```bash
#   classification_counts：runnable / no_automation / conflict_update 三分类计数
#   selection.only_testing_ids：翻译成 -only-testing 的 OID（已过形态校验、去重）
#   selection.unmapped_runnable_case_ids：可自动化但没映射的用例（响亮上报，不静默丢）
#   selection.idempotency_key：impact:<head短sha12>:<选择集sha256前16>
#   submission: null（dry-run 零写入）
# 输出中的 base_commit/head_commit 恒为归一后的 40 位全 sha；短 sha、分支名、
# HEAD 混写不产生第二套结果，幂等键也只认归一后的全 sha（身份稳定）。
```

### 6.4 正式提交（幂等 + 按 head 分桶的重跑配额）

```bash
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-impact-rerun \
  --base "$BASE_SHA" --head "$HEAD_SHA"
# 预期：submission.run_id=run-xxxxxxxx，replayed=false，status=queued

# 同参数再跑一次：返回同一 run_id 且 replayed=true，jobs 零增生、配额不双扣
# （第二次把短 sha 换成等价全 sha 也同样命中幂等——归一后身份一致）
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-impact-rerun \
  --base "$BASE_SHA" --head "$HEAD_SHA"
```

配额：每次真实提交占 `rerun_budget` 一行，桶键 `impact:<head短sha>`（默认每日 20，
profile `limits.daily_rerun_quota` 可调）；重放命中幂等账本不扣配额。

### 6.5 执行与查看（同场景 A 的 runner）

```bash
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-runner run-once
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-runner list
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-runner show --run-id run-xxxxxxxx
```

### 6.6 三分类怎么解读

| 分类 | 含义 | 系统动作 |
|---|---|---|
| runnable | 影响到的用例在 map 中有有效绑定 | 翻译成 OID 进选择集，可自动执行 |
| no_automation | 探索性用例等无自动化形态 | 只上报 ID，不进选择集 |
| conflict_update | 符号 removed/签名变化等冲突 | 只上报，等人审更新用例/映射 |
| runnable 但未映射 | 该有自动化却缺绑定 | `unmapped_runnable_case_ids` 显式列出并给补映射提示 |

### 6.7 守卫行为（全部实测，exit 2，零入队）

| 触发方式 | 预期报错要点 |
|---|---|
| map 停在旧 head（`--head` 传父提交） | 「automation-map 已过期…禁止拿旧映射跑新代码」 |
| map 文件缺失（或 `--map` 指错路径） | 「automation-map 不存在…请先运行 testpilot-scan-automation」 |
| 影响集为空/全部未映射 | 「选择集为空…禁止静默退化为全量执行」，附未映射 TC 清单 |
| base/head 不可达（bad object） | git diff 失败收口 exit 2（不出 traceback） |
| map schema 版本不符/JSON 损坏 | 版本或损坏提示，拒绝使用 |

> rev 归一化（2026-11-22 修复）：短 sha/分支名/HEAD 在守卫之前先归一成 40 位全 sha，
> 因此「短 sha 输入」本身不再触发任何守卫；只有引用确实无法解析时才走 bad object 行。

2. 分流规则（依据 JSON 既有字段，不要自造标记）：
   - 任一 oracles[].type == "ui_assertion" → UI 分支（AlarmKitSpikeUITests）；
   - 其余 → 单元分支（AlarmKitSpikeTests）；
   - 人工交付指令显式指定分流时以指令为准，但必须在 generation-report.md 标注覆盖原因；
3. V1 测试用例文档标 📱 的用例（硬件键/全屏闹钟画面/音频/震动/锁屏视觉）模拟器
   不可验，一律不生成 UI 测试，进 skipped 注明「仅真机可验」。

【通用代码规则】（两个分支都适用）
1. 每个测试方法上方独占一行写标记：// testpilot-case: <TC-ID>
   一个方法覆盖多个 TC 时，连续写多行标记，每行一个 TC-ID；
2. 方法命名：func test_<TC-ID 去横线转驼峰>_<英文蛇形短描述>()，
   例 TC-C1 → func test_TCC1_countdownSnapshots()；转换规则与 TestPilot
   tc_id_to_swift_token 同源（去 "-"，各段首字母大写）；
3. 断言必须能回溯到该 TC 的 oracles[].expectation；mined_oracle_suggestions 中
   status=approved 的条目可作为补充断言来源，pending/rejected 不得作为断言依据，
   每条断言在方法内注释标注来源（oracle 序号或 suggestion）；
4. 前置条件（preconditions）用私有 helper 或 setUp 表达；步骤（steps）翻译成
   方法内分段注释 // Step 1 ...，保持与 JSON 文本可对照；
5. 禁止事项：不改 Sources/ 下任何生产代码；不修改/删除 Tests 与 UITests 下存量
   测试；不引入第三方依赖与新 Pod；新类不得与存量类重名。

【单元分支规则】
1. 落点：AlarmKitSpike/Tests/AgentGenerated/（新文件，按模块命名，
   如 RoutineAlarmAgentTests.swift），类名 Agent<Module>Tests；
2. hostless 风格：只构造纯 Foundation 输入调被测类型，不做网络/UI 跳转，
   参考存量 RoutineAlarmTests（Calendar.shanghai、直接 init 领域模型）。

【UI 分支规则】
1. 落点：AlarmKitSpike/UITests/AgentGenerated/（新文件，按模块命名，
   如 QuickAlarmAgentUITests.swift），类名 Agent<Module>UITests，XCUITest 形态；
2. 照抄 ProductFlowUITests 的基建：XCUIApplication 驱动真实 UI，不直接 init
   领域模型；setUpWithError 中 continueAfterFailure = false；启动参数固定
   app.launchArguments = ["--ak-clear-all", "--ak-purge-dates", "--ak-accept-privacy"]
   （隐私门专项改用 --ak-reset-privacy；参数语义见 CLAUDE.md 避坑指南），每用例冷启零累积；
3. 等待一律 waitForExistence(timeout:) 轮询，**禁止 `sleep(`/`usleep(`/`Thread.sleep`
   死等**——静态红线 GS-001 会直接扫红（门禁命令见下方【静态红线门禁】），注释与字符串
   遮罩后判定，写在注释里的说明文字不误伤；断言「旧页面消失」而不仅是「新标题存在」，
   防同名节点假绿；关键步骤截图存为 xcresult attachment；
4. 系统级授权弹窗由测试自己点掉（UI 测试是模拟器上唯一可靠的点屏通道），
   不假设 simctl 能 tap；
5. **接力（relay）段附着规则（红线 GS-002/GS-003）**：混合执行中段 B 用例
   附着的是系统接力场景里**已存活的进程**，只能 `app.activate()` 附着，禁止
   `app.launch()` 冷启动——冷启动销毁系统接力场景且让状态跨用例累积。同一 test 方法内
   activate 与 launch 并存即 GS-002 红；一个 test 方法出现两次以上 `.launch(` 即 GS-003 红。
   每个用例至多一次冷启动，且只允许出现在 setUp/首段；
6. **六类前置条件的承接模板（与 hybrid-plan-v1 前置 kind 一一对应，生成代码不得越界
   自行实现）**：

   | 前置 kind | 生成代码/运行期承接方式 |
   |---|---|
   | `device_unlocked` | 无代码承接：锁屏/侧键永久是 human:action 闸门（无密码测试机策略不立），生成代码不得尝试解锁 |
   | `session_window_materialized` | 无代码承接：DH-AX 运行期探针负责，不满足走 repair/人工闸门 |
   | `portrait_orientation` | 无代码承接：runner 侧 rotate repair（截一张判一张，像素判方向），生成代码禁止自行旋转设备 |
   | `app_not_running` | devicectl 无进程列表动词、恒 unknown：需要干净态时走 `--terminate-existing` 冷启动 + 启动参数钩子，不假设进程死活 |
   | `no_active_alarms` | 固定 launchArguments 带 `--ak-purge-dates`（清活钟），由 xcodebuild 段兜底；生成代码不自行删库 |
   | `notification_permission` | 恒 unknown、只能人工闸门确认；隐私门专项用 `--ak-reset-privacy`，授权弹窗由 UI 测试自己点（见规则 4） |

## 附录 C：外部生成偏差回流与用例变更流程（AR 流程）

<a id="appendix-c"></a>

> 来源：2026-11-17 TC-A1 首批外部生成（`generation-report.md` DEVICE-VERIFY 章）登记
> 三条实测偏差，本附录把「偏差如何收口、什么情况下才允许改用例」固化为当前操作规范。
> 首批 AR-001..004 实例与模板演进留档见 [ADR-20261117-01](archive/03-方案演进与废弃决策.md#adr-20261117-01)
> 起四条；工作态模板在 `subsystems/out/external-generation/tca1/` 下
> `04-corpus-hook-proposal/`（语料仓产品侧补丁提案）与 `05-amendments/`（AR 文件，gitignored）。

### C.1 总原则（不可绕过）

1. **用例评审库是唯一事实源，Swift 测试是下游生成物。** 收口方向只能是「偏差 → 用例库
   变更 → 重新导出 → 重新生成」，禁止只改 Swift 断言而库内规格不动（否则 automation-map
   锚定的规格与分支上的实际断言漂移，整条导出闭环失去可信度）。
2. **外部 Agent 只有登记权，没有规格修改权。** 实测与锁定规格不符时，逐字保持规格、
   在 `generation-report.md` 登记证据并提请人工确认（与[附录 A](#appendix-a) 任务书 §6.2 同口径）；
   修订必须等 AR 裁决后由新一轮生成承接。
3. **语料仓只读纪律不变。** TestPilot Agent 不向语料仓写任何文件；跨边界产物（语料仓
   补丁草稿、用例文档修订块、新版 prompt）一律落本仓 gitignored 目录，由**人工携入**。
4. **无证据不受理。** 每条 AR 必须附实测证据（xcresult/截图附件/os_log 摘录/源码行号
   至少一项），推测性偏差退回补充取证。

### C.2 偏差三分类（先分类，再定路径）

| 分类 | 判定标准 | 改用例吗 | 审批权重 | 典型收口 |
| --- | --- | --- | --- | --- |
| **product_defect（产品缺陷）** | 规格成立、产品实现与规格不符，且产品侧已有/应有修复 | **不改**，规格一字不动 | 低：确认修复合入即可 | 语料仓合入修复 commit，重跑同一规格验证转绿 |
| **fixture_change（夹具/刺激方式变更）** | 断言成立，但既有测试钩子/夹具驱动不出规格要求的状态（能力缺口） | 只改 **steps 的刺激方式**，oracle 不动 | 中：审 steps 改动与新钩子设计 | 语料仓先补测试钩子（走产品正规链路），再修订步骤文本与 Swift 启动参数 |
| **spec_amendment（规格修订）** | 规格自身与平台事实不符（SwiftUI 呈现模型、系统权限归属等），原断言在当前平台恒红或恒真 | 改 steps 和/或 oracle | **高**：强制红证方案，禁止弱化成恒真断言（与 [01 总体设计 §9.7](01-总体设计.md) 验收红证防假绿同源） | 修订断言锚点/补条件步骤，mutate-red 证明新断言仍抓得住缺陷 |

分类有争议时从高不从低（按更严一档走审批与红证）。

### C.3 六阶段流程

1. **登记（AR）**：每条偏差复制 `05-amendments/_AR-TEMPLATE.md` 建一份
   `AR-NNN-<简短名>.md`，填证据、分类、拟议变更、影响面、红证方案；在任务 handoff 登记，
   首批 AR-001..004 实例索引见本文末 ADR 归档链接。登记不阻断其他用例的生成与执行。
2. **人工裁决**：按 C.2 权重审批。spec_amendment 必须当场确认红证方案可执行；裁决结论
   以**日期追加**写在 AR 内，原始偏差登记与证据不删不改。
3. **产品基线先冻结**：语料仓侧动作（合入缺陷修复、应用钩子补丁）全部由人工在演示分支
   完成并过 `xcodegen generate` + `build-for-testing` 门禁；产品基线未定型前不得动
   TestPilot 侧规格。
4. **库内修订（身份稳定、版本自动递增）**：
   - 用例 `external_id` **保持不变**（TC-A1 修订后仍是 TC-A1），不新建「TC-A1-r2」，
     保证 OID、automation-map、hybrid 计划接线不断；
   - 修订动作落在语料仓用例文档（演示分支），TestPilot 侧重跑 ingest 即可：
     `TestCase.version` 由文档内容 hash 自动赋值（`case_docs.py` 解析期
     `version=sha256(文档文本)[:12]`），文档一改版本自动换新，零 DDL；
   - 修订前导出的 `case-set-<UTC>-<hash8>.json` 是不可变快照，原样留存，AR 记录
     新旧 version 与两个快照文件名。
5. **下游再生成（内容寻址自动换代）**：重新导出 case-set → 出新版 prompt 包（v2/v3…）
   → 外部 Agent 按修订规格改 Swift，重跑构建门禁与 GS 扫描 → 重建 hybrid-plan。
   plan 是内容寻址制品，规格文本一变 hash 自动变；旧 plan 文件与 `hsess-*` 会话账本
   原样保留为历史证据（加日期注记，不删除不覆盖）。
6. **红证 + 真机验收**：每条获准 AR 做 mutate-red/revert-green（临时回退产品修复/钩子、
   恢复旧断言，分别证明对应测试变红后复原），零 TEMP-RED 残留，再进 hybrid E2E runbook
   的真机走查。红证记录贴回 AR。

### C.5 版本链与证据保全对照

| 制品 | 版本机制 | 修订后的处置 |
| --- | --- | --- |
| 语料仓用例文档 | git 轨迹（演示分支） | 修订块带日期小节；主线文档不动 |
| `TestCase.version` | 文档 sha256 前 12 位，ingest 自动赋值 | 重灌即换，AR 记录新旧值 |
| case-set 导出 | 文件名带 UTC 时间戳 + hash8 | 每轮新文件，旧文件不可变留存 |
| prompt 任务书 | 包内版本号（v1/v2…） | 新版置顶列与上版 diff |
| hybrid-plan | 内容寻址 hash 文件名 | 新 hash 新文件；旧 plan、`hsess-*` 账本保留加日期注记 |
| generation-report / AR | dated 追加 | 原始偏差登记永不删改，裁决与红证向下追加 |
