## 0. 总设计原则

> **不要试图"规范人"，要让系统迁就脏乱数据。**

"不写 commit message、用例只有步骤没有预期、文档更新不及时"在任何公司都不会靠"定规范+培训"
解决。Demo 的核心姿态：**人照样乱写，系统从机器可得的高可信信号（代码 diff、CI、执行结果、
commit 历史）里自己把知识捞出来，再把补全草稿推给人一键确认**——知识沉淀是工作流的副产物，
不是额外任务。

第二条原则：**无证据不结论**。检索为空、定位冲突、用例不可执行时各自降级；定界/问答结论必须
带证据引用，宁可输出"未知"，不编造文件名、模块名或结论。

## 1. 系统全景（目标形态）

```
┌─────────────────────────────────────────────────────────────┐
│  触点层：IM Bot / IDE 插件（模拟）/ Web 控制台 / CI 评论回写     │
├─────────────────────────────────────────────────────────────┤
│  编排层：LangGraph 状态机（问答 / 测试生成 / 失败归因三条图）     │
│         模型路由（小模型分类 → 大模型生成）· HITL 人审节点      │
├─────────────────────────────────────────────────────────────┤
│  工具层：Git 工具 · 代码检索（grep/AST）· 跑测试(xcodebuild)   │
│         · 取日志(os_log/xcresult) · 工单读写 · 影响面分析       │
├─────────────────────────────────────────────────────────────┤
│  知识层（四层，见第 3 节）                                      │
│  L0 实时源联邦查询 │ L1 实体关系库 │ L2 加工语料索引 │ L3 规则资产│
├─────────────────────────────────────────────────────────────┤
│  治理层：质量评分 · 新鲜度/stale 检测 · 增量摄入调度 · 评测回归  │
│         · Langfuse 追踪 · 采纳反馈回流                         │
├─────────────────────────────────────────────────────────────┤
│  数据底座：Chroma(向量) + BM25(全文) + SQLite(实体/图谱/元数据) │
│         + Ollama(本地模型, 私有化叙事)                         │
└──────────────────────────────────────────────────────────────┘
```

关键设计：**L0 实时数据不进知识库，用时联邦直查**。CI 状态、当前 HEAD 的代码、工单最新状态
永远查实时接口；知识库存的是"加工过、有保质期的认知"（摘要、关系、经验），不是原始数据的拷贝。
这一条直接消解"更新不及时"焦虑——最容易过期的东西压根不缓存。

系统边界与对接方式另见 [04-系统边界与外部对接清单.md](04-系统边界与外部对接清单.md)：TestPilot Core
只依赖端口接口，本地文件/JSON、xcodebuild、Jira/GitLab、JUnit/Gradle/K8s 等都作为可替换适配器。

## 3. 知识库怎么建：分层与加工管线

### 3.1 四层结构（以 AlarmKitSpike 举例）

- **L0 实时层（不入库）**：Git 仓当前代码、CI 结果、工单状态。Agent 回答"现在主钟 backup 是多少秒"
  时实时读 `MissionCoordinator.swift`，不信任何旧切块。
- **L1 实体关系层（SQLite 图库）**：机器抽取的**实体和关联**，是对抗"文档乱写"的主力：
  - 实体：需求条目、用例、代码符号（`MissionCoordinator.schedulePrimary`）、缺陷、文档章节、CI 流水线；
  - 关系：需求→测试点→用例→代码符号、缺陷→修复 commit→符号、文档→引用的符号；
  - 每条关系带 **confidence（0–1）和证据**（如"用例 TC-A2 与 schedulePrimary 关联：confidence 0.9，
    证据=用例文本提到 +30s backup"）。低置信关系不展示给用户，只在检索时降权。
- **L2 语料层（向量 + BM25 混合索引）**：文档切块、代码符号级摘要、事故复盘、用例文本。
- **L3 规则资产层**：领域术语表（kill-backup、companion、侧键接管……）、prompt 模板、
  **golden set 评测集**、few-shot 案例、工具白名单。

### 3.2 加工管线怎么处理脏乱输入

```
原始输入 → ①解析归一化 → ②质量评分 → ③实体链接 → ④切块嵌入 → ⑤登记元数据
```

**① 归一化——针对"因人而异"**：

| 脏乱输入 | 不靠人规范，系统怎么做 |
|---|---|
| commit message 空/废话 | **根本不依赖 message**：从 `git diff` 用 AST 提"变更符号集合 + 变更类型（增删改签名/改逻辑）"，再让小模型**反推**一条规范 message 草稿回写到 MR 给开发者确认 |
| 需求文档自由格式 | LLM 抽固定骨架：{功能点、规则、验收标准、涉及模块}；抽不出验收标准的条目标缺，不硬编 |
| 用例只有大致步骤、没预期 | 见 3.3，oracle 挖掘，这是 Demo 亮点 |
| 工单格式不一 | 抽 {现象、复现步骤、根因（若有）、修复 commit}；根因缺失就只建现象索引 |
| 人员能力参差 | 与作者解耦——所有条目按**证据质量**而非作者职级排序；机器信号（代码/CI）权重高于人写文本 |

**② 质量评分**：每个条目算 `quality_score`（结构化程度、有无证据链接、信息完整度、是否被后续事件
证实）。检索排序 = 相关性 × 质量分 × 新鲜度衰减。**烂数据不删、不拦、只降权**——硬拦会让人彻底
不用系统。

**③ 实体链接**：切分时同步识别"这段文字提到了哪些代码符号/需求/用例"（术语表 + LLM），在 L1
建引用边。这是后面重构感知和影响面分析的地基。

**⑤ 元数据**：每条知识必带 `来源、作者、时间、content_hash、适用分支、关联符号集、最后验证版本
(commit)、访问计数`。

### 3.3 专项：没有评判标准的测试用例怎么办（oracle problem）

1. 把用例表示成结构化对象：`{前置条件, 步骤[], oracle[]}`，oracle 分四类——**UI 断言、日志断言
   （os_log 关键字/时序）、状态断言（系统闹钟快照/账本字段）、人工确认**；
2. 对只有模糊步骤的存量用例，Agent 从四个来源**挖 oracle**：需求里的验收标准、现有自动化代码里的
   断言（`XCTAssertTrue(...)`）、历史缺陷（每个 bug 天然是一条回归 oracle）、代码当前行为；
3. 挖出来的 oracle 生成**草稿**推给测试人员："TC-A2 原来没有预期，我建议补：① `ROUTINE` 组
   UUID 与 fire 一致（日志断言）② 105s 内无第二次接力页（状态断言）"，一键采纳/修改/拒绝；
4. 实在挖不到的，标记为**探索性用例**，不进入自动化执行链路，只做步骤引导。

叙事：**AI 不替代人判断，但把人从"写格式"提升到"判对错"**。

### 3.4 知识怎么不断沉淀（飞轮，零额外动作）

- 人修改了 AI 生成的用例/摘要 → diff 存为"偏好样本"，进 L3；
- 人审通过 → 直接入库（带 confirmed 标记，质量分 +0.3）；
- 点"踩" → 进 bad case 池，每周触发 prompt/检索策略回归；
- CI 失败归因被确认 → 缺陷-根因-符号关系自动入库；
- 事故复盘 → Agent 用 Git/CI/日志事件自动重建时间线，人只补"为什么"，复盘文成文即带实体链接入库；
- MR 合入 → diff 摘要、变更符号、影响用例自动入库。

## 4. 保鲜、重构、双轨：三个时序难题

### 4.1 更新不及时 → 事件驱动 + 实时校验双保险

- **事件驱动摄入**：git push / CI finished / ticket closed 的 webhook 触发增量 ETL；定时全量扫描
  兜底。索引增量延迟可在监控页看到（目标 P95 < 5 分钟）。
- **代码类回答生成前强制 live-verify**：RAG 召回的代码摘要只是线索，Agent 在生成答案前必须调工具
  确认引用的符号在当前 HEAD 仍存在、函数体 hash 未变；变了就**当场重读代码重新生成**，旧切块只
  贡献"历史经验"。这样哪怕索引滞后，答案也不会错——Demo 里值得专门演示的机制。
- 新鲜度分级 TTL：CI/状态不缓存；代码摘要 TTL 跟随 commit 事件；架构文档长 TTL；事故复盘
  **永不过期但标注"验证于版本 X"**。

### 4.2 重构后知识失配 → 知识绑定符号实体，不绑定文本

- 知识条目锚定的是**稳定符号 ID**（`Symbol:MissionCoordinator.schedulePrimary`），不是文件行号；
- 摄入时用 Git rename detection + AST 调用图 diff 识别重构事件（rename/move/签名变化），更新符号映射；
- 引用了被重构符号的知识条目自动标 `STALE`，**按价值分批 reindex**：高价值（被检索/引用多）的立刻
  用新代码重新生成摘要；低价值的 lazy reindex（下次被命中时再生）；
- 事故复盘这类历史文档**不改写**——它是历史证词。检索时两个结果并列呈现：**「历史经验
  （2026-09-14 版本）」+「当前实现（HEAD 实时摘要）」**，Agent prompt 明确区分二者。这个设计本身
  是设计要点：知识库要的是"可追溯"，不是"永远现在时"。

### 4.3 重构双轨期 → 分支感知索引 + blue-green 切换

- **每个长期分支独立索引 namespace**，知识条目带 branch 维度；问答时从用户当前 `git branch`
  自动路由，不用人选；
- 实体关系允许同一逻辑实体两个实现并存，关系带 `valid_from/valid_to + 分支归属`；跨分支提问时
  Agent 调 diff 工具输出"新旧实现差异 + 迁移影响面"；
- **blue-green 索引**：重构分支创建后 CI 自动对它**预索引**（先建新的）；合入删旧代码时旧条目
  不删，标 `superseded_by=新符号`（再标旧的），杜绝"新代码知识没建成、旧知识已失效"的真空期。

## 5. 研发/测试什么时候用、怎么用（触点嵌入既有工作流）

原则：**不让人来平台找 AI，把 AI 塞进他们已在的工具和时刻**。以一次真实迭代为例：

| 阶段 | 时刻 | 系统动作 | 人做什么 |
|---|---|---|---|
| 需求评审 | 需求文档链接丢进 IM Bot | 输出测试点清单、验收标准缺口、**影响面**（关联代码/历史相似缺陷，如"涉及 kill-backup，历史有 3 次相关事故"） | 评审会上直接讨论，确认测试点 |
| 用例设计 | 测试人员打开用例页 | 推送相似历史用例草稿 + 补全 oracle（3.3） | 改草稿而不是从零写，一键确认入库 |
| 编码/CR | MR 创建 | 自动生成 MR 摘要；评论区挂"**影响 12 条用例，其中 3 条无自动化、2 条与本次 diff 冲突需更新**" | 开发者点链接更新用例 |
| CI 执行 | 流水线失败 | 自动归因：flaky / 环境 / 真缺陷 / 用例过期，附日志证据，回写 MR 评论；疑似真缺陷起草工单 | 看结论，确认或纠偏（反馈即沉淀） |
| 测试执行 | 每日回归 | Agent 跑用例、失败时拉 os_log/xcresult 重建时间线 | 只处理 Agent 判不了的 |
| 事故复盘 | 故障关闭 | 自动重建事件时间线、生成复盘骨架并带实体链接 | 只写"为什么"和改进项 |
| 日常 | 随时 | IM/IDE 里自然语言问"侧边键兜底有哪几层""这个函数谁在用" | 零学习成本 |

**研发用、测试也用，但用法不同**：研发侧主打 MR 影响面、CR 辅助、问答；测试侧主打用例生成、
执行归因、回归范围推荐。演示时准备两个角色视角。

## 6. Demo 演示脚本（10 分钟版）

1. **问答 + 引用**：问"裸按侧边键后铃声为什么还能继续？" → 回答引用四层兜底文档 + 当前代码，
   标注"文档更新于 commit X，HEAD 代码一致 ✅"。
2. **脏乱数据鲁棒性**：展示一条 message 为空的 commit，系统照样从 diff 抽出变更符号并生成摘要草稿。
3. **测试 Agent 闭环**：丢一份"killBackupInterval 调参"需求 → 自动出测试点和用例（含从历史事故
   挖出的 oracle）→ 人审通过两条 → 真实跑 `xcodebuild test` → 故意展示一条失败用例被归因为
   "用例期望 90s 未随代码更新"（用例过期，不是代码 bug），给出更新建议。
4. **保鲜/重构 live 演示**：现场把 `schedulePrimary` 重命名 → push → webhook 触发 → 知识条目变
   STALE → 高价值条目自动 reindex；再问同一个问题，答案引用新符号名。
5. **双轨**：切到 refactor 分支问同一问题，答案自动切到分支版本，并能对比新旧差异。
6. **治理看板收尾**：golden set 评测曲线、检索命中率、坏答案分类、单请求成本下降（路由+缓存）、
   采纳率。**每个数字标注数据版本/模型版本/参数版本。**

第 3、4、6 是差异化爆点，多数同类 Demo 只做到第 1 步的问答演示。
