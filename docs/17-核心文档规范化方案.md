## 2. 业界参照与选型结论

不引入重型测试管理平台（V1 规模 52 条用例、单人维护、docs-as-code 现状），只借标准与方法：

| 参照 | 借什么 | 不借什么 |
|---|---|---|
| **ISO/IEC/IEEE 29119-3**（软件测试文档标准） | 测试用例的标准要素集：标识、前置条件、输入、操作步骤、预期结果、后置条件、优先级/状态；测试规格与测试过程分离 | 全套文档模板与合规流程（POC 过重） |
| **ISTQB CTFL** 用例纪律 | 三段式心智（前置/步骤/预期）；可判定、可复现、原子性——一条预期只陈述一个可判真假的命题 | 等价类/边界值等设计技术属测试设计层，与文档规范无关 |
| **EARS**（Mavin et al., *Easy Approach to Requirements Syntax*, RE 2009） | 五类受控需求句式，把复合句改写成可 lint 的规则句（见附录 B） | 不强制全量需求一步到位，先治 FR-2 系列重灾区 |
| **Gherkin / BDD（Given-When-Then）** | 前置→触发→预期的三段结构心智，与 29119-3 要素同构 | 不引入 .feature 文件与 Cucumber 工具链；Markdown 是本仓既定载体 |
| **Specification by Example / ATDD**（Gojko Adzic） | 关键实例与需求同仓、随代码变更一起保鲜；具体实例代替抽象验收描述 | 不搞三 amigo 工作坊流程 |
| **docs-as-code + CI lint** | Markdown 入仓、门禁化校验（本仓已有 pytest/import-lint/build_web 三门禁先例） | — |

**一句话选型**：29119-3 定要素、ISTQB 定纪律、EARS 治需求句式、GWT 借三段心智、SbE 保实例保鲜、docs-as-code 落工具链。

## 3. 目标与非目标

**目标**

1. 两套规范化 Markdown 模板（用例文档、需求文档），与现有解析器能力对齐并给出能力缺口清单；
2. `testpilot-lint-cases` 只读探针：结构/可判定性/锚点/保鲜四类规则 + 可量化聚合指标，先报告后阻断；
3. Agent 辅助重写走既有 HITL + outbox 回写基建，语料仓只读红线不破；
4. V1 两文档分批迁移，每批可独立验证、可回退。

**非目标（本期不做）**

- 不改 schema 版本、不建新表（重写建议通道复用既有建议/审批模型，建表决策留待 R2 切片）；
- 不把用例改写成 Gherkin/feature，不引入外部 ALM；
- 不追求一次性重写 52 条用例；不重写历史实测记录的原始措辞（历史证据纪律）；
- 不在本稿实现任何代码（切片排期见 §7）。

## 4. 规范化模板

### 4.1 用例文档模板（叙事体为规范形态，表格体降级为索引）

文档头元信息表与「通用约定」段沿用现状。每条用例统一五段骨架：

```markdown
### TC-xx 用例标题（FR-x/FR-y）P0 🤖    <!-- 环境标记入标题行；📱=必须真机 -->

**前置**：
- 冷启携带 `--ak-clear-all --ak-accept-privacy`，无残留 mission
- 设备已解锁、通知授权已授予

**步骤**：
1. 单一动作一句，编号连续（对应 parser 顶格编号正则）
2. ……

**预期**：
- 【UI 断言｜步骤2】系统全屏闹钟消失，锁屏无补救通知
- 【日志断言｜步骤2】T0 起 120s 内见 `RINGER gate unmuted ...`
- 【人工确认｜步骤4】主观无叠音/双震动（2026-11-16 订正：原稿误写「人工断言」，
  解析器 EXPLICIT_TYPE_LABELS 只认 UI 断言/日志断言/状态断言/人工确认四词，误写会回退
  关键词分类；顺手补齐步骤锚点示例）

**背景与平台约束**（仅供理解，不可作为断言依据，不进自动化导出）：
- 平台约束：后台非混音会话必抛 !int，必须保持 .mixWithOthers
- 版本差异：iOS 26.4 不投递 LA .ended（三轮实测）

**实测记录（2026-09-16，iPhone 16 Pro / iOS 26.4）**：
- 历史证据原样冻结，参数后续变更只加日期注记，不回改原句
```

写作规则（lint 规则的人工对应版）：

1. **标记完整**：`**前置**：`/`**步骤**：`/`**预期**：` 必须带全角或半角冒号（D1 直接对策）；
2. **原子断言**：一条 bullet 只陈述一个可判真假的命题；日志链按检查点拆条（治 D3，拆分规则待 docs/16 §4.8 盲评定阈）；
3. **显式标签权威**：预期 bullet 以 `【类型｜步骤N】` 开头（类型集沿用现有四分类），人审标签高于一切词表；
4. **步骤单一动作**：一条编号步骤只含一个主动作，钩子参数/观察说明移到该步骤子句或前置；
5. **前置独立成段**：环境、授权、钩子、账号/数据准备只进前置段（D4）；
6. **知识材料只进背景段**：平台约束、机制指针、版本差异、历史沿革禁止出现在预期段（D2 源头对策；独立段解析未上线前，C2 词表继续在预期段内兜底）；
7. **步骤锚点显式化**：断言归属明确时写「步骤 N」或标签锚点段；全程断言不硬锚（None 合法）；
8. **历史冻结**：实测记录必须带日期与设备，参数变迁追加注记不回改（D6，对齐 CLAUDE.md 历史证据纪律）。

**TC-A1b 规范化前后对照（节选）**：

```markdown
<!-- 规范化前：D1+D2 并发，机制夹注跨行混在预期标记行 -->

<!-- 规范化后：标记干净、机制说明移背景段、断言带类型标签 -->
```

## 5. lint 探针设计：`testpilot-lint-cases`

### 5.1 架构（对齐现有纯函数纪律）

- core 新增 `case_lint.py`：**纯函数、零 IO、零三方**，吃 `parse_case_markdown` 的
  `TestCase + dead_letters` 产出结构化发现项；风格仿 `quality.py`（frozen dataclass、
  分项可解释、带 reasons）；
- workers 新增薄 CLI `testpilot-lint-cases`（命名对齐 `testpilot-ingest-cases` 等
  既有入口）：遍历摄入文档 → 调纯函数 → 输出 JSON 报告；退出码 0=无 error、
  1=有 error 发现、2=运行环境错误（对齐 `case_export` 的 exit 2 先例）；
- 每条规则配 hostless 正反夹具测试，红证纪律：临时回退规则实现必须变红。

### 5.2 规则登记表（首版，三级：error / warning / info）

| 规则号 | 级别 | 检查内容 | 病灶 |
|---|---|---|---|
| LINT-C-001 | error | 预期/步骤标记存在但缺冒号或标记拼写漂移 | D1 |
| LINT-C-002 | error | 用例有步骤但 `oracle_missing=True`（真缺预期，而非标记故障） | D1 |
| LINT-C-003 | error | 步骤编号不连续/重复；step_id 越界死信（直接汇总解析 dead_letters） | 锚点 |
| LINT-C-004 | warning | 预期段 bullet 被 C2 分流为 context（列出条目与命中词表），源头独立段化后应清零 | D2 |
| LINT-C-005 | warning | 超长断言：字符数或反引号日志 token 数超阈（阈值先跑分布再定，写入 params 版本） | D3 |
| LINT-C-006 | warning | 断言无显式 `【类型】` 标签且无法被关键词分类器确定归类 | 可判定性 |
| LINT-C-007 | warning | 表格体用例（迁移进度指标，迁移完成后降级 info） | D5 |

| LINT-C-011 | info | 需求侧：FR 描述不符合 EARS 五类句式（需求 lint，二期） | D7 |

## 6. Agent 辅助重写流程（HITL，复用既有基建）

红线：语料仓只读，Agent 永远不直接改 V1 原档。整条链路复用 S2 已建成的
ingest → 建议 → 审批 → outbox → dispatch 通道：

```
testpilot-lint-cases 问题清单（按用例聚合，带规则号+证据片段）
  → Agent 产出「重写建议」（结构化 diff：原 bullet → 建议五段骨架，附命中规则与理由）
  → 人在审批页逐条 adopt/modify/reject（复用 plan_case_decision 的 fail-closed 纪律：
    一次评审必须交代全部待决项，防静默遗漏）
  → 通过项走 outbox（target_system=markdown-case-repo，既有通道）
  → dispatch 写本仓回写根：每用例一文件（writeback_rel_path 既有约定），内容寻址幂等
  → 人手动把回写文件合并回语料仓（提 PR，人是最后一道闸）
  → 合并后 testpilot-ingest-cases --full + testpilot-extract-requirements --full
    + testpilot-mine-oracles --full 重灌，lint 复跑，前后指标对比入报告
    （2026-11-16 注记：需求文档有改动时 extract-requirements 不可省——
    requirement_skeletons 是独立表，跳过会让挖掘按旧 AC 重建建议；建议 URN 为
    sha1(type|expectation) 内容寻址，旧文案生成同 URN，幽灵建议清扫后原样复活）
```

设计要点：

- **建议而非改写**：Agent 输出是带理由的候选 diff，原始 bullet 全文保留在建议载荷里，
  人可逐字对照；不允许静默删除历史实测记录（重写建议触及实测段时强制 warning 并要求显式确认）；
- **幂等与对账**：回写幂等键沿用 `outbox_idempotency_key`（同用例同渲染文本同键），
  重放不产生重复文件；幻影记录可幂等取消，符合「先持久化账本再发起外部副作用」纪律；
- **不新建通道**：R2 切片优先复用现有 suggestion/approval 模型承载重写建议（新增
  source_kind 枚举值而非新表）；若载荷形状实在容纳不下，建表决策另立评审，本稿不预设；
- **重灌兼容**：重写必然改变 content hash，迁移批次统一走 `--full` 显式重灌（docs/16
  §5 的 hash-skip 教训）；批次尽量安排在审批库低存量期，避免 --full 清扫与已审批数据冲突。
