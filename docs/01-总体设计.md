| 项      | 内容                                                                                                                |

## 1. 定位与建设策略

不做「手搓 RAG → 上框架 → 再重构」的线性路线，而是**第一天就按最终架构立骨架**，
每个里程碑交付一条可真实使用的纵切链路，在使用中暴露知识缺口，再在实现中定向补缺。

三条铁律：

1. **架构一次到位，范围逐片扩大**：端口/适配器、独立 runner worker、证据账本、HITL（关键动作人工点头才执行）、outbox（外部写先在本地记账再派发，中途被杀也能续）、评测/trace 从第一行代码就存在。多项目、K8s、Jira/GitLab 真实对接、vLLM 容量均为 P2，留适配器接口和 profile，不在当前范围实现。
2. **每片都要真实使用 + 指标门禁**（门禁=不过线不许进下一片的机器校验）：每个里程碑结束必须跑通 [06 核心评测指标体系](06-核心评测指标体系.md) 中该切片对应的指标门禁。

## 2. 设计原则

1. **迁就脏乱数据，不规范人**：以机器高可信信号（diff、CI、执行结果、commit 历史）为主，
   人写文本降权不删；知识沉淀是工作流副产物。「不写 commit message、用例只有步骤没有预期、文档更新不及时」不靠定规范+培训解决——人照样乱写，系统从机器信号里自己把知识捞出来，再把补全草稿推给人一键确认。
2. **无证据不结论**：所有事实性输出带引用、版本、新鲜度；检索为空/冲突显式降级（依赖不可用时走简化路径并挂出标记）为「未知」，宁可输出未知也不编造文件名、模块名或结论。
3. **核心不认识具体系统**：Core 只依赖端口接口与统一领域模型；xcodebuild/Gradle/Jira/文件路径
   一律在适配器层（[04 系统边界](04-系统边界与外部对接清单.md) §6）。
4. **外部副作用最小授权 + 先账后事**：默认只读；写入必须 HITL，先持久化 outbox/幂等键再发起
   （[04](04-系统边界与外部对接清单.md) §7）。
5. **评测驱动**：每次 prompt/检索/模型改动都跑冻结 golden set，前后成对报告（[06](06-核心评测指标体系.md)）。
6. **环境差异诚实**：模拟器给不出的结论（真机后台、签名、多进程、物理刺激）显式标注未覆盖；哪层已验、哪层只能真机/生产验，必须写进执行记录。

## 3. 逻辑架构

```text
┌─────────────────────────────────────────────────────────────────┐
│ 触点通道（Channel Adapters）                                      │
│  Web 控制台（Next.js 静态导出，6 路由）                              │
│  通知通道（P2：IM Bot/CI 评论）                                     │
└───────────────┬─────────────────────────────────────────────────┘
                │ REST / SSE
┌───────────────▼─────────────────────────────────────────────────┐
│ testpilot-orchestrator（FastAPI，7 个 API 域 47 端点 + /health）    │
│  三条 LangGraph 工作流：问答 / 测试设计 / 执行归因                   │
│  统一模型 · 证据账本 · HITL 审批 · 权限策略 · outbox · 预算守卫     │
└───────┬──────────────────────────────────┬───────────────────────┘
        │ 端口接口（testpilot-core 定义）     │ 任务队列（QueuePort）
┌───────▼──────────────────────────────────▼───────────────────────┐
│ Workers（ingest / runner / eval 等角色，同一 Python 包多入口）       │
│  ETL/实体链接/索引/stale/reindex · 独立进程执行测试，超时隔离 · 评测 │
└───────┬──────────────────────────────────────────────────────────┘
        │ 适配器（按 profile 装配）
┌───────▼──────────────────────────────────────────────────────────┐
│ SCM(git) │ Docs(fs) │ Cases(md) │ Tickets(json) │ CI(json events)  │
│ Runner(xcode→P2:junit) │ Env(iOS sim→P2:k8s) │ Artifact(localfs)  │
│ Logs(os_log→P2:elk) │ Model(Ollama/云API) │ Vector(Chroma)        │
└──────────────────────────────────────────────────────────────────┘

数据底座：SQLite（元数据/FTS5 BM25/outbox/审批/评测/反馈，schema v15）
          Chroma（向量，offline-demo 可关）│ 本地 FS（制品/夹具）│ Langfuse（trace，可选）
```

架构要点：

- CI、测试执行器、环境管理器是三个独立外部系统，runner 从第一天独立进程化，
  LangGraph 节点不直接 subprocess；
- 知识库拆为**知识源（端口）** 与 **派生索引（TestPilot 资产）**，文件系统只是源适配器；
- 评测/trace/outbox 不是独立模块，而是横切所有工作流的内建能力；
- **L0 实时数据不进知识库，用时联邦直查**：CI 状态、当前 HEAD 代码、工单最新状态永远查实时
  接口；知识库存的是「加工过、有保质期的认知」（摘要、关系、经验），不是原始数据拷贝。

## 4. 子系统与代码边界

工程根 `subsystems/`，分包即边界，Core 的 import 规则用 lint 强制
（禁止 core 依赖任何 adapter / SDK，`scripts/import_lint.py` 机器校验）。

| 子系统 | 职责 | 边界纪律 |
|---|---|---|
| `packages/core`（testpilot-core） | 领域模型、端口接口、策略、证据账本模型、错误/降级类型、全部 hostless 纯函数 | 无 IO、无 SDK、无框架依赖（纯 Python） |
| `packages/adapters`（testpilot-adapters） | git / fs-docs / md-cases / json-tickets / json-ci-events / xcode-runner / ios-sim-env / localfs-artifact / oslog-logs / chroma-vector / fts5-bm25 / ollama-model / SQLite 队列与账本 / FileGateStore 等 | 每个 adapter 一个目录 + 契约测试 |
| `packages/orchestrator`（testpilot-orchestrator） | FastAPI、LangGraph 三图、HITL API、outbox 调度、SSE、静态 SPA 同端口托管 | 只依赖 core 的端口；7 个 API 域：qa/approval/assets/badcase/execution/gate/knowledge |
| `packages/workers`（testpilot-workers） | 全部控制台脚本（20 个 console script）：ingest/runner/eval 三角色 + 导出/映射/重跑/混合执行/ws-gate 等 | 独立进程，**LangGraph 节点不直接 subprocess** |
| `web/` | Next.js（App Router）静态导出控制台：对话、审批、执行详情（runs/detail）、知识管理、闸门（gates）6 路由 | 调 orchestrator REST；前端无单测，门禁是 build_web + 人工走查 |
| `deploy/` | docker-compose.yml + docker-compose.host-minio.yml，Ollama/Langfuse/Redis/Chroma/MinIO 编排 | 一键起；compose 内均为开发默认值，禁生产 |
| `scripts/` | verify_s0 门禁与 29 个 hermetic 探针、device_hub_ax_cli.swift 等真机侧脚本 | 探针不依赖模拟器/外部服务 |
| `tests/` + fixtures | 141 个测试文件、1704 个 hostless 用例；工单 JSON、CI 事件、离线 runner 录制结果、golden set | 生成物不入库 |

进程间通信：

- orchestrator → workers：`QueuePort`。**当前四个 profile 全部使用 SQLite 队列表**，保证无外部
  依赖也能演示完整状态机；Redis + arq 作为端口预留（P2）；
- worker → orchestrator：回写 SQLite 业务库 + 任务状态；前端经 SSE/轮询订阅进度；
- 所有跨进程任务带 `idempotency_key`，worker 至少一次投递 + 任务侧幂等（同一操作重复 N 次效果等于一次，重投不产生重复数据）。

## 5. 统一领域模型与 URN（testpilot-core）

首批模型（字段全量在需求说明书 [08](08-需求说明书.md) 展开）：

```text
Project/RepoRef          项目与仓库引用（路径走配置，不写死）
SourceDocument           知识源文档（source_system, uri, version/etag, acl, 权威等级）
KnowledgeChunk/Entity/Relation   切块、实体、带 confidence+证据的关系
Requirement/TestPoint/TestCase    需求、测试点、结构化用例{前置,步骤[],oracle[]（oracle=判断对错的参照标准，即"预期结果"的学名）}
ChangeSet/CodeSymbol     diff 变更集、版本化符号（稳定 SymbolId，不绑行号）
TestExecutionRequest/TestRun/CaseResult    语言中立的执行契约
Issue/IssueDraft         工单与工单草稿
Evidence/EvidenceRef     证据（source_system, uri, version/hash, 查询条件, 抓取身份, 时间）
Approval/OutboxRecord    人审记录、外部副作用账本
Feedback                 采纳/修改/拒绝 + 原因
EvalCase/EvalRun         golden 题与评测批次（数据/模型/prompt/参数版本四元组）
```

后续切片在**零 DDL 红线**下增量落地的模型字段（均随 pydantic 模型 + raw_json 投影持久化，
schema 版本定格 v15）：

- `Oracle.step_id`（1-based 步骤锚点，None=用例级全程断言）与 `TestCase.context_notes`
  （知识/平台约束等不可判定材料），规则全文见 §8；
- `TestExecutionRequest.launch_arguments`（混合执行清场启动参数的账本追溯字段，不穿越
  xcode argv，见 §10.5）。

URN（系统内统一资源名，外部系统自己的 ID 不当主键）规范：
`urn:testpilot:<source_system>:<resource_type>:<external_id>@<version>`。

## 6. 三条工作流（最终形态）

### 6.1 知识问答图

```text
提问 → 意图/权限校验 → 混合检索(FTS5+Chroma+rerank) → 证据分级
     → 代码类问题强制 live-verify(HEAD 符号/hash 复核)
     → 生成（带引用骨架，约束只许引用召回证据）
     → 引用校验器（URI 可达/hash/版本；失败则重生成或降级"未知"）
     → 输出（答案+引用+版本+新鲜度标注；历史证词并列"历史经验/当前实现"）
     → 反馈采集
```

### 6.2 测试设计图

```text
需求接入 → 骨架抽取（把自由文档抽成固定四段结构）{功能点,规则,验收标准,模块}（缺验收标准显式标缺）
        → 影响面检索（相似历史用例/事故/相关符号）
        → 测试点生成 → 用例生成（结构化；oracle 四类：UI/日志/状态/人工）
        → oracle 挖掘（需求验收标准/现有断言/历史缺陷/当前代码 四源，步骤锚点规则见 §8）
        → 草稿（不入库）→ HITL（采纳/修改/拒绝；diff 即偏好样本）
        → 批准后经 TestCaseRepositoryPort 回写（Markdown adapter 起步）
```

### 6.3 测试执行与失败归因图

```text
选择用例/接收 PipelineFinished 事件
  → 环境能力校验（模拟器不满足真机能力直接 unsupported_capability）
  → EnvironmentPort.acquire → runner-worker 执行（xcodebuild；P2 JUnit）
  → 采集 xcresult/JUnit + 截图/录屏 + os_log（按 runId/时间窗）
  → 失败归因（候选：真缺陷/用例过期/flaky（同代码时过时不过的不稳定用例）/环境失败/产品改动；先列多候选再取证区分）
  → 归因结论 + 证据包 + 置信度
  → HITL → outbox：MR 评论 / 工单草稿 / 用例更新建议（R2/R3 分级，见 04 §7）
```

### 6.4 横切能力（每个节点都经过）

- **证据账本**：每次工具调用与结论写 Evidence（记账留证，可从最终输出反查全部来源）；
- **预算守卫**：步数/token/重跑次数硬上限；工具白名单；
- **trace**：全链路 Langfuse（runId 与证据账本、TestRun 关联）；不设 `TESTPILOT_TRACER`
  时不导出任何 trace，Langfuse 自身遥测由 `TELEMETRY_ENABLED=false` 关闭；
- **降级标注**：模型/检索/适配器任一不可用时输出降级标记，计入评测。

## 7. 知识工程与保鲜

### 7.1 四层知识库

- **L0 实时联邦（不入库）**：Git 仓当前代码、CI 结果、工单状态，用到时实时取、不缓存结论。
  回答「现在主钟 backup 是多少秒」时实时读当前 Swift 源文件，不信任何旧切块。
- **L1 实体关系（SQLite 图库）**：机器抽取的实体和关联，是对抗「文档乱写」的主力。
  实体：需求条目、用例、代码符号（如 `MissionCoordinator.schedulePrimary`）、缺陷、文档章节、CI 流水线；关系：需求→测试点→用例→代码符号、缺陷→修复 commit→符号、文档→引用符号。
  每条关系带 **confidence（0–1）和证据**；低置信关系不展示给用户，只在检索时降权。
- **L2 混合索引（Chroma 向量 + SQLite FTS5 BM25）**：文档切块、代码符号级摘要、事故复盘、用例文本。offline-demo profile 关闭 Chroma，检索保持 FTS-only。
- **L3 规则资产**：领域术语表（kill-backup、companion、侧键接管……）、prompt 模板、
  **golden set 评测集**、few-shot 案例（提示词里附少量示例教模型按格式输出）、工具白名单。

### 7.2 加工管线怎么处理脏乱输入

```text
原始输入 → ①解析归一化 → ②质量评分 → ③实体链接 → ④切块嵌入 → ⑤登记元数据
```

| 脏乱输入                | 不靠人规范，系统怎么做                                                                                              |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| commit message 空/废话 | **根本不依赖 message**：从 `git diff` 用 AST 提「变更符号集合 + 变更类型（增删改签名/改逻辑）」，再让小模型**反推**一条规范 message 草稿回写到 MR 给开发者确认 |
| 需求文档自由格式            | LLM 抽固定骨架：{功能点、规则、验收标准、涉及模块}；抽不出验收标准的条目标缺，不硬编                                                            |
| 用例只有大致步骤、没预期        | oracle 四源挖掘 + 步骤锚定（§8）                                                                                   |
| 工单格式不一              | 抽 {现象、复现步骤、根因（若有）、修复 commit}；根因缺失就只建现象索引                                                                 |
| 人员能力参差              | 与作者解耦——所有条目按**证据质量**而非作者职级排序；机器信号（代码/CI）权重高于人写文本                                                         |

- **质量评分**：每个条目算 `quality_score`（结构化程度、有无证据链接、信息完整度、是否被后续事件证实）。检索排序 = 相关性 × 质量分 × 新鲜度衰减。**烂数据不删、不拦、只降权**。
- **实体链接**：切分时同步识别「这段文字提到了哪些代码符号/需求/用例」（术语表 + LLM），在 L1 建引用边，是重构感知和影响面分析的地基。
- **元数据**：每条知识必带 `来源、作者、时间、content_hash、适用分支、关联符号集、最后验证版本(commit)、访问计数`。

### 7.3 知识飞轮（零额外动作）

- 人修改了 AI 生成的用例/摘要 → diff 存为「偏好样本」，进 L3；
- 人审通过 → 直接入库（带 confirmed 标记，质量分 +0.3）；
- 点「踩」→ 进 bad case 池，定期触发 prompt/检索策略回归；
- CI 失败归因被确认 → 缺陷-根因-符号关系自动入库；
- 事故复盘 → Agent 用 Git/CI/日志事件自动重建时间线，人只补「为什么」，复盘文成文即带实体链接入库；
- MR 合入 → diff 摘要、变更符号、影响用例自动入库。

### 7.4 三个时序难题

1. **更新不及时 → 事件驱动 + 实时校验双保险**。git push / CI finished / ticket closed 事件
   触发增量 ETL，定时全量扫描兜底；**摄入延迟目标 P95 < 5 分钟**（[06](06-核心评测指标体系.md)
   §4 指标口径）。代码类回答生成前强制 **live-verify**：召回的代码摘要只是线索，生成前必须
   调工具确认引用符号在当前 HEAD 仍存在、函数体 hash 未变；变了当场重读代码重新生成，
   旧切块只贡献「历史经验」。新鲜度分级 TTL：CI/状态不缓存；代码摘要跟随 commit 事件；
   架构文档长 TTL；事故复盘**永不过期但标注「验证于版本 X」**。
2. **重构后知识失配 → 知识绑定符号实体，不绑定文本**。知识条目锚定稳定符号 ID
   （`Symbol:MissionCoordinator.schedulePrimary`），不是文件行号；摄入时用 Git rename
   detection + AST 调用图 diff 识别重构事件；引用被重构符号的条目自动标 `STALE`（索引条目与当前代码对不上的过期标记），**按价值分批 reindex**（重新切块嵌入替换旧索引）：高价值立即
   重建，低价值 lazy（下次被命中时再生）。事故复盘等历史文档**不改写**——检索时「历史经验
   （某版本）」与「当前实现（HEAD 实时摘要）」并列呈现。
3. **重构双轨期 → 分支感知索引 + blue-green 切换（P2 预留）**。长期分支独立索引 namespace，条目带 branch 维度，按当前 `git branch` 自动路由；重构分支 CI 预索引（先建新的），合入时旧条目标 `superseded_by=新符号` 而不删除，杜绝新旧知识真空期。

## 8. 用例模型：步骤锚点、知识分流与 oracle 形态

本章把结构化用例的判定性内容（oracle）与非判定性内容（背景知识）分开，并让每条断言可锚定到具体步骤，全链路（解析→挖掘→审批→回写→导出→外部 Agent prompt）无损传递。早期串案与假oracle 事故的修复过程见 [INC-20261114-01](archive/01-事故与踩坑记录.md#inc-20261114-01)。

### 8.1 模型字段（零 DDL）

```python
class Oracle(BaseModel):
    type: OracleType
    expectation: str
    source_refs: list[str] = Field(default_factory=list)
    confidence: float = Field(default=0.5, ge=0.0, le=1.0)
    step_id: int | None = None        # 1-based，对齐 steps 序号；None=用例级（全程）断言

class TestCase(BaseModel):
    ...
    context_notes: list[str] = Field(default_factory=list)  # 知识/平台约束，非判定性材料
```

- 持久化无需迁移：`upsert_test_case` 以 `model_dump_json()` 全量写 raw_json，老数据反序列化取默认值 None/[]；
- `step_id` 取值域：`None` 或 `1..len(steps)`，越界即非法载荷；
- 知识材料独立成 `context_notes` 而不是给 Oracle 加 role 枚举——断言列表保持单一职责，
  exploratory 判定、导出分流、外部 Agent 资格判断都不必再过滤「伪 oracle」。

### 8.2 解析器锚定规则（确定性、保守，零模型参与）

叙事体「预期」段每个顶层 bullet 产出一条 oracle，锚点优先级：

1. **显式步骤引用**：文本匹配 `步骤\s*N` / `Step\s*N`（阿拉伯数字）→ `step_id=N`。
   `1 ≤ N ≤ len(steps)` 正常锚定；**越界不静默**：step_id 置 None 并产 `CaseParseError`
   死信（单条失败整批继续的 AC2 纪律），死信原因写明越界值与步骤总数；同条断言引用多个
   不同步骤号按歧义死信同口径处理。
2. **嵌套子弹**：继承所属顶层 bullet 的 step_id。
3. **事件相对描述**（T0、侧边键后、解锁后、亮屏瞬间…）：一律 `None`。事件不是稳定序号，
   硬映射就是猜测；用例级断言在导出时翻译为步骤间注释，不丢语义。
4. **表格体**：单预期格无步骤结构，恒 `None`。
5. 历史无锚点文档行为不变（全 None）。

### 8.3 知识型 bullet 分流（context_notes）

纯函数 `classify_bullet_role(text) -> Literal["assertion","context"]`，**默认 assertion**，仅命中确定性保守词表时归 context（宁可漏分流，不可误杀判定性断言）：

- 词表：段首「平台约束」「真机实锤」「历史：/历史 +四位年份」「实测记录」，以及纯机制说明
  句式（「iOS x.y 不投递…」「仅为其他版本/出口保留」）；「历史」段首必须冒号或四位年份
  紧随，防「历史告警记录页面应展示…」这类真断言被误分流；
- 句首括号机制夹注（如 `（…按代码现文案核对；机制见 X.y(…)）：`）三端齐备才命中；
- **两阶段分流**：入口期只按段首标记分桶以保证嵌套子项随父汇聚，build 期对拼接完整文本再跑
  全量复核，命中者从断言桶移到背景桶，其步骤锚点与锚点死信一并撤销；
- 人审回写显式标签 `【类型…】` 是权威断言，任何词表不得覆盖；
- `context_notes` 不进 oracle_suggestions、不参与 exploratory 判定、不进 v1 导出 oracles[]；
  Web 区块明示「仅供理解，不可作为断言依据，不进自动化导出」。

### 8.4 oracle 挖掘链路

- **suggestion_urn 保持 `hash(type|expectation)` 不含 step_id**：锚点修订不换 URN，已审批/
  已回写记录不产生孤儿，重灌幂等不受锚点迭代影响；
- 确定性三源：自有断言携带解析期 step_id；requirement_ac 与 incident 源默认 `step_id=None`
  （AC/事故句子没有步骤序号语义）；
- 模型补点（仅 oracle_missing 用例）：JSON schema 的 items 增可选 `step_id`；prompt 铁律
  「仅当白名单用例步骤文本与断言存在显式对应时给 step_id，否则 null，禁止按事件描述猜测
  序号」；白名单拒入增校验：非 null 且越界 → `RejectedOracle(reason="bad_shape")` 进
  dead_letters（source=oracle-mine），与幻觉台账同路径；
- R2/R3 纪律：平移仍仅对 oracle_missing 开放，来源用例 URN 强制追加。

### 8.5 审批视图与 Markdown round-trip

- 审批 API `ReviewQueueItem` 携 `steps`/`preconditions`（从 raw_json 取，零 SQL 改动）；
  建议列表按 `step_id` 分组——「用例级（全程）」组 + 「步骤 1…N」组，组内沿用来源/置信度/
  「平移自」徽章；分组逻辑抽纯函数，门禁 build_web + 人工走查。
- 回写标签扩展（无标签旧文档行为不变）：

```markdown
- 【UI 断言｜步骤3】系统全屏闹钟消失，锁屏上没有补救通知
- 【日志断言】T0 见 KEEPALIVE armed ……        ← 无锚点=用例级，写法兼容
```

  全角 `｜` 为规范分隔符，半角 `|` 同步接受；`step_id is not None` 时才输出锚点段，
  渲染→解析 round-trip 后 step_id/类型/文本三字段无损。

### 8.6 导出契约状态与未落地项（P3）

- **当前导出契约仍是 case-export-v1**：v1 为显式白名单 dict，step_id 不外泄、context_notes
  不泄漏（有红证锁死）。`case-export-v2`（oracle 增 step_id、case 增 context_notes[]、
  `--contract v1|v2` 双版本、外部 Agent prompt 升 v2）**未落地，列入 P3**；
- P3 另两项未落地：①长日志链拆分（仅对「反引号大写日志 token 序列 + 箭头连接」强结构句式机械拆分，需先做盲评对照再定阈值）；②模型草稿语义去重（embed 余弦相似度，阈值须在冻结夹具上标定后写入 params 版本，无 embed 适配器的 profile 自动跳过）。

### 8.7 规则升级时的重灌纪律

解析规则变更而源文档未变时，文档 content hash 不变，增量模式会整文档跳过
（`skipped_unchanged`），新规则不执行。**「规则升级重灌」必须显式 `--full` 强制整组重建**：

```bash
uv run testpilot-ingest-cases --full
uv run testpilot-mine-oracles --full
```

常规重灌走增量即可；审批库有 approved 数据后，step_id 回填应走兼容重灌而非清扫。
盲评封存的 seal 与冻结指标永不重算，新规则结果按「冻结列/新规则列」双列报告，
见 [BASE-20261112-01](archive/05-评测基线快照.md#base-20261112-01)。

## 9. 用例导出与 Xcode 执行闭环

前置定案：系统内**不做 Swift 代码生成器**（决策背景见
[ADR-20261113-01](archive/03-方案演进与废弃决策.md#adr-20261113-01)）——AI 产规格、外部 Agent 辅产代码、人审合入、系统负责映射与真实执行；全程 schema v15 零 DDL。

### 9.1 两个必演场景与系统边界

- **场景 A：需求 → 全量用例 → 外部生成代码 → 回流真实执行**
  1. 对真实需求文档跑 S2 管线（需求骨架→测试点→结构化用例→oracle），人审批准；
  2. 导出结构化 JSON 用例集（case-export-v1）；
  3. 人工携出系统边界，在语料仓的**长期演示分支**上由外部 Agent 按约定生成 Swift 测试，人审编译通过后合入该分支；
  4. 本系统扫描演示分支，按 TC 标记建立「用例 ↔ Swift 测试」映射（automation-map-v1）；
  5. 经映射把用例选择集翻译成 `-only-testing`，真实 `xcodebuild test` 执行，xcresult 回收、失败归因（复用 §6.3 既有能力）。
- **场景 B：commit diff → 影响面 → 存量用例选择重跑 → 归因**
  1. 对演示分支两个真实 commit 跑影响面分析（三分类runnable/no_automation/conflict_update）；
  2. CLI 把 runnable 集经映射翻译成 Swift 标识符并提交执行队列，未映射用例显式报告；
  3. 真实 xcodebuild 选择重跑 → xcresult → 归因五候选落账，全程 runId 贯通。

```text
┌─────────────────────── ai-testpilot（本仓，系统内，全自动+人审点）──────────────────────┐
│ 需求骨架 → 测试点 → 用例/oracle（S2 既有）→ HITL 审批（既有）                              │
│   → E1 导出 JSON 用例集（版本化契约）                                                     │
│ E3 扫描演示分支 Swift 测试 + TC 标记 → automation-map.json（人审映射）                    │
│ E4 影响面 runnable → 映射 → TestExecutionRequest → 队列（配额/幂等/策略全复用既有）        │
│ E5 xcode runner（S3 既有适配器）→ xcodebuild → xcresult 解析 → 归因（S3 既有）            │
└───────────────────────────────▲────────────────────────────────────────────────────────┘
                                │ JSON 携出（人工） / 只读 git 读取演示分支（人工合入）
┌───────────────────────────────┴────────────────────────────────────────────────────────┐
│ 语料仓（系统外，只读接入）                                                                 │
│ 演示分支 demo/agent-generated-tests（长期存在，永不合主线）：                              │
│ 外部 Agent（Claude 等）按约定生成 Swift 测试 → 人审 + 编译验证 → 人工合入                  │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

边界纪律：

1. testpilot **永不写**语料仓（git 连接器只读）；分支创建与代码合入是人工动作，runbook 给全步骤；
2. 外部 Agent 的生成过程不属于本系统能力，演示话术与文档均如实标注，生成对话记录以附件留痕；
3. 系统只信任两类事实：人审批准的用例规格、演示分支上**真实存在且编译通过**的 Swift 测试；
4. 映射缺失时响亮失败/显式报告，绝不静默全量执行或假绿。

### 9.3 契约二：外部生成约定与 TC 标记规范（双 target）

对外部 Agent 的硬性约定（prompt 模板全文在 [13 系统使用说明书附录 A](13-系统使用说明书（克隆到使用全流程）.md#appendix-a)，
可整段复制）：单元测试与 UI 测试是契约内两个对等分支，共用标记/命名/溯源规范，
仅落点与代码形态不同。

1. **标记注释**：每个生成的测试方法上方一行 `// testpilot-case: <TC-ID>`；一个方法覆盖多个
   TC 时写多行标记；单元/UI 两类标记语法完全一致，扫描器按目录自动分流 target；
2. **命名**：`func test_<TC-ID 去横线转驼峰>_<英文短描述>()`，例：
   `TC-C1 → test_TCC1_countdownSnapshots()`；
3. **target 分流规则（依据导出 JSON 既有字段，不引入新字段）**：
   - 该 TC 任一 `oracles[].type == "ui_assertion"` → **UI 分支**：写入
     `AlarmKitSpike/UITests/AgentGenerated/`（按模块命名文件，类名 `Agent<Module>UITests`），
     归属 `AlarmKitSpikeUITests` target（XCUITest，驱动真实产品 UI）；
   - 其余 → **单元分支**：写入 `AlarmKitSpike/Tests/AgentGenerated/`（类名
     `Agent<Module>Tests`），归属 `AlarmKitSpikeTests` target（hostless 纯 Foundation 测试）；
   - 人工可在交付指令中显式覆盖分流，但必须在 `generation-report.md` 逐条记录覆盖原因；
     系统侧不强制分流，扫描映射只认最终落点目录；
   - `exploratory=true`、或 `oracle_missing=true` 且无任何 oracle 的用例两个分支都不生成，
     进报告 skipped 清单；
4. **UI 分支额外硬约定**（对齐存量 `UITests/ProductFlowUITests.swift`，外部 Agent 必须先读
   再写）：XCUITest 形态，`XCUIApplication` 驱动真实 UI，不直接 init 领域模型；
   `setUpWithError` 中 `continueAfterFailure = false`，每用例冷启动零累积，启动参数固定带
   `--ak-clear-all --ak-purge-dates --ak-accept-privacy`（隐私门专项用 `--ak-reset-privacy`
   强制重弹，参数语义以语料仓 `CLAUDE.md` 避坑指南为准）；等待一律
   `waitForExistence(timeout:)` 轮询，禁止死等；断言旧页面消失而非仅断言新标题存在
   （防同名假绿）；关键步截图作为 xcresult attachment；V1 测试用例文档标 📱（硬件键/全屏
   闹钟画面/音频/震动/锁屏视觉）的用例模拟器不可验，**不得生成模拟器 UI 测试**，进 skipped
   并注明「仅真机可验」；🤖 标记才可生成；
5. **编译门禁**：两类产物都必须在 `AlarmKitSpike/` 子目录先 `xcodegen generate`（两个 target
   的 sources 都是 folder group，新文件必须重新生成工程才进编译）再
   `xcodebuild build-for-testing` 通过，人审确认断言与 oracle 期望一致才可合入；
6. **禁止事项**：不改 `Sources/` 生产代码、不修改/删除 `Tests/` 与 `UITests/` 存量测试、
   不引入第三方依赖与新 Pod；若实测确认是产品侧测试钩子/能力缺口，按 AR 流程立
   `fixture_change` 类偏差（[13 附录 C](13-系统使用说明书（克隆到使用全流程）.md#appendix-c)），
   补丁由 TestPilot 侧起草、人工评审后在语料仓独立分支应用，不属于外部 Agent 的生成 diff；

### 9.4 契约三：自动化映射文件（`automation-map-v1`）

落盘 `store/<profile>/automation-map.json`（`--out` 可改路径），可人审编辑后重跑扫描合入，
或用 `--bind/--review` CLI 登记。

```json
{
  "map_schema_version": "automation-map-v1",
  "generated_at": "...",
  "repo_path": ".../app-calendar-alarm",
  "branch": "demo/agent-generated-tests",
  "head_commit": "<sha>",
  "map_hash": "<sha256，剔除 generated_at/map_hash 自身后规范化哈希；head_commit 参与哈希——HEAD 移动 hash 必变>",
  "bindings": [
    {
      "case_external_id": "TC-C1",
      "only_testing_id": "AlarmKitSpikeTests/RoutineAlarmTests/test_TCC1_countdownSnapshots",
      "source_file": "AlarmKitSpike/Tests/AgentGenerated/RoutineAlarmAgentTests.swift",
      "line": 42,
      "origin": "marker",
      "reviewed_by": "",
      "reviewed_at": null
    },
    {
      "case_external_id": "TC-U1",
      "only_testing_id": "AlarmKitSpikeUITests/AgentQuickAlarmUITests/test_TCU1_quickCountdownFlow",
      "source_file": "AlarmKitSpike/UITests/AgentGenerated/QuickAlarmAgentUITests.swift",
      "line": 31,
      "origin": "marker",
      "reviewed_by": "",
      "reviewed_at": null
    }
  ],
  "unlinked_swift_tests": [
    {"only_testing_id": "AlarmKitSpikeTests/HolidayCalendarTests/testPlainDays",
     "source_file": "...", "line": 60}
  ],
  "unmapped_active_cases": ["TC-N2"],
  "scan_warnings": ["重复标记: TC-C1 同时出现于 FileA.swift:10 与 FileB.swift:20"]
}
```

规则：

- 扫描口径：正则识别 `class …Tests` 与 `func test\w+`（Swift 方法签名封闭形态，不引 Swift
  解析器）；标记只认行首空白后 `// testpilot-case: TC-…`，挂在下方最近方法、遇 class 清空
  悬挂标记；target 按目录映射（Tests→AlarmKitSpikeTests，UITests→AlarmKitSpikeUITests），
  并有两道 containment——路径必须含工程根段 `AlarmKitSpike`，工程根内再分 target，仓里根
  `Tests/` 的作废 SPM 包不被误纳；非 ASCII 方法名不被 `\w+` 识别，不计入台账；
- `origin=marker` 自动绑定；`origin=manual` 是人审对无标记存量测试的手工绑定
  （CLI `--bind <TC>=<Target/Class/method> --by <人>`，或编辑本文件后重扫合入；Swift 方法
  必须真实存在，悬空即 fail-closed）；
- 一个 TC 可绑定多个方法（执行时标识符全量带入、xcresult 按方法分别回收，产生 exit 3 警告
  催人审）；一个方法标记多个 TC 时执行记录双向回链；
- 映射同时投影到 `test_cases.raw_json.automation`（只追加、reindex 存活口径同知识治理），
  **schema 保持 v15 不动**；
- **三档退出码**：**exit 2 硬错误**（TC 不存在/非活跃、畸形标记、非法 OID、悬空 manual、
  旧 map 损坏）→ 不写 map、不覆盖旧 map；**exit 3 警告**（一 TC 多方法、探索性标记被剔除）
  → map 照写催人审；**exit 0** 干净。重扫幂等：同 HEAD 同内容 map_hash 稳定，人审记录
  跨重扫保留。

### 9.5 契约四：通道一刺激能力圈（`stimulus-channel1-v0`，草案，未转正）

真机刺激的第一个自动化通道是现有 xcodebuild 管线内的**包内 XCUITest**，编号「通道一」。
通道二（Appium+WDA）、通道三（go-ios/CoreDevice 私有面）留待后续 spike 另立契约，
本契约不提前承诺它们的能力。方案校准与真机实验台账见
[CAL-20261113-02](archive/02-探针校准与环境实测.md#cal-20261113-02) 与
[EVD-20261113-02](archive/04-真机验收台账.md#evd-20261113-02)。

**通道一能力圈（硬边界，证据 = Xcode SDK `XCUIDeviceButton.h` 头文件）**

| 刺激（DeviceStimulus 拟议名） | 通道一判定 | 依据与守卫 |
|---|---|---|
| `volume_up` / `volume_down` | **在圈（官方 API）** | `XCUIDeviceButton.volumeUp/volumeDown`，枚举标 `XCUI_SIMULATOR_UNAVAILABLE`，仅真机可用；模拟器 run 不得声明覆盖 |
| `home` | **在圈（官方 API）** | 同枚举 `.home`，真机限定 |
| `unlock` | **条件在圈（社区技法，非 API 承诺）** | 仅允许 `XCUIApplication(bundleIdentifier:"com.apple.springboard")` 滑屏 + 密码盘路径；守卫见下「解锁技法四守卫」；spike 通过前不得进自动执行 |
| `lock` | **圈外** | 枚举无 lock case；官方特性面无锁屏动作（devicectl 全量子命令亦无）；通道一遇到 lock 必须 fail-loud 或挂起人工，禁止伪装成功 |
| `side_button`（真实 HID 侧键） | **圈外** | 枚举无对应 case（`.action`/`.camera` 不等同侧键 HID 语义）；不得用软件事件冒充硬件侧键，两类事件的 os_log 因果链不同 |

解锁技法四守卫（缺一不可）：① pin 住 iOS 大版本，密码盘布局漂移即失效；② 断言「锁屏页面
消失」而非仅「新标题存在」，防同名假绿；③ 设备密码只经 profile/环境变量注入测试 bundle，
**密码明文绝不入仓、不入日志、不进 query 回显**；④ 连续 10 次运行零假绿方可转正在圈，
证据录屏随 spike 报告封存。

**接合规则（本切片不实现 DeviceControlPort）**

- 刺激只允许作用于**已租约的 env_id**：无 EnvironmentPort 租约不裸操作设备，租约口径复用
  既有 acquire → env_id_for_lease → release；真机环境 `reset` 永远 PolicyDenied，抹除只能
  人工经系统设置或 MDM；
- 未来 `DeviceControlPort.capabilities()` 的通道一实现必须逐字按上表声明，不支持的
  DeviceStimulus 不进能力集；worker 预检遇圈外刺激 → 响亮失败或挂起人工混合流，
  **绝不静默跳过**；
- 通道一适配器与 xcodebuild 同进程出口（唯一 SubprocessExecutor，argv 数组永不 shell），
  不引入 Node/WDA/Go 任何新运行时；schema 保持 **v15 零 DDL**，刺激记录走既有执行事件
  契约 + ArtifactStorePort 制品 URN。

**A 层（日志归因层）os_log 因果链硬约定**

1. 每个刺激用例必须带可回放时间窗（start/end ISO8601）与 NSPredicate 原文，随 query 回显
   落执行记录；真机走 `.logarchive` 两步法（[03](03-语料工程与实测环境（AlarmKitSpike）.md)
   §3.7），manual 模式下人工 collect 命令原文必须随档留存，证据链不断；
2. 刺激生效的断言必须以 os_log 条目（subsystem/process/message + 时间戳）为因果证据，
   不允许仅凭 UI 状态截图判定「刺激已生效」；UI 录屏只作旁证；
3. 时间窗闭区间 `[start, end]`，窗外条目经服务端 `filter_window` 二次剔除，不得入证据集；
   NDJSON 坏行计数留片、fail-closed，不用残缺数据凑因果；
4. 模拟器 run 的 `uncovered_layers` 继续显式声明 ios.device 等三层未覆盖；真机 run
   （profile `target: device`）三层物理可验、uncovered_layers 为空，两种口径不得互串；
5. 红证要求：通道一刺激测试必须能抓住「刺激未真实发出」的回归（临时回退 press 调用，
   断言须变红），警惕全程全绿中的假阳性。

### 9.8 明确不做

1. 不做系统内 Swift/任何语言代码生成、不做编译器封装（`xcodebuild build-for-testing`

2. 不做 web 页面承接本闭环（控制台补全方案整体搁置，见

3. 不做自动分支创建/自动合入；不把外部 Agent 生成的代码拷入本仓，不把演示分支合入语料仓主线；
4. 不做 schema v16（映射走 raw_json + 独立 map 文件）；不改动 S2/S3/S4 既有语义与探针封存值；
5. 不做 WS↔gate store 常驻桥接进程与 web 交互页：一期人工介入走 CLI——structural 全自动用
   `testpilot-hybrid ws-run` 单命令，**人工 gates 用独立 TTY 三终端序列**
   （`testpilot-ws-gate-driver` 前台交互，TTY 边界实证见
   [INC-20261119-01](archive/01-事故与踩坑记录.md#inc-20261119-01) 与
   [ADR-20261119-02](archive/03-方案演进与废弃决策.md#adr-20261119-02)），不引
   Node/WDA/Go 新运行时；
6. 不做多会话循环：一期一次调用一条 TC-Ax（单会话 complete 即收口）；一条 xcodebuild
   action 串行多用例的 gate_id 自路由多会话列二期；
7. 不写 test_runs 表、不接 FileGateStore（core 四态无 rejected、gate id 闭集不同构、双时钟
   会给假续期）；B1 本地转录 + localfs URN 是一期账本，`ws-relay:` 幂等前缀的终态直写
   导入器留二期；
8. 不做 build-for-testing 自动化与 DerivedData 自动发现（`--xctestrun` 必须显式）；
   模拟器 profile 保持 iproxy 不启用，device profile 供真机人工序列使用；ws-run 人工
   stdout 转发产品化列二期；
9. TestPilotKit Swift 侧零改动、不进 Python 包，留语料仓本地 SPM；线协议字面量
   （`tp-hybrid-ws-p0`、`TP_*` 环境键、全部消息类型、`g-*` 闸门 id）冻结，Swift 按字对线。

## 10. 混合执行与人工闸门（hybrid-plan-v1）

S3 打通的 xcodebuild 闭环只覆盖「单进程内 UI 操作 + UI/日志断言」。真实 P0 用例存在两类
系统判不了的环节：①**圈外刺激**——锁屏、物理侧边键、`sudo log collect` 等不在自动化能力
圈内（HID/CGEvent 合成输入在模拟器与真机均惰性；真机 DH AX 仅 Home/Rotate/Screenshot
三动词可达，Lock/Siri 等菜单灰显，取证见
[EVD-20261113-02](archive/04-真机验收台账.md#evd-20261113-02)）；②**感官裁决**——铃声、
震动最终体感必须由人确认。本方案把一条 TestCase 不拆分，派生出可恢复、可审计、人机共编的
混合执行计划，全程 runId/会话 id 贯通，人工环节有弹窗、有超时、有结构化裁决单，且人工
裁决必须绑定系统侧客观证据。

### 10.1 三层模型与零 DDL 约束

```text
TestCase（既有，不拆、不改）
   │  人读规格：steps/oracles/preconditions 原文，lifecycle=active 才可派生
   ▼ 派生（纯函数，内容寻址）
hybrid-plan-v1（JSON 制品，落 store，不建表）
   │  有序步骤 + 结构化前置 + 裁决单规格 + 幂等键 + content_hash
   ▼ 运行时
hybrid session（会话游标/账本，raw_json 制品，不建表）
   ├─ 子 run：auto:xcodebuild 步骤仍走既有 RunStatus 五态状态机与租约回收
   └─ 会话层：SessionStatus 另立，只描述游标，不进数据库
```

- **schema 保持 v15 零 DDL**：计划、会话检查点、闸门全部是 ArtifactStore 内内容寻址/文件态
  JSON；现有 run 表、状态机、迁移闭集一行不动；
- 子 run 失败语义不变（产品缺陷 → failed）；会话层 `blocked` 只表达「基础设施/人工未就位」，
  与产品失败严格区分，不污染失败归因五候选；
- 计划是 TestCase 的**派生制品**：TestCase 修订后 hash 变化即新计划，旧计划与旧会话保留不删。

### 10.2 五类执行方（actor 闭集）

| actor | 能力圈 | 动作闭集（v1） | 失败姿态 |
| --- | --- | --- | --- |
| `auto:xcodebuild` | 既有 XcodeTestRunner，一段 Swift 测试 = 一个子 run | `run_selector`（params.only_testing 非空） | 子 run 状态机裁决 |
| `auto:dh-ax` | Device Hub AX 语义通道（真机已验三动词） | `home` / `rotate_left` / `readiness` / `state` | 元素缺失/窗口零尺寸 fail-loud |
| `auto:devicectl` | 苹果官方 devicectl | `screenshot` / `launch_app` / `terminate_app` / `list_devices` | 非零退出 fail-loud |
| `human:action` | 人对物理设备的操作 | `lock_screen` / `press_side_button` / `other` | 超时 → blocked，可续期/放弃 |
| `human:verdict` | 人的感官/主观裁决 | `sensory_check` / `other`（带裁决单） | 超时 → blocked；与日志冲突 → 人工复核 |

表外 actor 在 pydantic 构造期即拒绝；表外 action 在计划校验期 `HybridPlanError` 响亮失败。
**未映射/不支持的刺激禁止静默跳过**。当前接线态：`auto:dh-ax` 已接 `home/rotate_left/
readiness`，`state` 与 `list_devices` 在运行期分派器显式拒绝（「尚未接线，拒绝静默跳过」）；
`terminate_app` 按 **PID** 终止（devicectl 无 bundle 终止动词，PID 必须在 `params.pid`
显式声明，缺失即 fail-loud）。DH AX 生产 CLI `scripts/device_hub_ax_cli.swift` 退出码闭集：
0 成功 / 2 进程缺失 / 3 参数非法 / 4 元素缺失或零尺寸窗口 / 5 AXPress 失败 / 6 AX 未授权
或 Mac 锁屏——非零一律 fail-loud，没有静默成功。

### 10.3 结构化前置条件（六 kind，三态探针）

每步声明零到多个前置，每条是 `kind + on_failure + repair?` 三元组。探针只回答三态——
`satisfied` / `unsatisfied` / `unknown`，**unknown 是诚实的能力圈边界不是失败**。

| kind | 实际探针 | 三态语义 | 典型 repair |
| --- | --- | --- | --- |
| `device_unlocked` | `DhAxAdapter.readiness()` 的 `screen_locked` | false→satisfied；true→unsatisfied；Mac 锁屏（exit 6）/AX 树脱物化（exit 4）取不到→unknown | `human_gate`（解锁归人） |
| `session_window_materialized` | readiness 的 `ok` + home/screenshot/rotate_left 三按钮可达性 | 全可达→satisfied；exit 4→unsatisfied；环境不可用→unknown | `dh_home` / `human_gate` |
| `portrait_orientation` | devicectl 截图落盘后 `png_probe` 读 IHDR 像素宽高（高>宽） | 竖屏→satisfied；横屏→unsatisfied；截图通道失败/PNG 非法→unknown | `dh_rotate_left`（转一步截一张，竖屏即停，上限 4 次；按截图判不按次数） |
| `app_not_running` | **恒 unknown**：devicectl 词汇表无进程清单动词，主机侧无法枚举存活 App | 仅支持按显式 PID 终止，禁止假装 satisfied | `devicectl_terminate`（须带 `params.pid`） |
| `no_active_alarms` | **恒 unknown**：App 内闹钟库对主机侧不可见 | 清场效果归该段 xcodebuild 结果兜底验证 | `app_launch_purge_args`（`--ak-purge-dates` 等启动参数，无 IO，并入子 run 载荷） |
| `notification_permission` | **恒 unknown**：授权归属可能不在本进程，重置命令未必有效 | 只能人工现场确认 | 仅 `human_gate` + blocked |

修复动词闭集：`dh_home` / `dh_rotate_left` / `devicectl_terminate` /
`app_launch_purge_args` / `human_gate`。其中 `human_gate` 只能配 `blocked` 姿态——能力圈外
的事不能判产品失败。**三级清理优先级**：① App 测试钩子（启动参数/测试菜单）> ② 宿主侧
DH AX / devicectl > ③ 人工闸门。前置建不起来时只有两种姿态：`blocked`（等人/等环境，
可恢复续跑）或 `fail_loud`（直接失败），禁止带假设状态开跑。串行执行的每条用例把前置
显式写进计划，而不是依赖上一条用例「恰好」留了干净现场。

### 10.4 计划契约（hybrid-plan-v1）

```json
{
  "plan_schema_version": "hybrid-plan-v1",
  "case_urn": "urn:testpilot:fs-cases:test_case:cases.md#TC-LOCK-01",
  "case_external_id": "TC-LOCK-01",
  "profile": "ios-local-poc",
  "project": "AlarmKitSpike",
  "steps": [
    {
      "step_id": "s1-purge-and-schedule",
      "actor": "auto:xcodebuild",
      "action": "run_selector",
      "params": {"only_testing": ["AlarmKitSpikeUITests/testLockRelay_schedule"]},
      "preconditions": [
        {"kind": "portrait_orientation", "on_failure": "blocked",
         "repair": {"verb": "dh_rotate_left", "params": {}}, "note": ""},
        {"kind": "no_active_alarms", "on_failure": "blocked",
         "repair": {"verb": "app_launch_purge_args", "params": {}}, "note": ""}
      ],
      "prompt": "",
      "verdict_form": null,
      "evidence_bindings": ["urn:testpilot:store:artifact:segA-xcresult"],
      "timeout_seconds": 300,
      "idempotency_key": "s1|TC-LOCK-01|schedule",
      "failure_policy": "abort_session"
    }
  ],
  "created_at": "2026-11-14T08:00:00Z",
  "content_hash": "<sha256，canonical JSON，剔除 created_at/content_hash>"
}
```

校验规则（计划期 fail-loud，`HybridPlanError`）：

1. 至少一个步骤；`step_id` 全计划唯一；
2. actor/action 必须在 §10.2 闭集；xcodebuild 段必须声明非空 `params.only_testing`；
   devicectl launch/terminate 必须声明 `bundle_id`（terminate 另需 PID）；
3. 人工步必须有非空 `prompt`（弹窗文案）；`human:verdict` 必须携带非空 `verdict_form`；
   自动步携带表单 = 非法；
4. 前置 kind、修复 verb 各走闭集；`human_gate` 修复只配 `blocked`；
5. 裁决表单字段 key 唯一；`choice` 字段必须给 `options`；
6. `require_evidence=true`（默认）的裁决步必须在 `evidence_bindings` 声明系统侧证据来源——
   **空口打勾在计划期就被拒**；
7. 仅 `lifecycle=active` 且非 `exploratory` 的 TestCase 可建计划；
8. 时间戳必须带时区；naive datetime 拒绝。

内容寻址与 case-export-v1 同纪律：canonical JSON（`sort_keys`、紧凑分隔、
`ensure_ascii=False`）sha256，剔除 `created_at`/`content_hash`，跨时间戳稳定、随内容变。
文件名 `hybrid-plan-<UTC时间戳>-<hash前8位>.json`。

### 10.5 会话状态机与崩溃恢复

```text
pending ──▶ running ──▶ passed / failed / error（终态，不可变）
              │  ├─▶ awaiting_human ──▶ running（闸门响应）
              │  ├─▶ blocked ──▶ running（环境恢复，当前步重回 running）
              └──▶ canceled（终态）
```

- `awaiting_human`：闸门已挂出，等人工响应；`blocked`：基础设施态不满足（DH 窗口消失、
  设备掉线、闸门超时）。两者都是**挂起态不是失败**；终态任何迁出都是非法迁移，纯函数直接
  抛错；单步状态 pending → running → completed/failed/blocked/skipped；只有 running 步可
  推进，对已处置步骤的重入显式拒绝。
- **检查点**：每推进一个步骤，`SessionCheckpoint`（会话 id、plan_hash、会话状态、每步状态
  表、completed 列表、current_step_id、gate_ids、updated_at）整体重写落盘；进程被杀后凭
  最后检查点续跑，不依赖任何内存态；推进是**纯函数**（不就地改入参，返回新对象），全部
  迁移规则有 hostless 红证测试钉死。
- 持久化信封 `HybridSessionRecord = session_id + plan 载荷 + checkpoint + ledger`，单文件
  `store/hybrid-sessions/hsess-<12hex>.json`，tmp+`os.replace` 原子写；session_id 由
  `case_external_id|content_hash` 确定性派生（同用例同计划版本重放同 id，重建幂等）。
  `ledger` 追加记录每步探针审计、repair 痕迹、子 run 引用（run_ref）、闸门 id 与适配器
  返回摘要；前置人工闸门响应后重入同一 running 步时凭 ledger 条目跳过对应前置，**不重复
  弹卡**；同一闸门重复 `resume_after_gate` 显式拒绝（防人工步双推进）。
- 编排器 `hybrid_runner.py` 提供 `start_session / drive_until_wait / resume_after_gate /
  unblock / get_session`：自动步连环推进到 awaiting_human/blocked/终态（迭代上限 100 防
  失控）；`AdapterUnavailableError` → blocked，动作失败按步骤 `failure_policy` 收口
  failed/blocked，两类语义严格区分。
- xcodebuild 段经 `ChildRunPort` 派发（`ChildRunRequest{only_testing, launch_arguments,
  idempotency_key}` → run_ref）。真实实现经既有 execution_service `submit_execution`
  入队（幂等键 `hybrid:<step key>` 命名空间，与 `impact:` 重跑源防撞、
  `daily_budget_key=None` 不占重跑配额），再轮询 run 账本到五态终态才交还 run_ref；崩溃
  续跑重放返回同一 run_id。失败严格分型：产品失败（FAILED）抛 `ChildRunFailedError` 走
  步骤 `failure_policy`；ERROR/TIMEOUT/CANCELED/等待超时/基础设施未就位抛
  `ChildRunUnavailableError`（带 runner worker 未排空 runbook 提示）→ 会话 blocked，
  不污染产品失败归因。
- **`launch_arguments` 是账本追溯字段，不穿越 xcode argv**：`xcodebuild -help` 无
  `-launchArguments` 旗标，`--ak-purge-dates` 等清场参数无法从主机 CLI 注入；真实生效路径
  是 Swift 侧 `XCUIApplication.launchArguments`（§9.3 生成契约，外部 Agent 写进段 A 方法）。
  该字段经 `TestExecutionRequest.launch_arguments`（默认空 list）随 request_json 零 DDL
  持久化，仅用于账本审计「本步打算清哪些场」，xcode argv 不消费它。

### 10.6 人工闸门与结构化裁决

实现：`adapters/gate_store.py`（`FileGateStore`，落 profile 写根 `data_dir/gates/
<gate_id>.json`，tmp+os.replace 原子写，gate_id 闭集正则防路径穿越）+
`workers/gate_service.py` + `orchestrator/gate_api/` + Web `app/gates/`。

1. 会话游标走到人工步 → `build_gate_request` 生成闸门载荷（gate_id 由
   `session_id|step_id` 哈希确定，**崩溃重建同 id，天然幂等**：重复 POST 挂单返回既有
   记录），状态 `pending`，带绝对 UTC deadline；
2. Web `/gates` 页 5s 轮询拉取全量闸门并按待处理/已闭环分组，pending 卡片展示倒计时与
   裁决表单（不做 osascript/系统通知，headless 友好；不做 SSE）；
3. **过期是读时现算而非定时任务**：任何 GET 到达时 service 用注入时钟对 pending 单比对
   deadline，过期即持久化 `expired`（测试可注入未来时间，零 sleep）；
4. 人在 deadline 前响应 → `responded`，裁决挂在同一 JSON 的 `response` 字段；过期单响应
   被拒绝（422「请先续期」），`renew` 把 expired 重开回 pending（会话 blocked 解除），
   `abandon` 走 canceled；已响应闸门不可取消（裁决留痕不可抹）；
5. HTTP 端点（6 个）：`POST /api/gates`（挂单）、`GET /api/gates?status=`（队列）、
   `GET /api/gates/{id}`、`POST /api/gates/{id}/respond|renew|abandon`；`HybridPlanError`
   统一映射 422，未知/非法 gate_id 映射 404；
6. 闸门状态闭集：pending / responded / expired / canceled。

裁决单 `verdict_form` 声明字段（boolean / choice / text，required 可控），响应
`HumanVerdict` 校验：必填字段齐；boolean 必须是真布尔；choice 值必须在 options 内；
text 非空；表单外字段拒绝；**证据强制**：`require_evidence=true` 时响应必须带至少一个
系统侧证据 URN（os_log 事件链制品、录屏抽帧、devicectl 截图），并记录 `decided_by`
见证人与 `decided_at`。人工结论与客观证据冲突时（例：人判「未响铃」但 os_log 存在完整
响铃事件链）：**不静默覆盖任何一方**，会话转人工复核队列，两份结论并排留痕，复核决定
计入归因。典型裁决单（锁屏响铃场景）：

| 字段 key | 类型 | 选项/说明 |
| --- | --- | --- |
| `ringtone_heard` | boolean | 是否听到铃声 |
| `vibration_felt` | boolean | 是否感到震动 |
| `confidence` | choice | high / medium / low |
| `note` | text，可选 | 环境噪声等备注 |
| 证据 URN | 强制 | os_log 响铃事件链 + 接力页录屏 |

### 10.8 驱动 CLI 与 ws-run 的队列外定位

`testpilot-hybrid`（workers 包 console script）把编排器函数面收敛为六个子命令：

| 子命令 | 作用 | 关键参数 |
| --- | --- | --- |
| `start` | 载入计划 JSON 建/重建会话（幂等，同 hash 返回同 session） | `--plan <plan.json>` |
| `drive` | 自动步连环推进到下一个 awaiting_human/blocked/终态 | `--session hsess-xxx --udid <硬件UDID> --bundle-id <bundle>` |
| `resume` | 闸门已响应后续跑（前置/步骤闸门内部自动区分路由） | 同上 + `--gate gate-<12hex>` |
| `unblock` | 环境阻塞解除后续跑（当前步重回 running） | `--session --udid --bundle-id` |
| `get` | 只读打印会话快照（计划/检查点/账本单 JSON） | `--session` |
| `ws-run` | **USB 反向监听单用例全链路**（队列外，交互式例外） | `--gates <json> --xctestrun <路径> --udid <UDID> --only-testing <OID> [--structural] [--target sim\|device] [--transcript-note]` |

契约：stdout 始终是单个 JSON 快照（`model_dump(mode="json")`），stderr 只放装配日志；
业务/装配硬错误统一 stderr `[hybrid-worker] 被拒: <Type>: <msg>` + **exit 2**，成功
exit 0；设备目标必须显式 `--udid`/`--bundle-id`（隐式 booted/默认 bundle 在真机会打错
目标），缺参 exit 2。profile 由 `TESTPILOT_PROFILE` 环境变量选择，**值必须是 yaml 完整
路径**（传裸 profile 名会报「profile 配置不存在」）；真机三进程（hybrid CLI、
`testpilot-runner worker`、uvicorn 闸门 API）必须同一 device profile，否则队列/闸门/会话
落在不同 data_dir 互不可见。**闸门响应不在本 CLI**：人在 Web `/gates` 页或
`POST /api/gates/{id}/respond` 提交裁决（expired 单先 `renew`），闸门转 `responded` 后
`resume --gate ...` 才合法。

**ws-run 是唯一的队列外子命令**：前五子命令驱动 hybrid-plan 会话、经 execution_service
队列派工；ws-run 是**单前台进程**编排一条 TC-Ax 的反向监听全链路，不进 worker 队列
（worker 无 TTY，`input()` 物理不成立；队列租约超时与 Swift 侧 120/240/240s 人工等待窗口
超时模型冲突）。拓扑：Runner（XCTest 进程内 TestPilotKit）在设备 loopback
`127.0.0.1:9876` 起 RFC6455 WS 服务端（NWListener），Mac 驱动是客户端；模拟器共享 Mac
loopback 直连，真机经 `iproxy`（usbmuxd）转发。driver-first：驱动先起（retry 窗 300s
硬下限兜 xcodebuild 启动墙钟），xcodebuild 后起；first-exit 对账（驱动非零先退立即
terminate 对方，shield 宽限防 CancelledError 灌入子进程 wait）；iproxy 在 finally 回收。
argv/注入/转录/profile 契约见 §9.6，模拟器 structural runbook 见
[03](03-语料工程与实测环境（AlarmKitSpike）.md) §3.8，真机三终端人工 runbook 见
[03](03-语料工程与实测环境（AlarmKitSpike）.md) §3.9。

**TTY 边界（受支持形态定稿）**：ws-run 单命令的人工 gates 形态经真机试跑证伪——子进程
stdout/stderr 仍是 PIPE，`wait()` 走 `communicate()` 排空即弃，驱动的闸门提示语到不了
编排终端，人工无法作答。故 **ws-run 受支持形态收敛为 structural 单命令（零提问全自动）**；
human gates 走独立 TTY 的 `testpilot-ws-gate-driver` 三终端序列（iproxy + 独立 TTY 驱动 +
注入器/xcodebuild）。事故与决策台账：[INC-20261119-01](archive/01-事故与踩坑记录.md#inc-20261119-01)、
[ADR-20261119-02](archive/03-方案演进与废弃决策.md#adr-20261119-02)；单命令人工形态的
stdout 转发增强列二期。

**reject 真实链**：Swift Runner 的 `XCTAssertEqual(verdict, "approve")` 在人工 reject 时
抛错，`finish()`/`close()` 不执行，XCTest 直接拆 NWConnection；驱动 recv 撞到连接关闭，
收口为第四 outcome `peer_closed`（传输无关，统一包 ConnectionClosed/EOFError/OSError），
必落转录（含 rejected 闸门 id）后 rc1 收口。分型：带 rejected 留痕且有产物 →
`product_failure`（exit 3）；无 reject 留痕 → `hard_error`（exit 2，现场矛盾不硬猜）。
xcodebuild rc≠0 **且有 result bundle** → `product_failure`（3）；rc≠0 无产物 →
`hard_error`（2）。任何路径都不存在 reject 自动冲绿。

### 10.9 B1 本地账本 vs FileGateStore（一期为什么不接 gate store）

ws-run 的账本是会话目录（§9.6 B1），不接 H2 的 FileGateStore，四条硬理由：
① core 闸门四态（pending/responded/expired/canceled）没有 rejected，reject 无处安放；
② 协议闸门 id 是 `g-*` 夹具闭集、与 gate store 的 `gate-<12hex>` 不同构，需要 ID 映射层；
③ Swift 侧 120/240/240s 硬超时与 store 续期是双时钟，桥接会给出假续期承诺；
④ `require_evidence` 与证据帧回流时序冲突（reject 早夭本就无证据）。
因此一期**不写 test_runs 表、不碰 FileGateStore**，转录字段 `test_run_ref` 恒 null 给二期
回填；WS↔gate store 常驻桥接（含 core reject 第五态、ID 映射、双时钟治理、B2 统一账本、
web 交互页）整体是二期一个切片，本期不做半截统一。

### 10.10 约束与不做的事

- schema v15 零 DDL；计划/会话/闸门只做制品与文件态，不新建表、不改 RunStatus；
- 不引入 WDA/go-ios 等新依赖；**不立无密码测试机策略**，锁屏/侧键/sudo 永远人工；
- 不支持的刺激与建不起来的前置 fail-loud/blocked，禁止静默跳过、禁止带假设开跑；
- 人工裁决强制证据 URN 与见证人；人机结论冲突走复核，不静默覆盖；
- 真机探针与人工 runbook 产物不进 verify_s0、不入库；store/out 制品不入库；
- 语料仓保持只读，本方案不改变 §9.1 系统边界；
- core reject 语义本期不变：reject 只存在于 B1 闸门转录（product_failure + rejected 闸门
  留痕），core 闸门不增第五态；
- 线协议字面量冻结，Swift TestPilotKit 按字对线；token 只走 `TESTPILOT_RELAY_TOKEN`
  环境变量，yaml/转录/快照绝不写明文。

## 16. 预期使用场景

### 16.1 触点嵌入既有工作流（不让人来平台找 AI，把 AI 塞进已在的工具和时刻）

| 阶段 | 时刻 | 系统动作 | 人做什么 |
|---|---|---|---|
| 需求评审 | 需求文档丢进入口 | 输出测试点清单、验收标准缺口、**影响面**（关联代码/历史相似缺陷） | 评审会直接讨论，确认测试点 |
| 用例设计 | 测试人员打开用例页 | 推送相似历史用例草稿 + 补全 oracle | 改草稿而不是从零写，一键确认入库 |
| 编码/CR | MR 创建 | 自动生成 MR 摘要；评论区挂「影响 N 条用例，其中无自动化/冲突需更新」清单 | 开发者点链接更新用例 |
| CI 执行 | 流水线失败 | 自动归因：flaky/环境/真缺陷/用例过期，附日志证据，回写 MR 评论；疑似真缺陷起草工单 | 看结论，确认或纠偏（反馈即沉淀） |
| 测试执行 | 每日回归 | Agent 跑用例、失败时拉 os_log/xcresult 重建时间线 | 只处理 Agent 判不了的 |
| 事故复盘 | 故障关闭 | 自动重建事件时间线、生成复盘骨架并带实体链接 | 只写「为什么」和改进项 |
| 日常 | 随时 | 自然语言问「侧边键兜底有哪几层」「这个函数谁在用」 | 零学习成本 |

研发侧主打 MR 影响面、CR 辅助、问答；测试侧主打用例生成、执行归因、回归范围推荐。

### 16.2 典型场景

1. **问答 + 引用**：问「裸按侧边键后铃声为什么还能继续？」→ 回答引用四层兜底文档 + 当前
   代码，标注「文档更新于 commit X，HEAD 代码一致 ✅」。
2. **脏乱数据鲁棒性**：展示一条 message 为空的 commit，系统照样从 diff 抽出变更符号并生成
   摘要草稿。
3. **测试 Agent 闭环**：丢一份调参需求 → 自动出测试点和用例（含从历史事故挖出的 oracle）
   → 人审通过两条 → 真实跑 `xcodebuild test` → 故意展示一条失败用例被归因为「用例期望
   未随代码更新」（用例过期，不是代码 bug），给出更新建议。
4. **保鲜/重构 live 演示**：把符号重命名 → push → 事件触发 → 知识条目变 STALE →
   高价值条目自动 reindex；再问同一个问题，答案引用新符号名。
5. **双轨**：切到 refactor 分支问同一问题，答案自动切到分支版本，并能对比新旧差异。
6. **治理看板收尾**：golden set 评测曲线、检索命中率、坏答案分类、单请求成本下降（路由+
   缓存）、采纳率。**每个数字标注数据版本/模型版本/参数版本。**

第 3、4、6 是差异化亮点：多数同类 Demo 只做到第 1 步的问答演示。
