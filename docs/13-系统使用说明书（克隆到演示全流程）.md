## 0. 这套系统是什么、两个必演场景

TestPilot 是智能研发测试助手，本说明书聚焦 2026-11 定案的 Xcode 执行闭环：

- **场景 A（需求 → 全量用例 → 真实 Xcode 执行）**：系统把需求加工成测试点/用例/oracle
  规格，导出结构化 JSON 用例集；**人工**把 JSON 携出系统边界，交给 Claude 等外部 Agent
  在被测仓的长期演示分支上生成 Xcode 测试代码（人审 + 编译门禁）；回流后系统扫描建立
  「用例 ↔ Xcode 测试方法」映射，并真实驱动 `xcodebuild` 执行、回收 xcresult。
- **场景 B（commit diff → 影响面 → 存量用例选择重跑）**：被测仓有新 commit 后，系统做
  符号级 diff 与影响面三分类（可自动跑/无自动化/冲突待人工），经映射翻译成
  `-only-testing` 选择集，只跑受影响的存量用例；空选择硬失败，**绝不静默退化为全量**。

**系统边界（演示诚信底线）**：系统内不生成 Swift 代码、不直接写被测仓；测试代码生成、
演示分支创建与合入都是人工步骤（§5、§6 给出可照跑的 runbook）。模拟器覆盖不到的三层
（后台音频/签名/真机）永远如实标注为未覆盖层，不夸大为真机验证。

### 验证层级声明（先建立预期）

| 层级 | 跑什么 | 何时跑 |
|---|---|---|
| L1 hermetic 自动化 | `pytest` 全量（1248 例）、`verify_s0.sh` 24 门禁、import-lint；不起模拟器/端口/外部服务 | 每次改动后，全本地可复现 |
| L2 模拟器真机链 | xcode profile 下真实 `xcodebuild` + simctl + xcresulttool（本说明书 §7/§8） | 演示前手动跑，依赖 macOS + Xcode |
| L3 仅生产/真机可验 | 后台音频、代码签名、真机进程生命周期 | 本地**永不**声称已验，见 docs/03 §3.6 手动 runbook |

## 1. 仓库布局与角色

需要两个仓库（系统不拷贝被测代码，只通过文件系统/git 只读对接）：

```
~/Documents/Code/
├── ai-testpilot/            # 本仓（智能体系统）
```

| Docker Desktop（仅真实模型/向量链路需要） | — | `docker ps` |

### 2.2 安装 Python 依赖

```bash
cd ai-testpilot/subsystems
uv sync            # 创建 .venv，editable 安装四个包
```

- 默认 PyPI TLS 失败时（本机环境备注）：
  `UV_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple uv sync`（只作环境变量，不写进仓库）。
- 若曾在包目录未建全时 sync 过，import 报 ModuleNotFoundError 空壳：
  `uv sync --reinstall-package testpilot-core --reinstall-package testpilot-adapters \
    --reinstall-package testpilot-orchestrator --reinstall-package testpilot-workers`
- **tree-sitter 可选 extra（verify_s0 A2 必装，每次 `uv sync` 后都要重装）**：
  tree-sitter 是 adapters 包的 optional dependency group，**不在默认依赖里，`uv sync`
  不会装、而且每次重跑 `uv sync` 都会把它从 .venv 移除**（环境被对齐回 lockfile）。
  缺它时 A2 恰好 8 个 `tests/test_tree_sitter_chunker.py` 用例报
  `AdapterUnavailableError: tree-sitter/tree-sitter-swift 未安装`。安装命令（README E6 同源）：

  ```bash
  VIRTUAL_ENV=$PWD/.venv uv pip install -e 'packages/adapters[tree-sitter]'
  # 验证：uv run python -c "from testpilot_adapters.tree_sitter_chunker import tree_sitter_available; print(tree_sitter_available())"
  # 应输出 True
  ```

  注意上面的 `--reinstall-package` 命令**不会**装回 optional extra，两件事不要混为一谈；
  日常顺序固定为「先 `uv sync`，再装 tree-sitter extra」。

### 2.5 基线自检（L1，必做；约 20 秒 + verify_s0 数分钟）

```bash

uv run python scripts/import_lint.py          # 预期：OK，core 零越界导入
```

- **A2 FAIL 且 8 个 `test_tree_sitter_chunker` 全红**：不是代码回归，是 tree-sitter
  optional extra 缺失（典型触发：刚跑过 `uv sync`），按 §2.2 末尾的


## 3. 四个 profile 怎么选

所有 worker 都用环境变量 `TESTPILOT_PROFILE` 选 profile，**值必须是 yaml 的完整路径**
（传 profile 名字会报「profile 配置不存在」）：

| profile | 用途 | runner / environment / logs | 数据目录 | 外部依赖 |
|---|---|---|---|---|
| `offline-demo`（默认） | 纯离线 hermetic 演示、CI | recorded / stub / stub | `store/offline-demo` | 无 |
| `ios-local-poc` | 真实语料库的录制型离线链路（不跑 xcodebuild） | recorded / stub / stub | `store/ios-local-poc` | ollama + chroma |
| `ios-local-poc-xcode` | **L2 真机链：真实 xcodebuild 执行（模拟器目的地）** | xcode / ios-simulator / os-log | `store/ios-local-poc-xcode` | ollama + chroma + Xcode + 模拟器 |
| `ios-local-poc-device` | **物理真机链（切片一）：xcodebuild 真机目的地 + devicectl 盘点 + 两步法设备日志** | xcode(target=device) / ios-device / os-log-device | `store/ios-local-poc-device` | ollama + chroma + Xcode + 已配对真机 |

便捷写法（后续命令统一用这个变量）：

```bash
export XCODE_PROFILE=$PWD/config/profiles/ios-local-poc-xcode.yaml
export DEVICE_PROFILE=$PWD/config/profiles/ios-local-poc-device.yaml
export IOS_PROFILE=$PWD/config/profiles/ios-local-poc.yaml
```

xcode profile 关键装配（改机型时编辑 yaml，不要把个人 UDID 写进文档/命令）：

- `runner.settings`：workspace=`AlarmKitSpike/AlarmKitSpike.xcworkspace`、scheme=`AlarmKitSpike`、
  xcresult 工作目录与产物根都在 gitignored 的 `store/ios-local-poc-xcode/` 下；
- `environment.settings.devices`：模拟器清单，**空清单在容器构造期就报错**（fail-closed）；
- `logs.settings.udid` 必须与设备清单 udid 显式一致，拒绝 booted 隐式目标。
- 查自己机器上的模拟器 UDID：`xcrun simctl list devices available | grep iPhone`，
  替换 yaml 中两处 udid（devices 与 logs）。

device profile 真机专用约定（详见 docs/03 §3.7、docs/14 附录 A）：

- UDID 必须是**硬件 UDID**（`devicectl list devices --json-output -` 的
  `properties.hardware.udid`），不是顶层 CoreDevice UUID；真机清单空/未连接时
  health_check 回 False、reset 永远被策略拒绝（平台不自动化任何抹机）；
- 日志默认 `collect_mode: manual`：worker 无 TTY 不代跑提权 collect。查询时若归档
  缺失，平台报错里携带可照跑的 `/usr/bin/log collect --device-udid …` 命令，人工
  采集到指定 `.logarchive` 后重跑即可（需要提权时人工自行加 sudo）；确认本机免提权
  才可改 `auto`（`use_sudo: true` 走 `sudo -n`，凭据未缓存立即失败不挂密码提示）；
- 上线前先跑手动探针（**不是自动门禁**）：
  `.venv/bin/python scripts/device_chain_probe.py`——首跑 exit 2 打印人工采集命令
  属设计内待办，同 `--run-id` 重跑接上 `log show`，报告在 `out/eval/device-chain-probe.*`。

```
【场景 A】
2.环境自检 → 5.1 建演示分支(人工,一次性)
          → 5.2 知识入库 ingest
          → 5.3 S2 用例生成链（需求骨架→测试点→oracle→人审→回写→关系）

          → 6.3 impact-rerun --dry-run 看影响三分类与选择集
          → 6.4 正式 impact-rerun 入队（幂等/配额）→ 6.5 run-once 执行 → 6.6 结果解读
```

`testpilot-ingest`、`testpilot-ingest-cases`、`testpilot-extract-requirements`、
`testpilot-generate-testpoints`、`testpilot-mine-oracles`、`testpilot-dispatch-outbox`、
`testpilot-promote-fewshot`、`testpilot-build-relations`、`testpilot-runner`、`testpilot-eval`、
`testpilot-badcase`、`testpilot-impact`、以及本闭环新增的
**`testpilot-export-cases`（E1）/ `testpilot-scan-automation`（E3）/ `testpilot-impact-rerun`（E4）**。

退出码契约（三个新 CLI 与 runner 一致）：**0 成功；2 硬失败（参数/守卫/外部依赖错误，
消息可操作，不产有效副作用）；3 仅 scan-automation 使用——map 已产出但有人审警告**。

## 5. 场景 A 分步操作

### 5.1 一次性：在被测仓创建长期演示分支（人工，另一个仓）

完整可复制命令见 [docs/12 附录 B](12-用例导出与Xcode执行闭环方案.md)。要点：

```bash
cd ~/Documents/Code/app-calendar-alarm
git checkout alarmkit-spike
git checkout -b demo/agent-generated-tests
# 在该分支 README.md 顶部加一行声明：「演示分支，永不合入主线，仅承载 Agent 生成测试」
git add README.md && git commit -m "chore: declare long-lived demo branch"
# 之后人工演示时把工作区留在这个分支上，testpilot 只只读扫描，不切分支不写 git
```

### 5.2 知识入库（S1.1，文档 + Swift 符号切块）

```bash
cd ~/Documents/Code/ai-testpilot/subsystems
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-ingest --full
# 预期：输出 created/updated/unchanged 盘点；重复跑幂等（unchanged），批次留痕 ingestion_runs
# 单篇坏文件进 dead_letters 不阻断整批；partial 时进程非零退出，不要把带死信的批次当成功
```

重置演示库（生成物，不入库，可随时删）：`rm -rf store/ios-local-poc-xcode`。

### 5.3 S2 用例生成链（需求 → 测试点/用例/oracle，严格按序）

> profile 前置（ios-local-poc-xcode 已内置，2026-11-13 修复）：`requirements` 装配
> fs-reqs、`cases` 装配 fs-cases，两者都用**单文件 root** 经 `${REPO_PATH}` 直指语料仓
> `docs/V1需求文档-强提醒闹钟.md` / `docs/V1测试用例文档.md`（不扫 docs/ 全目录，
> 市场调研等同级 md 不进抽取批次）；`case_repo` 装配 markdown-fs，写根默认
> `store/ios-local-poc-xcode/case-writeback/`，绝不写语料仓。若报
> 「容器未装配 requirements/cases 适配器」，先确认 profile 含这三段配置；
> 若报「需求/用例文档根目录不存在」，确认 `TESTPILOT_REPO_PATH` 或默认
> `../../app-calendar-alarm` 可达。ollama 不可用时需求链接自动降级
> （`link_degraded_docs=1`），确定性骨架照出、exit 0。

```bash
# ① 需求骨架抽取（读入库的需求 Markdown，产 requirement_skeletons，FR/NFR/AC 白名单链接）
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-extract-requirements
# 首次跑预期（V1.2 真档实测）：docs_seen=1、features_active=33、features_cancelled=1
# （FR-7 删除线）、rules=9、acceptance_criteria=7、parse_dead_letters=0；
# 再跑一次应 skipped_unchanged=1（content_hash 幂等）

# ②（可选）已有人工用例 Markdown 时入库；没有可跳过，oracle 的「现有断言源」只是为空
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-ingest-cases
# V1.2 真档实测：cases_upserted=52、cancelled=1（TC-B6）、oracle_missing=1（TC-A4）、
# parse_dead_letters=0；叙事体模块 A 与表格体模块 B–F 混合格式全部可解析

# ③ 测试点生成（前置①；确定性脊柱 + 模型补点，幻觉行进 dead_letters 并在报告单列）
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-generate-testpoints

# ④ oracle 四源挖掘（草稿恒为 pending，不碰正式用例库，等人审）
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-mine-oracles
```

**人审回写（HITL，无自动审批，bootstrap 也不提供自动放行）**：

```bash
# 方式一（推荐演示）：起 Web 审批页
bash scripts/build_web.sh                 # npm 不可用时 NPM_REGISTRY=https://registry.npmmirror.com bash scripts/build_web.sh
uv run uvicorn testpilot_orchestrator.app:app --port 8765
# 浏览器开 http://127.0.0.1:8765/approvals ，逐草稿采纳/修改/拒绝（评审人+理由必填）
# 若 404：uvicorn 是旧代码，重启即可（SpaStaticFiles 干净 URL 回退，见 §8 故障排查表）

# 方式二：hermetic 探针看完整审批机制（不起端口，不碰正式库）
uv run python scripts/approval_probe.py

# 审批结论落 outbox 后派发到写根（xcode profile 默认 external_write_enabled=true）
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-dispatch-outbox
# kill switch 开启时全部 blocked 且不烧重试次数；写策略经 /api/approvals/write-policy 查看
# 落地位置：store/ios-local-poc-xcode/case-writeback/<doc>/<case_id>.md + _manifest.json
# （profile 未装配 case_repo 时只记 adapter_not_configured、pending 保留不丢不烧重试）
```

```bash
# ⑤ 用例 ↔ 需求/符号关系派生（场景 B 影响面追溯的关系数据来源；空用例库 exit 2）
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-build-relations --full
```

### 5.4 E1：导出结构化用例集（case-export-v1）

```bash
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-export-cases
# 预期 stdout 打印导出路径（默认 <data_dir>/exports/case-set-<UTC时间>-<hash8>.json）、
# content_hash、cases/excluded/exploratory 分区计数；exit 0
```

契约要点（详见 docs/12 §3.1）：cancelled 用例只进 excluded 不进 cases；同库两次导出
内容 hash 一致（时间戳不参与 hash）；**空库导出 exit 2 不产空壳文件**。
版本四元组（数据/模型/prompt/参数）可用 `--data-version/--model-version/...` 显式标注。
`generation_convention` 同时携带单元/UI 两个 target 名（`--test-target`/`--ui-test-target`
可覆盖，默认 AlarmKitSpikeTests / AlarmKitSpikeUITests）；外部 Agent 按用例 oracle 类型
分流，导出载荷本身不新增字段。

### 5.5 外部 Agent 生成 Xcode 测试（人工，在被测仓）

把上一步的 JSON 用例集交给 Claude 等外部 Agent，prompt 全文照抄

## 6. 场景 B 分步操作（commit diff → 影响面选择重跑）

### 6.1 前置：被测仓有新 commit，且 map 与新 HEAD 对齐

```bash
cd ~/Documents/Code/app-calendar-alarm
git fetch && git log --oneline -3                 # 确认新 commit；演示分支人工 rebase/merge 后同理
HEAD_SHA=$(git rev-parse HEAD)
BASE_SHA=$(git rev-parse HEAD~1)
```

### 6.2 重扫 map（鲜度以 head_commit 为锚）

```bash
cd ~/Documents/Code/ai-testpilot/subsystems
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-scan-automation
# map.head_commit 必须等于即将使用的 --head；不一致会被鲜度守卫直接拒绝（见 6.7）
```

### 6.3 dry-run：只看影响面与选择集，不写任何账本

```bash
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-impact-rerun \
  --base "$BASE_SHA" --head "$HEAD_SHA" --dry-run
# 预期 JSON 关键字段：
#   classification_counts：runnable / no_automation / conflict_update 三分类计数
#   selection.only_testing_ids：翻译成 -only-testing 的 OID（已过形态校验、去重）
#   selection.unmapped_runnable_case_ids：可自动化但没映射的用例（响亮上报，不静默丢）
#   selection.idempotency_key：impact:<head短sha12>:<选择集sha256前16>
#   submission: null（dry-run 零写入）
```

### 6.4 正式提交（幂等 + 按 head 分桶的重跑配额）

```bash
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-impact-rerun \
  --base "$BASE_SHA" --head "$HEAD_SHA"
# 预期：submission.run_id=run-xxxxxxxx，replayed=false，status=queued

# 同参数再跑一次：返回同一 run_id 且 replayed=true，jobs 零增生、配额不双扣
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-impact-rerun \
  --base "$BASE_SHA" --head "$HEAD_SHA"
```

配额：每次真实提交占 `rerun_budget` 一行，桶键 `impact:<head短sha>`（默认每日 20，
profile `limits.daily_rerun_quota` 可调）；重放命中幂等账本不扣配额。

### 6.5 执行与查看（同场景 A 的 runner）

```bash
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-runner run-once
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-runner list
TESTPILOT_PROFILE=$XCODE_PROFILE uv run testpilot-runner show --run-id run-xxxxxxxx
```

### 6.6 三分类怎么解读

| 分类 | 含义 | 系统动作 |
|---|---|---|
| runnable | 影响到的用例在 map 中有有效绑定 | 翻译成 OID 进选择集，可自动执行 |
| no_automation | 探索性用例等无自动化形态 | 只上报 ID，不进选择集 |
| conflict_update | 符号 removed/签名变化等冲突 | 只上报，等人审更新用例/映射 |
| runnable 但未映射 | 该有自动化却缺绑定 | `unmapped_runnable_case_ids` 显式列出并给补映射提示 |

### 6.7 守卫行为（全部实测，exit 2，零入队）

| 触发方式 | 预期报错要点 |
|---|---|
| map 停在旧 head（`--head` 传父提交） | 「automation-map 已过期…禁止拿旧映射跑新代码」 |
| map 文件缺失（或 `--map` 指错路径） | 「automation-map 不存在…请先运行 testpilot-scan-automation」 |
| 影响集为空/全部未映射 | 「选择集为空…禁止静默退化为全量执行」，附未映射 TC 清单 |
| base/head 不可达（bad object） | git diff 失败收口 exit 2（不出 traceback） |
| map schema 版本不符/JSON 损坏 | 版本或损坏提示，拒绝使用 |
