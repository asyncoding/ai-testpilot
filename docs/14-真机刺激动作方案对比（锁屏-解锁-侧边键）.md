# 14 - 真机刺激动作方案对比（锁屏 / 解锁 / 侧边物理键）

> 状态：**方案评审稿（2026-11-13）**，只做论证与选型，不含代码变更。
> 范围严格限定三个设备级刺激动作：**锁屏、解锁、侧边物理键（音量加/减、电源/侧键）**。
> 本文所有「本机已证」结论均可在当前机器（Xcode 27.0 / 27A266a）照命令复验；
> 凡标 **〔待真机 spike〕** 的，均未实测，不得在后续设计中当作既成能力引用。
> 关联：docs/12（用例导出与 Xcode 执行闭环）、docs/03 §3.6（真机执行取证 runbook）、
> 三层断言模型讨论（A 机器可判 / B 真机机器可判 / C 感官人工金标准）。

## 1. 问题边界与先置结论

### 1.1 为什么只需要这三个动词

AlarmKitSpike 的用例中，App 内 UI 流程（按钮、列表、设置项、弹窗、通知点按）由
TestCase / UITestCase（XCUITest）覆盖即可，这部分能力官方 API 完备、CI 可跑。
真正的能力缺口在**设备级刺激**：

| 刺激 | 典型被测行为（AlarmKitSpike） | 为什么 App 内测试做不到 |
|---|---|---|
| 锁屏 | 锁屏后闹钟是否按预期响铃/横幅/持续；锁屏态通知交互 | XCUITest 没有锁屏 API（见 §4.4 头文件取证） |
| 解锁 | 锁屏响铃后解锁进入 App，状态是否正确接续 | 解锁动作发生在 SpringBoard/系统 PIN 界面，不在 App 进程内 |
| 侧边物理键 | 响铃中按音量键/侧键：静音、停闹、贪睡等系统级行为 | 物理 HID 事件不经 App 视图树，UI 测试无法产生真实按键事件 |

**注意两个语义不能混为一谈**：

1. **锁屏状态语义**（lockstate：locked / unlocked）——多数用例要的是这个；
2. **真实 HID 按键语义**（侧键被物理按下的事件链）——只有少数用例（如"响铃中按侧键
   停闹"）需要。软件锁屏（WDA `lock`）能制造状态①，但不保证等价于硬件按键触发的
   完整事件链②。选型时按用例实际断言区分，不要用一个动作冒充另一个。

### 1.2 先置结论（TL;DR）

1. **Device Hub 不能被脚本直接驱动**：它没有 AppleScript 字典（sdef）、没有 CLI，
   只有一个未公开动作格式的 `devices://` URL scheme；它本身是 CoreDevice 私有框架的
   GUI 壳。「用 AppleScript 操作 Device Hub」只能退化为** macOS 辅助功能 API 模拟点
   菜单**，脆且不适合无人值守 CI（§4.2）。
2. **官方 CLI `devicectl` 明确没有 lock/unlock 动词**（§4.3 本机全量子命令取证）。
3. **包内 XCUITest 官方只覆盖 Home/音量键（真机限定），没有锁屏键**；解锁可借助
   SpringBoard 滑动+输密码的社区成熟技法（非官方 API 承诺）（§4.4）。
4. **三动词全覆盖、且有公开文档的现成路线是 Appium + WebDriverAgent（WDA）**：
   `mobile: lock/unlock/isLocked` 在 driver 官方文档中列明；代价是引入 Node/Appium/
   WDA 签名一整套重依赖（§4.5）。
5. **轻量替代 go-ios** 原生是否有 lock 动词本机未装、未证实，标〔待真机 spike〕；
   iOS 17+ 必须先建 CoreDevice tunnel（`sudo ios tunnel start`）（§4.6）。
   **2026-11-13 注记**：Web 资料级调研已收窄结论——文档面无原生动词，三动词仍依赖
   runwda/WDA（附录 A，E-B 级；本机 `ios --help` 盘点 S-4 仍是最终封口手段）。
6. **直连 CoreDevice 私有框架**能力上最对口（`action.lockstate` + 私有 HID 栈都在），
   但私有 API 随系统版本失效的风险最高，Demo 不建议自研（§4.8）。
7. 推荐路线：**先人工混合流（HITL）+ Device Hub 手动兜底 → 真机 spike 验证
   XCUITest/WDA 两条路线 → 以 DeviceControlPort 端口+能力标签收口，recorded/stub
   先行**，schema v15 零 DDL（§7）。

### 2.2 公开资料佐证（非本机实测）

- WWDC26 Session 260《Get the most out of Device Hub》：Device Hub 随 Xcode 27 发布，

  支持 `--json-output` 供脚本/CI 使用；会议未介绍 AppleScript 或 URL scheme 自动化，

- Apple 支持文档《Manage Device Hub access on your iPhone》：iPhone 端可由用户
  管控 Device Hub 访问授权——接入本身需要设备侧信任，不是纯 Mac 侧行为。

## 4. 九个候选方案逐一评估

### 4.1 方案①：Device Hub GUI 人工操作（现状基线）

- **能力**：Xcode 27 → Open Developer Tool → Device Hub，设备画面实时镜像，
  Control 菜单含 Lock 等硬件控件（Apple 文档对模拟器明确写了 Control→Lock；
  **真机是否展示同菜单、行为是否一致 = 待 spike E8**）。
- **优点**：零开发、零新依赖；Apple 官方 GUI，稳定性高于一切逆向路线；演示时可视、
  可录屏，正好承接 C 层（感官）人工金标准。
- **硬伤**：纯人工，无法进自动化流水线；E4 证明 **Mac 一锁屏 Device Hub 就暂停设备
  交互**，无人值守机不能锁屏；E2/E3 证明它没有任何官方脚本面。
- **定位**：演示兜底 + spike 期的人工参照实现，不作为自动化基座。

### 4.2 方案②：macOS 辅助功能 API / AppleScript 驱动 Device Hub（回答"Action Script"问题）

用户问的「能否通过 Action Script 之类操作」，取证结论分两层：

1. **原生 AppleScript 不可行**：E2——Device Hub 没有 sdef 字典，AppleScript 无法向它
   发语义事件（`tell application "Device Hub" to ...` 没有任何可调用术语）。
2. **通用 GUI 脚本理论可行**：通过 System Events 的 Accessibility（AX）API 按菜单名/
   按钮名模拟点击（AppleScript `tell application "System Events"` 或 Python
   `pyautogui`/`atomacos`）。但这是**在 Mac 上模拟鼠标点 GUI**，不是设备自动化接口：
   - **脆**：控件层级、菜单文案、窗口布局随 Xcode 小版本变，无任何稳定性承诺；
   - **授权重**：运行进程需「辅助功能」TCC 授权，CI runner 上要人工授予且随重置失效；
   - **环境苛刻**：必须有登录态 GUI 会话、窗口可前台、Mac 不得锁屏（E4）；
   - **失败模式差**：菜单没找到时点到别的控件，难 fail-closed，容易假绿；
   - `devices://` scheme（E1）角色仅 Viewer 且无公开动作 URL 格式，不能当捷径。
- **结论**：只适合做一次性桌面小工具，**不进测试平台主链路**。

> **2026-11-13 E-A 加注记（模拟器实测，详见附录 B）**：本节"理论可行"已被本机实验
> 收窄为"读路径可行、设备动词的合成触发被隔离"。AX 原生 API 可完整枚举菜单/工具条
> （含语言无关快捷键元数据与 SF Symbol 标识符），但 AXPress、HID 层 CGEvent 鼠标/键盘、
> System Events 七条合成通道对设备转发动词全部"调用成功、设备无动作"；同一进程本地
> 控件（Start、Capture Keyboard）对同样的合成输入真实响应，且 simctl 直连设备正常——
> 隔离墙在 Device Hub 的设备 HID 转发路径，不在权限/坐标/设备健康。**真机未验**，
> 设备重连后先用 `device_hub_ax_probe.swift` 复跑再定方案排序。

> **2026-11-13 晚 E-A 真机加注记（iPhone 16 Pro / iOS 27.2，详见附录 B.4）**：真机复跑
> **部分推翻**模拟器结论，隔离墙比 E20 表述的更窄——**AX 语义动作通道在真机上有效**：
> 工具条 AXPress Home 两次可重复地把设置页真实退回主屏（devicectl 前后截图为证），
> AXPress Rotate Left 真实把 Safari 从竖屏 1206×2622 转成横屏 2622×1206 并已复原；
> 而 **HID/CGEvent 合成点击通道在真机上仍然全惰性**（Home、Rotate 两动词均无设备侧效果）。
> 即墙只挡"伪造硬件归因的 HID 事件"，不挡 AXUIElementPerformAction 语义动作。
> 边界：真机 Controls 菜单全程灰显，仅工具条三动词（Home/Screenshot/Rotate）可达，
> Lock/Siri/App Switcher/Action Button/Record 五个菜单动词尚不可触达；且要求 Mac 解锁、
> DH 设备会话窗口已物化。DH 路线从"只读+HITL"升级为**真机 AX 语义刺激的 DeviceControlPort
> 候选**，但能力圈暂限三动词且带 GUI 会话前置。

### 4.3 方案③：devicectl 官方 CLI

- E6 全量取证：device 子命令为 appResize/capture/copy/info/install/motion/
  notification/orientation/pairings/pasteboard/process/profile/reboot/rename/settings/
  simulate/sysdiagnose/uninstall；`simulate` 只做 biometrics/location/statusBar。
- **没有 lock、unlock，也没有按键/HID 子命令**。WWDC26 把它定位为 Device Hub 的
  自动化对等物，但设备控制面就开放到这里。
- **定位**：继续承担它已经在做的事——配对、装 App、截图、sysdiagnose、信息查询
  （刺激前后的状态取证可以用 `devicectl device info details` 做旁证），**不指望它
  输出三动词**。

### 4.4 方案④：App 包内 XCUITest（与现有 TestCase/UITestCase 同栈）

- **音量键**：E7 头文件证明 `XCUIDeviceButton.volumeUp/volumeDown` 存在且为真机可用、
  模拟器不可用——这是**官方 API**，且 xcodebuild 已在我们现有执行管线内，接入成本最低。
- **Home 键**：同枚举 `.home`，真机可用。
- **锁屏**：枚举里**根本没有 lock case**，无法官方实现。
- **解锁**：没有官方解锁 API；社区成熟技法是在测试中拉起
  `XCUIApplication(bundleIdentifier: "com.apple.springboard")`，在锁屏界面做滑动
  手势 + 点按密码盘。WDA 的 unlock 底层也是这套。风险：密码盘布局随 iOS 版本变、
  测试 bundle 要持有设备密码（密钥管理问题）、属于跨进程操作 SpringBoard 的
  非显式承诺面，需 spike 固化并 pin 住 iOS 版本。
- **结论**：覆盖「音量键 + 解锁（社区技法）」，锁屏仍需外部方案；作为**首选低成本
  切片**，但先写红证探针验证它在 AlarmKitSpike 真机上真的抓得住行为，不信单次全绿。

### 4.5 方案⑤：Appium + WebDriverAgent（三动词覆盖最完整的现成路线）

- **能力**：driver 官方文档有 `mobile: lock/unlock/isLocked`；解锁带密码设备需把
  PIN 配给 WDA；`mobile: pressButton` 支持音量/Home 类按钮（本机未装，实测留 spike）。
- **机理**：WDA 是跑在真机上的 XCTest runner，借助 Apple 私有/半私有接口实现锁屏
  等动作——本质是把方案⑧的私有 API 风险**外包给活跃社区维护**，Appium 每个 Xcode/iOS
  版本跟进兼容，这是它相对自研 CoreDevice 的最大价值。
- **成本**：Node 运行时 + Appium server + WDA 工程签名（需开发者证书、每 7 天/企业
  签名续签问题）+ session 生命周期管理；与现有纯 Python + xcodebuild 栈异构。
- **CI**：可无人值守，session 可远程化；但节点维护成本明显高于现栈。
- **结论**：若 spike 证明 XCUITest 路线盖不住锁屏（大概率），**WDA 是锁屏动作的
  首选落地适配器**；可以只把 WDA 当窄依赖（仅 lock/unlock 两个端点），不全面迁栈。

### 4.6 方案⑥：go-ios（轻量第三方）

- 纯 Go 单二进制，无需 Xcode 跑测试 bundle 即可做安装、日志、截图、WDA 拉起等，
  体量比 Appium 小一个数量级。
- **iOS 17+ 前置**：必须 `sudo ios tunnel start` 建 CoreDevice 隧道（涉及 root 权限
  与后台常驻进程，CI 镜像要显式管理生命周期）。
- **关键缺口**：go-ios 原生是否有 lock/unlock 动词、HID 子命令能做到什么程度，
  权威文档未证实（E9 本机未装）。已证实的只有 `runwda`——即它也可以走 WDA 路线，
  那与方案⑤能力同源，只是换了更轻的客户端。
- **结论**：〔待真机 spike〕`ios --help` 全量子命令盘点后再定；若原生动词齐备可作
  Appium 的轻量替代，若只有 runwda，则价值限于"轻量 WDA 启动器"。
- **2026-11-13 Web 调研注记（E-B 级，本机仍未安装，详见附录 A）**：多版本官方 README
  镜像（v1.0.207–v1.0.214）交叉核对，CLI 清单**无原生 lock/unlock/lockscreen 动词**，
  也未见免 WDA 的原生 touch/HID 注入；三动词实际路径仍是 `runwda` 拉起 WDA 后说 WDA
  协议（与方案⑤同源）。原生 lock 疑问由 🔒/❓ 收窄为"文档级否定，待 S-4 本机封口"。

### 4.7 方案⑦：MDM DeviceLockCommand

- Apple 企业管理协议的 DeviceLock 是官方能力，但：需要设备被监督（supervised，
  DEP/ABM 注册）、要有 MDM 服务器与 APNs 通道；**方向单向——只能锁，不能解锁**
  （解锁只能用户输密码）；完全没有按键能力。
- **结论**：企业域产品才可考虑，POC 演示设备不满足前置，排除。

### 4.8 方案⑧：直连 CoreDevice 私有框架

- E5 证明能力最对口：`com.apple.coredevice.action.lockstate` + LockStateProtocol
  覆盖锁状态，HIDXPCService / UniversalHIDButton 覆盖真实按键 HID——三动词包括
  真实侧键 HID 事件理论上都在这一层。
- **风险**：私有框架、无头文件、无稳定承诺，Xcode/iOS 大版本升级即可能失效；
  逆向成本高，且与我们"证据驱动、fail-closed"的工程纪律冲突——失效模式是不可预期的
  协议拒绝，不是清晰的能力缺失。
- **结论**：Demo 阶段**不自研**；知道 WDA/go-ios 底层就在这一层即可，私有 API 风险
  由社区上游吸收。

### 4.9 方案⑨：人工刺激混合流（HITL 编排）

- 平台编排执行到刺激步骤时**挂起 run**，在 Web/审批页弹出指引（"请锁屏并保持 10 秒"），
  人工在 Device Hub 或真机上操作，点击"已完成"后恢复；期间 os_log 采集窗不中断，
  A 层断言（日志因果链、状态快照）照常机器判定，人只负责注入刺激、C 层感官金标准。
- **优点**：零新依赖、零逆向风险、今天就能做；与现有 HITL 审批哲学一致；
  每一步人工动作带时间戳留痕，证据链完整。
- **代价**：非全自动，演示与人工 QA 流程可用，不能承诺无人值守。
- **定位**：**第一阶段落地形态**，也是所有自动方案失败时的 fail-closed 兜底
  （能力缺失 → 挂起人工，而不是静默跳过）。

## 5. 多维对比与失败模式

| 维度 | ②AX 脚本 | ④XCUITest | ⑤Appium/WDA | ⑥go-ios | ⑧CoreDevice 自研 | ⑨人工混合 |
|---|---|---|---|---|---|---|
| 三动词覆盖 | 全（模拟点击） | 音量✅解锁🟡锁屏❌ | 最完整 | 待证 | 理论全覆盖 | 全 |
| 接口稳定性 | 极差（GUI 布局） | 高（官方）/中（SpringBoard） | 中高（社区跟进） | 中 | 极低（私有） | 不适用 |
| 新增依赖 | 无 | 无（同栈） | Node+Appium+WDA 签名 | 单二进制+tunnel | 自研逆向 | 无 |
| CI 无人值守 | 需 GUI 会话+TCC | ✅ 已在管线 | ✅ 重节点 | ✅ root 隧道 | ✅ 高维护 | ❌ |
| 失败可观测性 | 差（误点难查） | 好（xcode 产物链） | 好（WDA 日志/session） | 中 | 差 | 好（人工留痕） |
| fail-closed 难度 | 高 | 低 | 低 | 中 | 高 | 天然 |
| 与现栈契合 | 低 | **最高** | 中（异构但可窄接） | 中高 | 低 | 高（HITL 同构） |

选型纪律（呼应仓库工程纪律）：

- **能力缺失必须响亮失败**：适配器声明不了某刺激能力时，worker 直接报错退出，
  严禁静默跳过（与"未映射用例大声上报"同口径）。
- **红证先行**：每个自动刺激适配器配对照测试，必要时临时回退实现看它变红，
  警惕"动作报成功但设备没动"的假绿；刺激前后各取一次 `devicectl ... info` /
  截图 / os_log 标记作为因果旁证。
- **环境差异写清**：模拟器暴露不了锁屏/物理键（E7 标注 simulator unavailable），
  文档必须写明"哪层模拟器验、哪层真机验、哪层只能人工/生产验"。

## 6. 对现有审批流（/approvals）的影响：零影响

讨论中的真机刺激支持**不改变** `http://127.0.0.1:8765/approvals` 的任何行为：

1. 审批页读写的是 store 中既有的待审批草稿/outbox（schema v15 表结构不动），
   DeviceControlPort 是执行阶段的**下游新端口**，不进入审批数据模型；
2. HITL 语义不变——系统不存在任何自动审批，刺激能力是审批通过之后、执行 run 期间
   才发生的事；
3. 新刺激的证据（前后状态、日志窗、人工操作时间戳）挂在既有 run 的事件/制品链上，
   不新增表、不改 API 契约；
4. 方案讨论与 spike 阶段不动一行业务代码，审批流连部署都不受影响。
   唯一新增的接触面是未来人工混合流可能在**执行详情页**（不是审批页）增加挂起/恢复
   交互，且那是独立切片、独立评审。

### 7.2 DeviceControlPort 拟议形状（设计稿，非实现）

放在 `testpilot_core/ports.py`，与 EnvironmentPort 的租约体系对齐——刺激只允许作用于
**已租约的 env_id**，无租约不裸操作：

```python
class DeviceStimulus(Enum):
    LOCK = "lock"                    # 锁屏状态语义
    UNLOCK = "unlock"
    VOLUME_UP = "volume_up"
    VOLUME_DOWN = "volume_down"
    SIDE_BUTTON = "side_button"      # 真实 HID 语义，多数适配器声明不了
    HOME = "home"

@runtime_checkable
class DeviceControlPort(Protocol):
    def capabilities(self) -> set[DeviceStimulus]:
        """静态能力声明；worker 预检，不支持即响亮失败，不允许运行时静默降级。"""

    async def apply(self, stimulus: DeviceStimulus, *, env_id: str) -> StimulusResult:
        """对租约环境施加刺激；StimulusResult 含前后状态旁证（devicectl/截图 URN/
        os_log 时间窗）与适配器动作版本戳，供归因与回放。"""
```

收口约束：

- **schema v15 零 DDL**：刺激记录走既有执行事件契约 + ArtifactStorePort 制品 URN，
  不加表；
- 适配器三档：`stub`（拒绝一切，hostless 测试默认）、`recorded`（回放录制序列，
  离线演示与测试）、真机实现（XCUITest 桥接或 WDA，按 spike 选型）；
- profile 中以 adapter ref + 能力标签装配，未知 type 装配期拒绝（沿用 factory 现有
  守卫口径）；
- 进程出口仍只有 SubprocessProcessExecutor 一个（argv 数组），WDA/go-ios 一律经它调用，
  结构化日志固定 subsystem 名，日志抓取谓词写进 docs/03 runbook。

### A.2 工具事实（E-B）

- 定位：纯 Go 跨平台（macOS/Linux/Windows）iOS 真机自动化 CLI，活跃维护——2026 年仍在
  发版（观察到 v1.0.213/v1.0.214），分发渠道含 npm 包 `go-ios` / `go-ios-canary` 与
  GitHub release 二进制；
- **iOS 17+ 硬前置**：先 `sudo ios tunnel start` 建 CoreDevice TUN 隧道并常驻，
  配套 `ios tunnel ls` / `ios tunnel stopagent` 管理生命周期（多源一致，E-B）。
  两个冲突点：① sudo 与本仓 worker 无 TTY 约束冲突，只能人工起隧道（同 manual collect
  范式）或外置为机器级服务；② 常驻守护引入进程生命周期/重连对账问题；
- 文档面 CLI 能力清单（按族归并）：

| 能力族 | 动词（README 列名） | 备注 |
|---|---|---|
| 设备/配对 | `list` `info` `apps` `pair` `tunnel` `lockdown get` | `info` 的 "Lockdown getValues" 是 **lockdownd 守护服务查询，与锁屏无关** |
| App 管理 | `install` `launch` `kill` | 与 devicectl 能力重叠 |
| 取证 | `screenshot`（含 `--stream`）`syslog`（`--parse`）`crashlog` | 免 Xcode 的轻量取证是其真实差异化 |
| 测试 | `runtest` `runxctest` `runwda` | WDA 管理是 UI 自动化的实际入口 |
| 辅助功能 | `ax`（accessibility inspector，**只读**）`assistivetouch`（系统开关 enable/disable/toggle/get） | 无文档证据表明可注入点击/手势 |

### A.3 三动词专项结论（核心调研问题）

1. **锁屏 lock**：当前权威文档的 CLI 清单**没有原生 lock/unlock/lockscreen 动词**
   （多版本 README + 两轮定向检索交叉一致，E-B；检索同时确认 `sendnote`/`pressButton`
   等猜测名也无索引命中）。矩阵 ⑥ 原生 lock 由 🔒/❓ 收窄为**文档级否定**，
   仅保留 S-4 本机封口；
2. **解锁 / 触摸 HID**：无免 WDA 的原生 touch/swipe/HID 注入证据；`ax` 只读、
   `assistivetouch` 只切系统设置。真实 UI 操作路径是 `runwda` 拉起 WebDriverAgent 后
   说 WDA HTTP（`/wda/lock`、`/wda/unlock`、`/wda/locked`），Appium 的
   `mobile: lock/unlock/isLocked` 正是这层协议的 driver 封装——**与方案⑤同栈，
   只是省掉 Appium server，自己实现 WDA 客户端**；
3. **音量/侧键**：go-ios 原生面未见；WDA 侧 `pressButton` 能力与方案⑤共同一个待 spike 项；
4. **对本 Demo 的净增量评估**：本机是 macOS + Xcode 27，devicectl/XCUITest 已在手，
   go-ios 对三动词的增量为**零**（任何一条都要先 runwda，等于引入 WDA 签名与常驻依赖，
   而 WDA 路线方案⑤文档更全、社区更大）。其差异化价值（无 Mac 的 Linux/Windows CI、
   免 Xcode 截图/syslog）与当前场景不匹配；
5. 兼容性留白：公开实操资料最新到 iOS 18，**iOS 26/27（本机真机 27.2）兼容性零实证**，
   列入 S-4；隧道在断线重连/无人值守 CI 的行为同样待 spike。

### A.4 若未来引入的架构契合度（预判，不代表立项）

- 进程出口：CLI 形态可经唯一 SubprocessExecutor 以 argv 数组调用，无 shell 面，架构兼容；
- 提权与守护：tunnel 必须人工/机器级预置，profile 只配隧道端点，平台不代起 sudo——
  与 os-log-device 的 manual 模式同范式；
- 新基建代价：Go 二进制（或 npm 分发）+ WDA 签名 bundle + 常驻隧道，属 P1 之后独立
  切片，schema 可继续保持零 DDL；
- 否决条件（任一命中即不引入）：S-4 证实无原生动词且 WDA 路线已由方案⑤承接、
  iOS 27 不兼容、隧道无人值守不可靠。

## 附录 B：Device Hub 菜单/工具条合成输入隔离墙取证（2026-11-13，E-A 本机实测）

起因：用户提供 Controls 菜单截图（Home/Lock/Siri/App Switcher/Action Button/Rotate
Left/Rotate Right/Screenshot/Record Screen 九动词），要求调研菜单按钮触发方案。
完整报告与 17 张前后对照截图、32 个渐进取证脚本存
`subsystems/out/eval/device-hub-stimulus-probe/`（gitignored 工作产物）；
可重跑探针 `subsystems/scripts/device_hub_ax_probe.swift`（默认只读零副作用，

### B.1 环境与方法

- Xcode 27.0 内置 Device Hub 255.2.6.6（bundle id `com.apple.dt.Devices`），
  载体为 iPhone 17 模拟器 iOS 27.0；物理真机当时 unavailable，**真机行为未验**。
- 方法：libproc 按可执行路径解析真实 PID → 原生 AXUIElement API 枚举/动作 →

  因果判读与健康对照。每次动作均有前后截图，不信 AX 调用返回码的"假成功"。

### B.2 关键证据（E15–E23，完整台账见 out/eval 报告）

- **E15 应用事实**：无 sdef、entitlement 为零、无沙盒；URL scheme 仅 `devices://`
  且二进制内无动作型 URL 路径。

  unix id=0/0 menu bar/AppleEvent 超时（-1712）；libproc 真实 PID + 原生 AX 可完整

  AppleScript 方案在 E2 之外再添一层实测否决。
- **E17 选择器素材稳定**：菜单快捷键走 AXMenuItemCmdChar/CmdModifiers（语言无关，
  Home=⌃⌘H、Lock=⌘L）；窗口工具条按钮带 SF Symbol 标识符（Home=`app.grid.3x3`、
  Screenshot=`camera.viewfinder`、Record=`record.circle`），不依赖中文/英文文案。

- **E20 设备动词七通道全惰性**：菜单 AXPress（单/两步）、菜单与工具条 HID 实时坐标
  点击、工具条 AXPress、CGEvent postToPid、CGEvent hid-tap、System Events keystroke、
  Capture Keyboard 开/关两态——全部成功返回，设备侧零变化（不回主屏、不锁屏、不旋转、
  无截图文件），13 张截图为证。
- **E21 设备健康反证**：`simctl openurl` 成功拉起 Safari 加载 example.com，故障隔离
  在 DH 的 HID 转发路径。
- **E22**：Home 按钮仅支持 AXPress 单一动作，无备用 AX 入口。
- **E23 边界**：仅模拟器结论；真机待验；CGEvent 之下仅剩原始 IOHIDEvent 构造（S-7，缓议）。

### B.4 物理真机复跑：AX 语义通道有效、HID 通道仍惰性（2026-11-13 晚，E-A 实测）

真机复跑后，B.2/B.3 的模拟器结论被**部分推翻并收窄**：隔离墙不是"所有合成输入"，
而是只挡 HID/CGEvent 这一类带合成事件归因的输入；辅助功能层的语义动作在真机上能
真实驱动设备。

**环境**：iPhone 16 Pro（UDID 00008140-001A39590162801C），iOS 27.2，wired 连接、
开发者模式 enabled；Xcode 27.0 内置 Device Hub 255.2.6.6（PID 83446）；Mac 端
AX 授权已具备。设备侧因果判读一律用 `devicectl device capture screenshot` 前后对照，
不信 AX 返回码。动作仅限设置/Safari 拉起、Home、Rotate（已复原竖屏），无锁屏/抹除。

**证据 E24–E30**：

- **E24 锁屏是硬环境门控**：实验中途 Mac 进入锁屏（`CGSessionCopyCurrentDictionary`
  的 `CGSSessionScreenIsLocked=1`，HIDIdleTime ≈34 分钟）。锁屏下 DH 与 Finder 的窗口
  frame 全部塌缩为 (0,0,0,0)，SwiftUI 设备磁贴/工具条 AX 子树完全不物化（结果表只剩
  一个 Title 空列），AX 置 frontmost 返回 err=0 但属性不翻转，`screencapture` 报
  "could not create image from display"。人工解锁后同一 PID 的两个会话窗口立即带真实
  几何（1100×800）物化，工具条按钮带实时坐标。**无人值守方案必须把"Mac 解锁+会话窗口
  已物化"列为前置断言，锁屏态没有纯软件绕过。**
- **E25 AXPress Home 真机有效且可重复（2/2）**：devicectl 拉起 `com.apple.Preferences`
  并截图确认设置页 → 工具条 `app.grid.3x3` AXPress（err=0）→ 截图为真机主屏
  （01→02）；重拉设置再做一轮（05→06）同样回主屏。设备侧效果由 devicectl 截图证实，
  不是返回码假成功。
- **E26 HID 合成点击真机仍惰性（两动词对照）**：同一 `app.grid.3x3` 用 CGEvent
  `.cghidEventTap` 在实时坐标发真实鼠标 down/up（光标自动复原），设置页不回主屏
  （03→04 停留设置）；Rotate Left 同样 HID 点击后截图尺寸维持 2622×1206 横屏（11）。
  模拟器 E20 的 HID 墙在真机原样复现。
- **E27 AXPress Rotate Left 真机有效，且暴露朝向渲染约束**：Safari 竖屏截图
  1206×2622 → AXPress 后 2622×1206 横屏（09→10），逐次按压最终回到 1206×2622 竖屏
  复原。注意两条约束：① 主屏不支持旋转，在主屏按 Rotate 截图无变化（07/08 相同），
  验证旋转类动词必须用 Safari 等支持横屏的 App；② 无 Home 键 iPhone 不渲染
  portraitUpsideDown，四个物理朝向里有一个 UI 不落地，连续旋转的界面态不是简单四等分，
  自动化要以截图尺寸/内容做断言而非按按压次数推算朝向。
- **E28 真机 Controls 菜单全程灰显**：会话存活、工具条可用的整个窗口期间，Controls
  七个菜单项始终 en=false（与模拟器 E18"挂会话后菜单 enable"不同）。工具条只暴露
  Home/Screenshot/Rotate Left 三个动词，**Lock/Siri/App Switcher/Action Button/
  Record Screen 五个菜单动词在真机当前形态下无可达 AX 入口**，为什么菜单不 enable
  列为 S-8。
- **E29 devicectl 无旁路动词**：`devicectl device` 子命令盘点（capture/process/
  orientation/simulate/notification/pasteboard 等），`simulate` 仅 biometrics/
  location/statusBar，`orientation` 仅朝向——没有 Home/lock/tap 类刺激动词，
  九动词的官方 CLI 对等物不存在，DH 工具条是目前唯一实测有效的真机语义刺激面。
- **E30 机制推断（标注为推断，非苹果官方说明）**：AX `kAXPressAction` 走的是辅助功能
  语义通道，Device Kit 在 CoreDevice 真机会话里把它翻译成设备控制命令，因此不经过
  HID 事件归因校验；CGEvent 合成的鼠标/键盘即便投到 `.cghidEventTap` 仍带合成事件标记，
  在设备 HID 转发路径被丢弃。模拟器上 AX 也惰性（E20），说明模拟器的 DH 控制桥没有把
  AXPress 接到设备动词，是模拟器栈的实现缺口而非 AX 通道本身受限。

- **E31 生产 CLI 首跑：设备 unavailable 时 readiness 按契约 fail-loud（2026-11-14，本机实测）**：
  入库的生产形态 `subsystems/scripts/device_hub_ax_cli.swift` 首跑 `readiness` 动词，
  退出码 4 并输出诊断 JSON（零尺寸窗口 + 工具条三按钮不可达）。同日 `devicectl list
  devices` 显示物理真机 iPhone 16 Pro（硬件 UDID `00008140-001A39590162801C`）连接态为
  unavailable（自 11-13 晚起断连/休眠），整机清单只剩模拟器；旧探针旁证 DH 进程
  frontmost=1 但工具条 AX 子树脱物化（仅剩 Close 按钮、菜单项 en=false），与 E28
  「工具条依赖活动设备会话」一致。这是环境态而非代码缺陷：CLI 没有把不可用伪装成成功，
  exit 4 + 结构化原因正是设计契约（适配器据此映射 `DhAxActionError`，编排器收口 blocked
  而非 failed）。**真机全绿四动词链路顺延到 H4 人工 runbook，设备重新连接后照单复跑**，
  本节不回填未取得的证据。
- **E32 devicectl 进程控制词汇表取证（2026-11-14，`devicectl device process --help`
  实测）**：进程子命令为 awaitTermination/launch/openURL/resume/sendMemoryWarning/
  signal/suspend/terminate；`terminate` 按 **`--pid`** 终止（无按 bundle id 终止动词），
  且全词汇表**没有进程清单/list 动词**——主机侧无法枚举某 App 是否存活，docs/15 §4 的
  `app_not_running` 探针因此恒判 unknown 是词汇表约束下的诚实结论；`launch` 支持
  `--terminate-existing` 与位置参数透传（映射段内 `--ak-purge-dates` 清场参数），
  截图动词为 `device capture screenshot --device <udid> --destination <path>`，产物 PNG。

**修正后的判决与方案影响**：

1. Device Hub 路线在**真机**上从"只读观测 + 人工 HITL"升级为**可立项的
   DeviceControlPort 候选**：AX 语义动作可无人值守驱动工具条动词，选择器用语言无关的
   SF Symbol 标识符（`app.grid.3x3`/`camera.viewfinder`，Rotate 无稳定 id 用
   AXDescription）。当前实测能力圈 = Home/Screenshot/Rotate 三动词。
2. 能力边界（写进契约前必须保留的前置条件）：① Mac 保持解锁且 DH 设备会话窗口已打开、
   AX 子树已物化（E24）；② 进程持辅助功能 TCC 授权；③ 仅工具条三动词可达，五个菜单
   动词待 S-8；④ 效果断言以 devicectl 截图为准，AX err=0 一律不作数；⑤ HID/CGEvent
   通道（含 cliclick/pyautogui 等同层工具）真机仍死，不要再投入；S-7（IOHIDEvent）
   动机随 AX 通道打通而进一步下降。
3. 无人值守锁屏/解锁/侧边键三主动词仍不在当前 DH 能力圈内，主排序维持 S-2 XCUITest、
   S-3 SpringBoard、S-5 WDA；DH AX 通道作为**补充刺激面**（回主屏、截屏、旋转）先接入，
   与 docs/12 §3.4 能力圈契约的关系在下一切片评估，不擅自扩契约。
4. 模拟器结论保留原值不回改（E15–E23 历史证据），仅以本节标注载体差异；任何探针结论
   继续显式标注验证载体（模拟器/真机、iOS 版本、DH 版本）。
